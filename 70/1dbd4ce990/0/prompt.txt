# Securing agent shell commands: what works

Nov 12, 2026 · @Daniel Bentes

Validating command strings is unsolved and will stay that way. What works is to constrain what the process can do, at the kernel, with credentials kept out of reach. Open-source tools for this exist, but they contain damage and do not judge intent.

## Why command validation keeps failing

The guard inspects a string while bash executes a program. Deciding what an arbitrary shell program will do is undecidable in general, so better rules won't close the gap.

- **Guards fail across the board.** Adversa's [GuardFall survey](https://securityaffairs.com/194546/ai/guardfall-flaw-hits-10-of-11-popular-open-source-ai-agents.html) (June 2026) bypassed the command filters of ten of eleven open-source agents. Only Continue held, and it still leaks on substitutions nested in quoted arguments and on the long tail of destructive-by-flag commands.
- **Denylists can't be completed.** An [arXiv study](https://arxiv.org/pdf/2606.15549) of about 1,700 real denylists found 69% to 98.6% miss at least one route to an operation they try to block. Closing just "read" takes roughly 217 extra commands per list.
- **Allowlists fail too.** [Trail of Bits](https://blog.trailofbits.com/2025/10/22/prompt-injection-to-rce-in-ai-agents/) got code execution through pre-approved commands such as `go test -exec`, `rg --pre=sh` and `fd -x=python3`. Codex's "safe" `git show` accepted `--output`, which writes arbitrary content into `.git/config` ([GitPwned](https://www.pillar.security/blog/gitpwned-allowlist-to-rce)).
- **Vendors say so themselves.** Anthropic's permission docs, as reported, concede that a `Bash(rm *)` rule doesn't stop `/bin/rm` or `bash -c 'rm …'`: rules match text and aren't a security boundary.
- **LLM judges are probabilistic.** The 38.7% recall measured in #305 fits the pattern. Anthropic's auto-mode classifier [misses 17%](https://www.digitalapplied.com/blog/claude-code-auto-mode-classifier-numbers-published) of a 52-case set of overeager actions, and an independent stress test put the miss rate at 81% on ambiguous authorization prompts.

## What works: enforce below the shell

Stop judging what a command says and constrain what the process can do. Three layers carry this:

1. **Kernel sandbox for filesystem and network.** How the agent spells the command stops mattering, because OS-level restrictions bind every subprocess, not just the agent's own tools. Both halves are needed: without network limits, readable files can be exfiltrated.
2. **Credentials outside the sandbox.** A proxy injects the real secret on outbound requests, so the agent only ever holds a useless session token.
3. **Rollback and narrowly scoped tokens** for the damage that remains possible inside the boundary.

## Open-source tools

agentsh is the closest thing to a correct command guard, because its policy sees the binary that actually runs. None of these tools has been run for this review.

| Tool | Mechanism | Licence | Caveat |
| --- | --- | --- | --- |
| [sandbox-runtime (`srt`)](https://github.com/anthropic-experimental/sandbox-runtime) | Seatbelt on macOS, bubblewrap on Linux, alpha Windows build, domain-filtering proxy | Apache-2.0 | Beta research preview; Anthropic reports 84% fewer permission prompts internally |
| [nono](https://news.ycombinator.com/item?id=47237327) | Landlock/Seatbelt plus a "phantom token" proxy that swaps a per-session token for the real credential outside the sandbox; rollback and audit | Apache-2.0 | Rated early alpha and not security-audited by an independent index |
| [agentsh](https://github.com/canyonroad/agentsh) | Hooks execve via seccomp user-notify, so `env sudo`, `find -exec sudo` and Python `subprocess` calls are all caught | Apache-2.0 | Linux kernel features required; falls back to ptrace where seccomp-notify is blocked |
| [just-bash](https://turso.tech/blog/agentfs-just-bash) (Vercel) | From-scratch TypeScript bash with an in-memory filesystem and no real shell underneath | Apache-2.0 | Suits data and text agents; can't run real toolchains |
| MicroVMs: E2B, microsandbox, matchlock | Hardware VM boundary; matchlock adds a credential proxy | E2B Apache-2.0, matchlock MIT | Heavier to run; the choice for untrusted repos, since process sandboxes are the weakest boundary and containers share the host kernel |

A wider list is in the [awesome-agent-sandboxes index](https://github.com/runtimeteam/awesome-agent-sandboxes), of which only the first part was read.

## What a sandbox does not solve

A sandbox limits where code runs, not what the agent is authorized to do. Three gaps remain:

- **Trust handoff.** Pillar's seven [July 2026 escapes](https://www.pillar.security/blog/the-week-of-sandbox-escapes) never broke a sandbox. Each abused something outside it that later read or ran the agent's output: git hooks, `.vscode` tasks, the Docker socket.
- **Escape hatches and fail-open defaults.** Claude Code's sandbox runs commands unsandboxed if it can't start, unless `failIfUnavailable` is set. Auto-approved commands can also set `dangerouslyDisableSandbox` without a prompt.
- **Authorized destruction.** `git push --force` or `terraform destroy` with a valid token passes any sandbox, because kernel hooks see raw syscalls and not application-level meaning. Token scope and method/path rules at the proxy are the controls here.

## Architecture for Flow

Flow should stop deciding from command text and control three things instead: where Bash can write, which hosts it can reach, and who holds the GitHub credential. This is a proposal built from Flow 3.16.0's code and Claude Code's sandbox docs; nothing in it has been built or run.

Flow today reads every Bash command in `tier-gate.sh` (2,497 lines) and `lib/command-parse.sh` (1,684 lines), then checks again in `git` and `gh` wrappers on PATH. `references/three-tier-safety.md` already lists eight cases none of that covers, including `/usr/bin/git`, curl to the GitHub API, login shells and gh extensions.

&#91;embedded content: Flow architecture · sandbox, broker, snapshot hook, GitHub\]

Bash runs inside the sandbox with no credential that can write to GitHub, so a push, merge or release cannot happen from a shell command however it is spelled. Those actions go through typed broker tools, where the tier gate reads fields such as a PR number instead of parsing shell.

## What each existing guard becomes

Every text-reading hook is replaced by a boundary or a typed check; the hooks can stay as early, friendly refusals but stop being relied on and stop growing.

| Today | Becomes | Why it holds |
| --- | --- | --- |
| `tier-gate.sh` plus the `git` and `gh` wrappers | Broker tools, with a PreToolUse hook matched on the broker's tool names applying `tiers.*` | Bash has no credential that can write to GitHub, so spelling is irrelevant |
| `block-unchecked-merge.sh` | A check inside the broker's merge tool | The PR number and merge method arrive as fields |
| `block-force-push.sh` | The push tool offers `force_with_lease` only | A plain force push has no tool |
| `block-destructive.sh` | Sandbox write boundary plus the snapshot hook | Outside the worktree is unwritable; inside is restorable |
| `block-secrets.sh` | `sandbox.credentials` deny entries and Read deny rules | Secrets from files and environment never reach Bash; secrets typed into the chat still can, so the hook stays as advice |
| `ask-issue-create.sh` | The same hook, matched on the broker's issue tool | It reads typed fields |
| GitHub rulesets from `/flow:setup` | Unchanged | Still the only control that applies to every tool and credential |

## Settings /flow:setup writes

`/flow:setup` writes this block to user settings, the way `bin/flow-setup-permissions.sh` writes ask rules today. User scope matters: per the [sandbox docs](https://code.claude.com/docs/en/sandboxing.md), a `false` for `allowUnsandboxedCommands` there holds even when a repository sets `true`.

```json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "allowUnsandboxedCommands": false,
    "network": {
      "allowedDomains": ["github.com", "api.github.com", "registry.npmjs.org"]
    },
    "credentials": {
      "files": [
        { "path": "~/.config/gh/hosts.yml", "mode": "deny" },
        { "path": "~/.git-credentials", "mode": "deny" },
        { "path": "~/.ssh", "mode": "deny" },
        { "path": "~/.aws/credentials", "mode": "deny" }
      ],
      "envVars": [
        { "name": "GH_TOKEN", "mode": "deny" },
        { "name": "GITHUB_TOKEN", "mode": "deny" }
      ]
    }
  },
  "permissions": {
    "deny": ["Read(~/.ssh/**)", "Read(~/.config/gh/**)", "Read(~/.git-credentials)", "Read(~/.aws/**)"]
  }
}
```

- `failIfUnavailable` closes the fail-open default, and `allowUnsandboxedCommands: false` makes Claude Code ignore `dangerouslyDisableSandbox`.
- `excludedCommands` stays empty: an excluded command runs unsandboxed.
- The Read deny rules are needed because Claude's file tools run outside the sandbox and ignore `denyRead`.
- The registry entry is an example; setup fills the list from the detected stack. There is no built-in credential deny list, so only listed files and variables are protected.

## The broker's typed tools

The broker is an MCP server shipped with the plugin; local MCP servers run outside the sandbox with the user's normal `gh` login. Tool names here are illustrative.

| Tool | Fields | Tier setting | Replaces |
| --- | --- | --- | --- |
| `push` | branch, `force_with_lease` | `tiers.push` | `git push` |
| `tag_push` | tag | `tiers.release` | `git push` of a tag, in any of its spellings |
| `pr_create` | base, head, title, body | `tiers.prCreate` | `gh pr create` |
| `pr_merge` | number, method | `tiers.merge`, floor `confirm` | `gh pr merge` and the unchecked-merge hook |
| `release_create` | tag, title, notes | `tiers.release`, floor `confirm` | `gh release create` |
| `issue_create` | title, body, labels | `tiers.issueCreate` | `gh issue create` |
| `issue_assign` | number, assignees | `tiers.issueAssign` | `gh issue edit --add-assignee` |

Three rules keep the broker from becoming the new hole:

1. **No repository field.** The target is origin as recorded at setup, never read from the worktree's git config.
2. **No shell.** The broker starts git and gh by argument list, with `core.hooksPath` pointed at nothing, so a hook or alias the agent wrote does not run with the credential.
3. **One action per call.** An approval covers the one PR number or tag in the call, which fixes today's approval-by-kind gap.

## Applied to issue #305

The recommendation for [#305](https://github.com/synaptiai/synapti-marketplace/issues/305) is not to rebuild `guard.command-intent` on shell text. Under this design a destructive command is either impossible (outside the worktree, or a GitHub write) or restorable (inside it), so the judgment has no safety role and its 80% recall bar stops mattering.

If a judgment is still wanted, ask it about a broker call, not a command:

- **What is sent (criterion 1):** the tool name, the PR or issue number, booleans, and a class for each ref (default branch, feature branch, tag). Titles and bodies are not sent.
- **Why a credential cannot reach the provider:** the state has no free-text field, and the GitHub credential is never in the agent's environment to be copied.
- **Bars (criterion 2):** unchanged. The 400 ms latency bar now applies to a few broker calls per session, not to the roughly 58% of Bash commands the earlier design would have judged.

## Rollout

Each phase ships with an end-to-end test written first with `tests/lib/e2e.sh`, as `AGENTS.md` requires, and each test attacks the boundary rather than a command spelling.

1. **Strict sandbox.** `/flow:setup` writes the settings block and `/flow:status` reports when the sandbox is off. Test: from Bash, reading `~/.ssh`, printing a GitHub token, writing outside the worktree and reaching a host off the allowlist all fail, each tried through the five GuardFall spellings.
2. **Broker and credential removal.** Commands move from `git push` and `gh pr merge` to broker tools. Test: each of the eight uncovered cases in `three-tier-safety.md` fails to push, merge or release, and a broker merge asks once for one PR.
3. **Snapshot hook.** Test: `rm -rf` of tracked and untracked files, `git reset --hard` and deleting `.git` are each restored from the store. Measure the added time per Bash call against the 400 ms bar.
4. **Freeze the parsers.** No new cases go into `tier-gate.sh` or `command-parse.sh`; the docs describe them as advice.

## Not yet verified

These are assumptions the design rests on; each needs a test before the phase that depends on it.

- **macOS keychain.** `gh` and git's osxkeychain helper keep tokens in the keychain, not in the files the settings deny. Whether a sandboxed command can read them is untested; phase 1's token test decides it.
- **Read access to private repositories.** Fetch inside the sandbox needs a read-only credential. Claude Code's `mask` mode could supply one, but it needs the experimental `network.tlsTerminate`, file masks act as deny on macOS, and git sends the token base64-encoded, which the substitution may not match. A broker `fetch` tool is the fallback.
- **Plugin MCP servers and hooks.** The docs say local MCP servers and hooks run outside the sandbox; that a plugin-bundled server does, and that PreToolUse hooks match its tool names, needs confirming.
- **Snapshot cost and coverage.** Time on a large repository is unmeasured, and ignored files such as `node_modules` or `.env` are not captured unless listed.
- **Windows.** The sandbox does not run on native Windows, so Git Bash sessions keep only the text hooks; WSL2 works.
- **File tools.** Edit and Write run outside the sandbox. A file they write that a host tool later runs is the trust-handoff gap, covered only by Claude Code's own protected paths.

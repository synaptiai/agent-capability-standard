## Deviations

- The TypeScript binding-fixture runner is the package's
  `packages/acs-core/test/bindings.test.ts` (the checks are the package's
  `checkBindings`), not `examples/standard_agents/test/bindings.test.ts`.
- `load_bindings(records, nodes, requires, ontology_version, known=None)`
  takes the ontology's nodes and `requires` pairs and the layer's ontology
  version, rather than a supported major, so V109 uses the core's
  `check_cited_versions`.
- I-JSON integers: |n| <= 2^53 is accepted (the reference executor's limit);
  the design's test named 2^53 as failing.
- A capability string that does not match the id pattern is V101 (unknown
  capability), not S303: the ontology decides what a capability is.
- §5.18.1's table gained `standard` and `destination` rows (RECONCILIATION
  C25, S5's destination policy), and V109 covers a cited `standard`.
- SECURITY.md §5.4's `persist` secret row says the command hook's scan is
  S4's; until S4 lands the prompt hook is what checks it.
- `schemas/interop/standard_agents_mapping.yaml` moved to 1.2.0 / 2.2.0 and
  `tests/test_standard_agents_interop.py` changed: the conventions must name
  the versions the binding implements (`packages/acs-core/src/ontology.gen.ts`),
  and the row-level mapping's versions (1.1.0 / 2.1.0, a dated record) must be
  of the same major and not newer. The index is not rewritten.
- I-JSON numbers (review round 2): the bound stays the Standard's ±2^53
  (§5.14, the reference executor's), not RFC 7493's 2^53 - 1, so no 1.1
  behaviour changes. Both languages refuse an integer beyond it and a float
  canonical JSON writes as one (1.8e16); TypeScript reads JSON text that is
  then checked with `parseJsonExact` (an integer literal beyond 2^53 as a
  `bigint`), and a value that arrives already parsed (Standard Agents tool
  arguments) is checked as it is, a host gap the binding's statement names.
- `approval.expires` is at most 2^53 - 1 ms (§5.18.1's table and the
  schema's description), the largest every loader holds exactly.
- The adapter's §5.18.10 output-contract row (R402) stays in `not_applied`:
  Claude Code's tools return no capability output and an MCP tool's result
  is its own form. No stream owns a host form for it (FOUNDATION-notes).
- `CLAUDE.md` is not edited by this session (an instructions file); its
  Hooks bullet still needs the replacement text under Review round 1.
- `index.yaml`'s status counts for the ACS findings are left for phase 5
  (other streams change statuses too).
- To meet the figure-gap limit without exemptions, §5.18's lists of
  conditions and codes are tables (§5.18.1's members as Field | Type |
  Required | Description, `capability` "No" with "required unless `control`
  is true"; §5.18.2's offered-tool checks; §5.18.4's composite codes;
  §5.18.5's edge types; §5.18.6's None valid and Rollback; §5.18.8's refusal
  codes). The rules are unchanged. The site draws them (CODE_TABLE_FIGURES,
  `table-5.18.1`), and adds figures for §3 (the design principles) and §10.4
  (the safety-layer fixtures); a slot at a chapter heading now titles its
  figure "from §3", not "from §3.".

## 1. Per finding: decision, rationale, how it fixes the finding

### ACS-05 — domain profiles: application semantics, thresholds, key grammars

**Decision.**

1. **Who applies a profile.** A profile has effect only where it is
   *applied*:
   - a **host** applies profiles to a run by giving them to the executor at
     start (S2b's §5.19.2 start operation gains `profiles`); they cover every
     step of the run, nested runs included (§5.12), and are saved with the run
     (§5.19.4); they do not cover runs of agents it delegates to (§5.15);
   - a **safety layer** (S1's §5.18) applies the profiles its configuration
     names to every call it covers;
   - a **validator** MAY be given profiles; it then validates as an executor
     applying them would run (F501, W606, W608). Whether a step may carry an
     `approval` field stays independent of profiles, so a workflow's validity
     on that point does not depend on where it runs.
   A workflow does not select a profile. Its `profile` field (§5.1) stays
   descriptive in every version: it records the profile the workflow was
   written for and applies nothing; a host MAY use it to choose.
2. **Tighten only, several at once.** Several profiles may be applied;
   each applies on its own and the strictest result holds. For flags, checks,
   evidence, confidence and destination rules a profile only tightens: it
   never lowers a flag, never removes a check and never changes `risk` or
   `mutation`. `trust_weights` is the exception, by design: it *replaces*
   weights, in either direction, as 1.1's §8.3 already allowed (a domain may
   trust its own systems of record more than the generic model does); it is
   bounded by §8.3's lower-of rule for a source and a trust class, and across
   several profiles the lowest weight per key applies.
3. **What each member changes** (for a step or call of capability C whose
   effective risk before profiles is R; levels ordered `none` < `low` <
   `medium` < `high`; a threshold is a *set of levels*: `auto_approve: L` covers
   the levels at or below L, `require_review`/`require_human: L` the levels at
   or above L, `none` covers no level):

   | Member | Effect |
   |---|---|
   | `risk_thresholds.auto_approve: L` | `requires_approval` when R is not covered (above L; `none`: every R) |
   | `risk_thresholds.require_review: L` | `requires_approval` when R is covered |
   | `risk_thresholds.require_human: L` | `requires_approval` and **a person** when R is covered |
   | `risk_thresholds.block_autonomous` | `requires_approval` and a person when C is listed |
   | `checkpoint_policy` | key C or `*`: `always` → `requires_checkpoint`; `high_risk` → when R is `high`; `medium_risk` → when R is `medium` or `high`; `never` → nothing. Never for C = `checkpoint` (a checkpoint step cannot need a checkpoint before itself; `*` does not cover it, and the key `checkpoint` is S303) |
   | `evidence_policy.require_grounding` + `required_anchor_types` | one grounding policy (S4 §5.20): `require`, `kinds` |
   | `evidence_policy.minimum_confidence: c` | a host output whose `confidence` is a number below c fails the step: F504, reason `below_minimum_confidence`; a `confidence` member that is not a number from 0 to 1 fails it: F504, reason `invalid_confidence`; highest c of all profiles |
   | `allowed_destinations` | a destination policy in force (S5 §4.4.2, S5's text) |
   | `trust_weights` | §8.3 overrides where the host computes trust scores, either way; lowest weight per key across profiles |
   | `domain`, `version`, `standard`, `ontology`, `description`, `domain_sources`, `workflows`, `trust_model_reviewed`, `trust_model_reviewed_at`, `compliance` | none (identification, citation, information) |

4. **"A person", for the step only.** A step a profile requires a person for
   is *asked* as a step that uses an always-ask item is (§5.17): the request
   names a `human` approver with `always_ask: true` and no `mandate_ref`,
   whatever `approver` declares; a standing mandate does not cover it; the
   decision is recorded with no `mandate_ref`; in an unattended run it is not
   asked and `when_unattended` applies. W606 (existing) reports a static path
   from an unattended trigger to such a step without `when_unattended`. That
   is all it shares with the always-ask path. The requirement is **not a
   mark** (§5.17): it does not pass to the step's output store, to steps that
   read it, to nested runs or to injected recovery context, because a profile
   names capabilities and risk levels, not data. Its action records carry the
   new optional member `person_required: true`, not `always_ask` (whose
   canonical meaning, "the action used an item from an always-ask trust
   class", stays exact), and the trace records `person_required` with the
   profiles that require it. This gives `require_human` ("human execution")
   and `block_autonomous` ("never run autonomously") one meaning the executor
   already has for the request: no action without a person's decision each
   time.
5. **Key grammars and loading.** A profile is checked when loaded, with
   existing codes and `location: {profile, field}`:
   missing `domain`/`version` S304; malformed values S303 (a `domain` that is
   not kebab-case, a `version` that is not SemVer, a threshold outside its
   enum, a weight outside [0,1], a `trust_class:<c>` key whose class is not
   one of `agent_identity.trust_class`, an anchor kind outside §6.5, an
   invalid destination pattern, the `checkpoint_policy` key `checkpoint`, and
   any member of `risk_thresholds` or `evidence_policy` this version does not
   define: both mappings are closed); a capability id the ontology does not
   define, in `block_autonomous`, in `require_grounding` or as a
   `checkpoint_policy` key other than `*`, V101 with the closest id (one code
   for one fault wherever it sits, as §11.6 says for a later ontology's ids);
   `never` on a capability whose ontology requires a checkpoint W602;
   `require_review`/`require_human: critical` W603 (read as `none`); unknown
   *top-level* members W604 (`x-` exempt), the one place an unknown key is
   ignored, because nothing nested under it could tighten anything;
   `standard` not supported or `ontology` of another major V109 (§11.6). Any
   error refuses the profile: an executor refuses to start (StartError
   Invalid), a safety layer to load, a validator reports. No misspelled rule
   is ignored: a misspelling inside a rule mapping is an error.
6. **Shipped profiles** are migrated (each to `version: "2.0.0"`, with
   `standard: "1.2.0"`, `ontology: "2.2.0"`): `checkpoint_policy` labels map to
   the capability that makes the change the label names (part 3.7); the 29
   `required_anchor_types` become §6.5 kinds (the kinds the old entries name,
   plus the kinds of the profile's own `domain_sources`); `require_human` keeps
   its values (no shipped profile uses `critical`).
7. **Implemented** once, in `core/src/profile.rs` (load, raise, policy),
   used by the validator (`validate::Options.profiles`) and the executor
   (`StartOptions.profiles`), exposed to Python (`_core.Validator.validate(...,
   profiles=)`, `check_profiles`, `profile_flags`, `profile_policy`,
   `Run.start(..., profiles=)`), to `tools/validate_workflows.py --profile`,
   `WorkflowRunner(profiles=)`, `GroundedAgentConfig(profiles=)` (the Python
   safety layer), and to TypeScript through the WebAssembly interface
   (`CoreContext.checkProfiles`, `profileFlags`, `profilePolicy`, and the
   `profiles` start and validate options). There is no pure-TypeScript
   profile loader: no TypeScript component applies profiles without the
   core, and a third implementation of a normative loader would drift. The
   plugin hooks apply no profile (a safety layer MAY).

**Options considered.**
- *Mark profiles informative* (the finding's alternative, done in round 2 as
  an interim): rejected by the maintainer's instruction and because the
  compliance documents need an enforceable control.
- *The workflow selects its profile* (`profile` becomes normative): rejected.
  The profile is deployment policy, as S4's host grounding policy and S5's
  destination policy are; a workflow that must have a checkpoint or approval
  everywhere declares the flag (§5.2.1). A normative `profile` would also need
  a path or registry resolution rule the Sans-IO executor cannot perform.
- *Profiles may loosen* (e.g. `auto_approve` lifting the ontology's
  approval): rejected; §3.3 says a workflow cannot weaken the ontology, and a
  deployment policy must not either. (`trust_weights` is not a safety flag;
  it was always a replacement, §8.3.)
- *Remove `critical`*: rejected for a deprecation (W603, read as `none`), so a
  third-party profile that uses it still loads; `none` gives require_* the
  "no level" value `critical` was standing in for.
- *Free-form `checkpoint_policy` labels kept, ignored, or loaded with W604*
  (the first revision): a warning does not stop a run, so a misspelled id
  (`mutat: always`) would silently drop a checkpoint rule, and V101 for the
  same id in `block_autonomous` but W604 here gave one fault two codes. No
  1.1 component ever applied a profile, so label-keyed profiles have no
  behaviour to keep: V101.
- *Unknown members of `risk_thresholds`/`evidence_policy` as W604*: the same
  fail-open (`require_humen: low` ignored). Both mappings are closed in this
  version (S303); a later version that adds a member is a profile format
  change (§11.6 citation, `standard`).
- *Let `checkpoint_policy` raise `requires_checkpoint` on a `checkpoint`
  step*: `"*": always` would then make every workflow F501 at its first
  checkpoint (verified against the reference validator: a `checkpoint` step
  with `requires_checkpoint: true` is F501 at step 0), so the rule could not
  be met. Exempt, and the key `checkpoint` is S303 (a W602 "has no effect"
  would misname it: nothing is downgraded).
- *Mark the data of a person-required step* (reuse the whole always-ask
  path, the first revision): the mark would spread to every step that reads
  the output and to nested runs, asking a person for steps no profile
  covers, and the records would claim an always-ask trust class item that
  was never there.
- *`required_anchor_types` entries that are not kinds ignored*: fails open
  (no `kinds` filter at all when every entry is unknown). S303 instead.
- *A non-numeric `confidence` passes a minimum* (the first revision's
  `below_minimum` read numbers only, and the executor's output check reads
  presence only): `"0.1"` or `null` would pass the floor. F504 with its own
  reason `invalid_confidence`, so a host or auditor sees a malformed output
  apart from a low one; a failure mode `on_error: [F504]` matches both.
- *`minimum_confidence` as part of the grounding policy only*: rejected; the
  profile field says "for actions", and a failing step is predictable,
  recorded and catchable by a failure mode (`on_error: [F504]`).
- *A new code for profile errors or the confidence floor*: rejected; S303,
  S304, V101, V109, W602–W604 and F504 already say what is wrong.

**How it fixes the finding.** §5.21 says how a run selects profiles (the host
gives them), gives a tighten-only merge rule like §5.2.1's for every member
but the trust weights (which replace, as §8.3 always said), defines every
member in terms of effective flags and §5.14, ties every key grammar to
capability ids, `Anchor.kind` (§6.5) and trust classes, refuses every
malformed or misspelled rule, assigns diagnostics, and the executor,
validator and Python adapter implement it (TypeScript through the core)
against normative vectors. `critical` is resolved. The EU AI Act sentence
"Enforced at profile evaluation level" becomes true for hosts that apply the
profile, and the compliance documents name them.

### ACS-28 — the ontology's schema dialect

**Decision.**

1. **§4.1.2 Schema Dialect.** Capability contracts, and the type definitions
   of the canonical and supporting schemas that a contract reaches through
   `$ref`, are written in the **ACS schema dialect**:
   - keywords with their Draft 2020-12 meaning: `type` (a name or a list of
     names), `enum`, `const`, `properties`, `required`,
     `additionalProperties` (a boolean or a schema), `items` (one schema),
     `minimum`, `maximum`, `minLength`, `maxLength`, `pattern`, `format`,
     `minItems`, `maxItems`, `uniqueItems`, `oneOf`, `anyOf`, `allOf`,
     `description`, `title`, `default`, `examples`;
   - `type: any`: every JSON value; it may stand beside annotations
     (`description`, `title`, `default`, `examples`, `nullable`, `x-` keys)
     only; for §5.4 it is missing type metadata (a reference to it needs an
     annotation, B204; paths below it are open);
   - `type: "a|b"` (two or more distinct primitive names, not `null`): the same
     as `type: [a, b]`;
   - `$ref`: `<path>#<pointer>` (a path relative to the schema root, the
     repository root, that stays inside it) or `#<pointer>` (the same file); a
     JSON Pointer (RFC 6901). It is replaced by the schema it names, and the
     keywords beside it replace the target's keywords of the same name (a
     merge, unlike Draft 2020-12's conjunction). A `$ref` that names nothing,
     a cycle of `$ref`s (a recursive type), and a chain deeper than the
     implementation's limit (the reference core's is 12) are outside the
     dialect. The reference core refuses to load an ontology whose contract
     still holds a `$ref` once resolved (a load error, since contracts have no
     diagnostic channel); a workflow schema's `$ref` that names nothing stays
     S302;
   - `nullable: true` (OpenAPI 3.0's keyword): the value may also be `null`.
     For §5.4 type inference, `nullable` is not read (1.1's behaviour, kept
     so no 1.1 workflow gains W610);
   - keys starting with `x-` are annotations; `x-acs-` keys are this
     Standard's own.
   No other keyword is used. Every schema has a Draft 2020-12 **rendering**
   (rules normative): `a|b` → a type list; `any` → no `type` and
   `"x-acs-type": "any"`; `$ref` → the merged target, rendered (it terminates,
   since cycles are outside the dialect); `nullable: true` → `"null"` added to
   the type list (nothing added where no `type`); everything else unchanged.
   The rendering is exact on *values* (it accepts what the dialect accepts),
   not on *inferred types*: §5.4 reads a rendered `["number", "null"]` as
   nullable but does not read the dialect's `nullable: true`, so a validator
   reading the rendering can report W610 where one reading the dialect does
   not. The text says so, and a test pins it.
2. **`x-acs-type` adopted** (not renamed): it is already published, `x-`
   keeps it clear of future JSON Schema keywords, and Appendix B reserves
   `x-acs-` for this Standard so no vendor key collides.
3. **The published rendering** `schemas/generated/capability_contracts.schema.json`
   stays generated and checked in CI; the generator renders the contracts the
   core resolved (`_core.Validator.contracts()`), so `$ref`s from S4's
   ontology changes (`schemas/event_schema.yaml#/types/Anchor`) and their
   `nullable` members are rendered by one resolver, and a `$ref` that does
   not resolve stops the load in every consumer, not only in the generator.
   The generator's docstring states the `nullable` divergence; the test that
   compares the validator on the dialect with the validator on the rendering
   builds its strict ontology without the added `"null"` (part 6.4), and a
   probe pins the divergence.
4. **Machine check of the dialect.** `capability_ontology.schema.json` gains
   `$defs/contract_schema` (a recursive metaschema of the dialect);
   `input_schema` and `output_schema` reference it, so
   `tests/test_validators.py::test_ontology_validates_against_schema` fails on
   a keyword outside the dialect, `any` beside an assertion, or `a|null`.
5. **Per-skill output schemas** (`skills/*/schemas/output_schema.yaml`) stay in
   the dialect (they are read by skill authors and models), are written from
   the resolved contract (self-contained: no `$ref` to a file outside the
   skill), and their header names §4.1.2 and the rendering's `$defs` entry.

**Options considered.** *Rewrite the ontology in strict 2020-12*: a field
type change for 32 slots and churn for every consumer of the YAML; the
dialect is defined instead (the finding's own proposal). *Render `$ref` into
`$defs`*: rejected; the dialect's merge semantics differ from 2020-12's
`$ref`, and inlining the merged target is exact. *Rename `x-acs-type`*:
rejected (published, and nothing gained). *Leave `$ref`/`nullable` out of the
dialect*: impossible once S4's contracts reference the canonical `Anchor`.
*Define recursive `$ref`s* (render to `$defs` with a 2020-12 `$ref`):
nothing in the ontology or the canonical types a contract reaches is
recursive, and §5.4's path typing would need a fixed point; outside the
dialect, and refused at load. *Make §5.4 read `nullable`*: would add W610 to
1.1 workflows that order on such a member; the divergence is stated
instead. *Make the published rendering drop `"null"`*: it would then refuse
`null` values the dialect accepts; exactness on values is what a JSON Schema
consumer needs.

**Decision.**

### ACS-56 — trust arithmetic and vectors

**Decision.**

1. **§8.1** states the score `weight × confidence × decay` (in that order, in
   binary64), with the open cases decided:
   - *composition*: the product of `authority_trust_model.yaml`'s formula,
     now in the Standard;
   - *no reported confidence*: confidence 1 (the formula without the factor,
     what the benchmark computes);
   - *negative age*: counts as zero (a future-dated observation is never
     fresher than a present one; refusing it would make clock skew between
     sources an error). The reference function changes from refusing to
     clamping;
   - *`min_trust` above 0.5*: the floor applies; the 0.5 requirement is on the
     unfloored curve, so both hold;
   - *unknown weights*: evidence without a static weight has no score, and an
     implementation refuses to score it (no invented weight);
   - *field authority*: not a score factor; it ranks sources in §8.2.
2. **§8.2** defines six strategies — `highest_score` (new, the default: what
   the model's `conflict_resolution_function` describes),
   `prefer_authoritative_sources` (authorities for the field first, then the
   highest static weight), `prefer_recent`, `prefer_high_confidence`,
   `merge_with_uncertainty` (all, highest score first), `escalate_to_human` —
   ties within 10⁻¹², broken by the model's `tie_breakers` in order
   (`prefer_authoritative_source`, `prefer_high_confidence`, `prefer_recent`,
   `escalate_to_human`), still tied → escalated; a candidate without a static
   weight makes the conflict refused.
3. **§8.3** restated with the profile override rules (the class key must
   name a known class: S303 on load; any other key replaces or adds a source
   weight, in either direction; lowest weight across profiles).
4. **Field authorities have a binding member.** In 1.1 the data sat under
   `field_authority.examples`, a name that reads as illustration. The trust
   model gains `field_authority.fields` (an additive member of the canonical
   schema, 1.2.0): a list of `{field, authorities}` whose authorities are
   source types of `source_ranking.weights`; §8.2 and `TrustModel` read
   `fields` only. The canonical file's `fields` holds the three entries 1.1
   gave as examples; `examples` stays, unchanged and described as
   illustrative (a 1.1 reader still finds it). A host's own trust model puts
   its real authorities in `fields`. `tools/validate_canonical_schemas.py`
   checks `fields`.
5. **Vectors normative** (§10.3): `tests/conformance/trust/{decay,weight,score}.json`
   move to `standard: "1.2.0"`, `status: "normative"`, their `not_covered`
   cases become vectors (error vectors where the rule refuses); new
   `resolve.json`. `grounded_agency/trust.py` is the reference: `decay_factor`
   clamps a negative age; new `Candidate`, `Resolution`, `resolve`,
   `merge_trust_weights`; `TrustModel.from_mapping` reads
   `field_authority.fields` and `tie_breakers`.
   `benchmarks/scenarios/conflicting_sources.py` calls
   `grounded_agency.trust.resolve` (strategy `highest_score`) instead of
   `_recency_weight` and its own `>=` selection, so it implements §8.2 and
   its exact ties follow the tie-breakers. The published results do not
   change: over seeds 42, 0, 1, 7 and 123 (100 cases each) the smallest gap
   between the two candidates' scores is 6.8 × 10⁻⁴, far above the 10⁻¹² tie
   tolerance, so no case was decided by the old `>=` (measured for this
   design on the repository's benchmark).

**Options considered.** *Refuse a negative age* (the 1.1 reference): rejected
for the robustness reason above. *Forbid `min_trust` above 0.5*: rejected; a
deployment that wants age to matter little is legitimate, and the floor's
meaning is unambiguous. *Make field authority a multiplier*: no basis for a
number in the Standard or schema. *Leave §8.2 strategies undefined*: the
finding's remaining item; an integrator could not test them. *Declare the
entries of `field_authority.examples` binding*: a member named examples
would carry normative data, and a host would have no place for its real
authorities that does not read as illustration; an additive `fields` is
clearer. *Keep the benchmark's own selection and call it a §8.1 scorer*:
then the repository's one conflict-resolving program would not implement
§8.2; calling `resolve` changes no published number.

**How it fixes the finding.** One reusable reference function, language-
neutral vectors named by §10.3 as normative, every case they left open
decided, §8.2 and field authority given arithmetic, and the benchmark's
private copy replaced.

### 2.6 §4.1.2 Schema Dialect *(new, after S4's §4.1.1)*

````markdown
#### 4.1.2 Schema Dialect

A capability's `input_schema` and `output_schema`, and the definitions in the
canonical and supporting schemas (§6.1) that a contract reaches through
`$ref`, are written in the **schema dialect**. A workflow's `inputs`
declarations and the files they and `output_conforms_to` reference (§5.1,
§5.2) SHOULD be written in it too; a validator reads a keyword outside it as
an annotation.

These keywords have their JSON Schema Draft 2020-12 meaning: `type` (one
type name or a list of them), `enum`, `const`, `properties`, `required`,
`additionalProperties` (a boolean or a schema), `items` (one schema),
`minimum`, `maximum`, `minLength`, `maxLength`, `pattern`, `format`,
`minItems`, `maxItems`, `uniqueItems`, `oneOf`, `anyOf`, `allOf`,
`description`, `title`, `default` and `examples`. No other Draft 2020-12
keyword is used. The dialect adds:

| Form | Meaning |
|------|---------|
| `type: any` | Every JSON value. It MAY stand only beside `description`, `title`, `default`, `examples`, `nullable` and `x-` keys. For §5.4 it is missing type metadata: a reference to it needs an annotation (B204), and paths below it are open |
| `type: "a|b"` | Two or more distinct type names other than `null`, joined by `|`: the same as `type: [a, b]` |
| `$ref: "<path>#<pointer>"`, `$ref: "#<pointer>"` | The schema the JSON Pointer (RFC 6901) names in the file at `<path>`, a path relative to the schema root (the repository root) that does not leave it, or in the same file. The keywords beside `$ref` replace the target's keywords of the same name |
| `nullable: true` | The value MAY also be `null`. Type inference (§5.4) does not read it |
| keys starting with `x-` | Annotations, never assertions. Keys starting with `x-acs-` are this Standard's (Appendix B) |

A `$ref` is resolved before any other rule reads the schema. A `$ref` that
names nothing, a `$ref` that reaches itself again (a cycle: the dialect has
no recursive types), and a chain of `$ref`s deeper than an implementation's
limit are outside the dialect. An implementation refuses an ontology whose
contract holds one when it loads the ontology. In a workflow's `inputs`
declarations, a reference that names nothing is S302.

**Rendering.** A schema of the dialect is rendered in Draft 2020-12 by:
replacing `"a|b"` with the list `["a", "b"]`; replacing `type: any` with no
`type` and the annotation `"x-acs-type": "any"`, which keeps it apart from a
schema that states no type; replacing a `$ref` with the rendering of its
target with the keywords beside it merged as above; adding `"null"` to the
`type` of a schema with `nullable: true` (to its list, or making a list of a
single name; nothing where it has no `type`) and dropping `nullable`; and
keeping every other keyword. A schema and its rendering accept the same
values. They need not give §5.4 the same types: §5.4 reads `"null"` in a
`type` list but not `nullable`, so a reference to a member with `nullable:
true` is nullable in the rendering only (W610 can differ).
`schemas/generated/capability_contracts.schema.json` is the rendering of
every contract of the ontology, `$defs` `<capability>.input` and
`<capability>.output`; it is generated, and the ontology stays the source.
````

### 2.11 §5.21 Domain Profiles *(new, after S4's §5.20)*

````markdown
### 5.21 Domain Profiles

A **domain profile** states, for one domain, rules that tighten what this
Standard requires of steps and calls: which need a checkpoint, which need
approval and from whom, what counts as evidence, how confident an output
must be, where a `send` may go and how sources are weighed. A profile is a
YAML or JSON document of the shape `schemas/profiles/profile_schema.yaml`
gives. The profiles under `schemas/profiles/` are examples.

#### 5.21.1 Applying Profiles

A profile has effect only where it is **applied**:

- A host applies profiles to a run by giving them when it starts the run
  (§5.19.2). They apply to every step of the run, the steps of its nested runs
  included (§5.12), and stay with the run when it is saved and restored
  (§5.19.4). They do not apply to the runs of the agents it delegates to
  (§5.15), which those agents' hosts govern.
- A safety layer (§5.18) applies the profiles its configuration names to
  every call it covers.
- A validator MAY be given profiles. It then validates each workflow with the
  effective flags of §5.21.3, so that F501, W606 and W608 see what a run under
  those profiles would; nothing else changes. Without profiles it validates as
  if none were applied.

A workflow does not select a profile. Its `profile` field (§5.1) records the
profile it was written for and applies nothing; a host MAY use it to choose
the profiles it applies. A workflow that needs a checkpoint or an approval
wherever it runs declares the flag itself (§5.2.1). Whether a step may carry
an `approval` field (§5.14) does not depend on profiles: declare
`requires_approval: true` on a step whose approval only a profile would
require, to say how it is asked.

Several profiles MAY be applied together. Each applies on its own: a step or
call meets every one, so the strictest result holds. For flags, checks,
evidence, confidence and destinations a profile only tightens: it never
lowers a flag, never removes a check and never changes a step's `risk` or
`mutation`. Its `trust_weights` are different: they replace weights, higher
or lower, as §8.3 says, bounded by §8.3's rule that evidence with both a
source type and a trust class weighs the lower of the two; with several
profiles, the lowest weight given to a key applies.

#### 5.21.2 Loading a Profile

An implementation checks a profile before it applies it, and refuses a
profile with an error: an executor does not start the run, a safety layer
does not load its configuration, a validator reports the errors. A
diagnostic about a profile has `location.profile` (its `domain`, or `#<i>`,
its zero-based position among the profiles given, when it has no valid
`domain`) and `location.field` (the path to the member, such as
`risk_thresholds.block_autonomous[1]`).

| Member | Required | Value |
|--------|----------|-------|
| `domain` | Yes | Lower-case letters and digits, in words joined by single `-` |
| `version` | Yes | The profile's own version, `MAJOR.MINOR.PATCH` |
| `standard`, `ontology` | No | The Standard and ontology versions the profile is written for (§11.6) |
| `trust_weights` | No | A mapping of keys to numbers from 0 to 1: `trust_class:<class>`, where `<class>` is a trust class of `agent_identity_schema.yaml`, or a source key: a lower-case letter, then lower-case letters, digits, `_`, `.` or `-` |
| `risk_thresholds` | No | A mapping of exactly these members, each optional: `auto_approve` (`none`, `low`, `medium` or `high`), `require_review` and `require_human` (the same four), `block_autonomous` (a list of capability ids) |
| `checkpoint_policy` | No | A mapping of `*`, or a capability id other than `checkpoint`, to `always`, `high_risk`, `medium_risk` or `never` |
| `evidence_policy` | No | A mapping of exactly these members, each optional: `required_anchor_types` (a non-empty list of distinct anchor kinds, §6.5), `minimum_confidence` (a number from 0 to 1), `require_grounding` (a list of distinct capability ids) |
| `allowed_destinations` | No | A destination policy (§4.4.2) |
| `description`, `domain_sources`, `workflows`, `trust_model_reviewed`, `trust_model_reviewed_at`, `compliance` | No | Informative; no effect |

- A profile that is not a mapping, and a member of the wrong type or outside
  its grammar (a `trust_class:` key whose class is not a trust class, a kind
  outside §6.5, an invalid destination pattern, the `checkpoint_policy` key
  `checkpoint`), is S303; so is a member of `risk_thresholds` or
  `evidence_policy` that the table does not list, whatever its name: both
  mappings are closed. A missing `domain` or `version` is S304.
- A capability id the ontology does not define, in `block_autonomous`, in
  `require_grounding` or as a `checkpoint_policy` key other than `*`, is
  V101.
- A `standard` the implementation does not support, or an `ontology` whose
  major differs from its ontology's, is V109 (§11.6).
- A top-level member the table does not list is W604 and is ignored, except
  a member whose name starts with `x-`, which is never reported.
- `never` for a capability whose ontology requires a checkpoint is W602: it
  has no effect.
- `critical` as `require_review` or `require_human` is W603 and is read as
  `none`; it is deprecated.

#### 5.21.3 Effect on Steps and Calls

For a step, or a call classified by §5.18.3, let C be its capability and R
its effective risk (§5.2.1, before profiles). A threshold covers a set of
risk levels: `auto_approve: L` covers L and the levels below it,
`require_review: L` and `require_human: L` cover L and the levels above it,
and `none` covers no level (`low` < `medium` < `high`). Each applied profile
raises:

| Member | Raises |
|--------|--------|
| `risk_thresholds.auto_approve` | `requires_approval` when R is not covered |
| `risk_thresholds.require_review` | `requires_approval` when R is covered |
| `risk_thresholds.require_human` | `requires_approval`, and requires **a person**, when R is covered |
| `risk_thresholds.block_autonomous` | `requires_approval`, and requires a person, when C is listed |
| `checkpoint_policy` | `requires_checkpoint` when C is not `checkpoint` and the value for C or for `*` is `always`, is `high_risk` and R is `high`, or is `medium_risk` and R is `medium` or `high` |

An absent member raises nothing. The raised flags are effective flags
(§5.2.1): a step whose `requires_checkpoint` a profile raised needs a
`checkpoint` running before it (F501) and uses a valid checkpoint before it
runs (§4.4.1); one whose `requires_approval` a profile raised is asked for
approval (§5.14), and counts as a step that acts in §5.14's deferral rules.
A `checkpoint` step is never given `requires_checkpoint` by a profile: it
would need a checkpoint before itself.

**A person.** A step that a profile requires a person for is asked as a step
that uses an always-ask item is asked (§5.17): the request names a `human`
approver, with `always_ask: true` and no `mandate_ref`, whatever its
`approver` declares; a standing mandate does not cover it, and the decision
is recorded with no `mandate_ref`; in an unattended run it is not asked, and
its `when_unattended` applies (W606 where an unattended trigger reaches it
without one, §9.7). The requirement belongs to that step alone. It is not a
mark (§5.17): it does not pass to the step's output or to the steps that
read it, to the nested runs the step starts, or to context injected for
recovery (§5.12), each of which a profile governs by its own capability and
risk. The step's action records carry `person_required: true`
(`ActionRecord`, `world_state_schema.yaml`); they carry `always_ask: true`
only if the step also uses an always-ask item. A safety layer accepts for
such a call only a decision a person made for it.

Each applied profile also puts in force:

- **Evidence.** `require_grounding`, with `required_anchor_types` as its
  `kinds`, is a grounding policy (§5.20) applied as a host's: an output of a
  step whose capability it lists must pass it. `required_anchor_types`
  without `require_grounding` has no effect.
- **Minimum confidence.** When a minimum applies and an output a host
  returns for a step has a `confidence` member, that member MUST be a number
  from 0 to 1: one that is not (a string, `null`, a boolean, a number outside
  the range) fails the step with F504 and the reason `invalid_confidence`;
  one below `minimum_confidence` fails it with F504 and the reason
  `below_minimum_confidence` (§5.19.7). An output without a `confidence`
  member is not checked: a capability whose contract requires one already
  fails such an output (R402), and one whose contract does not require it
  reports no confidence to compare. The check comes after the grounding check
  and before the step's after-gates; outputs the executor builds itself are
  not checked (§5.20). With several profiles, the highest minimum applies.
- **Destinations.** `allowed_destinations` (optional): a destination policy
  (§4.4.2). A profile applied to a run, or to a safety layer, puts it in force
  beside the host's own policies, so a send must be allowed by each. An empty
  list allows no send. A profile whose list holds an invalid pattern is
  refused when it is loaded.
- **Trust weights.** Where a host computes trust scores for the run's
  evidence (§8), `trust_weights` overrides weights as §8.3 says.

A safety layer that applies a profile applies these to the outputs of the
calls it covers, as §5.20 says for hosts outside a workflow.

#### 5.21.4 Conformance

An implementation that applies profiles (an executor, a safety layer, or a
validator given them) MUST report each profile vector's diagnostics and
compute each one's effective flags and rules (§10.3).
````

````markdown
### 7.1 Entity Identification

An entity's id (`Entity.id` in `world_state_schema.yaml`, and an
`EntityRef`'s `entity_id`) is written

```
<class>:<namespace>/<local_id>
```

  vendor class, `x-` followed by a lower-case letter or digit and then
  lower-case letters, digits, `_` or `-`.
- `<namespace>` is one or more segments separated by `/`, outermost first.
  With the class, it makes the id unique within the world
  (`meta.world_id`). The taxonomy's `namespace_components` (organisation,
  domain, environment, system, subsystem) is the recommended order: an id
  SHOULD use those that apply, in that order, and MAY add segments of its

control character (percent-encode them, RFC 3986). An id therefore has

grammar; the entity id vectors (§10.3) fix it.

```
````

### 2.14 §8.1–§8.3 *(replace; S2b's §8.4 follows unchanged)*

````markdown
### 8.1 Trust Score Calculation

The **trust score** of a piece of evidence is a number from 0 to 1:

```
score = weight × confidence × decay
```

computed in that order in binary64 arithmetic, where:

| Factor | Value |
|--------|-------|
| Source ranking: `weight` | The evidence's static weight (§8.3) |
| Confidence weight: `confidence` | The confidence the source reports (§4.1.1), from 0 to 1; 1 when it reports none |
| Time decay: `decay` | `max(0.5 ** (age / half_life), min_trust)`, or `0.5 ** (age / half_life)` when the model sets no `min_trust` |

- `half_life` is `decay_model.half_life` of `authority_trust_model.yaml`: a
  duration of whole days, `P<n>D` with `n` at least 1. `age` is the time from
  the evidence's timestamp to the time the score is computed, in the same
  unit. An age below zero (evidence dated after that time) counts as zero.
- Time decay MUST be a true half-life: before the floor, the factor for an
  age of one half-life is exactly `0.5`. (An exponential time constant,
  `exp(-age / half_life)`, gives 0.368 there and does not conform.)
- `decay_model.min_trust` is a floor on the decay factor only: not on the
  static weight and not on the score. Age alone therefore never takes
  evidence's weight to zero; it only removes its advantage over fresher
  evidence. A floor above 0.5 holds the factor at the floor from the age at
  which the curve reaches it.
- A weight, a confidence or a `min_trust` outside 0 to 1, or a half-life of
  another form, makes the model or the evidence invalid, and an
  implementation refuses it. Evidence without a static weight (§8.3) has no
  score: an implementation MUST NOT give it one.

**Field authority** is not a factor of the score: the trust model's
`field_authority.fields` names, for a field, the source types that are
authoritative for it, and §8.2 ranks them first. (`field_authority.examples`
is illustrative and is not read.)

### 8.2 Conflict Resolution

When **candidates** give different values for one field of one entity, a
strategy resolves the conflict. Each candidate has its evidence: a source
type, a trust class or both (§8.3), an age and a confidence. A strategy
either chooses one candidate (`chosen`), keeps all of them (`merged`) or puts
the conflict to a person (`escalated`):

| Strategy | Result |
|----------|--------|
| `highest_score` (default) | The candidate with the highest trust score (§8.1) |
| `prefer_authoritative_sources` | Where some candidates' source types are authorities for the field (`field_authority.fields`), only those compete; of the competing candidates, the one with the highest static weight |
| `prefer_recent` | The candidate with the lowest age |
| `prefer_high_confidence` | The candidate with the highest confidence |
| `merge_with_uncertainty` | `merged`: every candidate with its score, highest score first, candidates of equal score in the order given |
| `escalate_to_human` | `escalated`: no candidate is chosen |

**Ties.** Two values are equal when they differ by at most 10⁻¹². When
several candidates are best by the strategy, the model's
`conflict_resolution_function.tie_breakers` apply to them, in order:
`prefer_authoritative_source` keeps those whose source type is an authority
for the field, if any is; `prefer_high_confidence` those with the highest
confidence; `prefer_recent` those with the lowest age; `escalate_to_human`
stops. If more than one candidate remains, the conflict is `escalated`. A
conflict with one candidate chooses it. A conflict in which a candidate has
no static weight is refused, whatever the strategy: it is not resolved by
leaving the candidate out.

A capability that resolves conflicts names its strategy (`integrate`'s
`conflict_resolution`); absent, the strategy is `highest_score`. The
conflict resolution vectors (§10.3) fix these results.

### 8.3 Trust Classes and Static Weights

`authority_trust_model.yaml` gives each source type a weight
(`source_ranking.weights`) and each sender trust class of §5.17 a default
weight (`trust_classes.weights`); the classes are exactly those of
`agent_identity.trust_class`. The **static weight** of evidence is:

- with a source type only: the source type's weight;
- from an item whose sender's identity has a trust class, with no source
  type: the class weight;
- with both: the lower of the two, so a trusted channel cannot lift an
  untrusted sender;
- with neither, with a source type that has no weight, or with a trust class
  the model does not have: none.

A domain profile applied to the run (§5.21) overrides weights with
`trust_weights`: the key `trust_class:<class>` (e.g. `trust_class:peer_agent`)
replaces the weight of that class, kept apart from a source key of the same
name; any other key replaces the weight of the source type it names, or gives
a weight to a source type the model does not name. A replacement may be
higher or lower than the model's weight; the rule above for evidence with
both a source type and a class still takes the lower of the two. With several
profiles, the lowest weight they give a key applies.
````

### 2.19 §11.6 Ontology Versions *(new)*

````markdown
### 11.6 Ontology Versions

The capability ontology (`schemas/capability_ontology.yaml`) has its own
Semantic Version, `meta.version`:

| Change to the ontology | Version |
|------------------------|---------|
| Remove or rename a capability, a layer or an edge type; move a capability to another layer; change a capability's `risk`, `mutation`, `requires_checkpoint`, `requires_approval` or `mutation_overridable`; add a required input or a required output field; remove an input or an output field, or stop requiring an output field; change a field's type (§11.4); add a constraint to an existing input or to a member it already names, or tighten one it has (a `pattern`, a bound, a narrower `enum`, a type for items it left open); tighten a constraint an existing output field already has; add or remove a `requires`, `precedes` or `conflicts_with` edge | MAJOR |
| Add a capability, an optional input, an optional member of an input or output object, an optional output field or an enum value; constrain the items or members of an existing output field where its contract left them open; remove or relax a constraint, other than its type, on an existing input; add or remove a `soft_requires`, `enables`, `alternative_to` or `specializes` edge | MINOR |
| Change only descriptions, rationales and examples | PATCH |

The constraint rows follow §11.4 and who bears a constraint. One on an input
binds the workflows that bind it, so adding or tightening it is breaking. One
on an output binds producers; where the contract said nothing about an
output's items or members, describing them binds producers only for values
the contract never described, and no implementation refuses an output on it
(an executor checks an output's required fields, §5.19). Tightening what an
output already promised is breaking for producers.

Ontology 2.1.0 widened `transform.output` from `object` to `object|array`, a
type change and so MAJOR by this table; it was published with Standard 1.1.0
as a MINOR version before this rule existed, and §11.4 of Standard 1.1.0
records it as the one breaking change of that release. This rule applies
from ontology 2.2.0.

An ontology MAJOR version is published only with a Standard MAJOR version:
every Standard 1.x uses ontology 2.x. An ontology MINOR version is published

ontology 2.2.0. An ontology PATCH version MAY be published alone. An
implementation of a Standard version uses the ontology version it names, or
a later PATCH of that version.

**Citing.** A document outside a workflow that names capabilities by id — a
domain profile (§5.21), a tool binding record (§5.18.1), an agent or catalog
manifest (§5.15.1, §5.1.1), an interoperability mapping — cites the versions
it was written against as `standard` and `ontology`, each `MAJOR.MINOR` or
`MAJOR.MINOR.PATCH`. Each format says where the two members sit (a domain
profile's are top-level members; the repository's interoperability mappings
keep them under `meta.agent_capability_standard`) and MAY make them optional
(a domain profile's are). A consumer checks those present:

- it refuses a document whose `ontology` has another major than its own
  ontology's, or whose `standard` it does not support, with V109;
- a document whose ontology MINOR is later than its own may name capabilities
  it does not know: each such id is V101 where the document uses it.

A workflow cites only the Standard version it targets (§11.5), which fixes the
ontology's major.
````

docs/domains/README.md." `trust_weights`, `risk_thresholds`,
`minimum_confidence`, `require_grounding`, `domain_sources`, `workflows`,
`compliance` are unchanged. The two blocks below change.

**Mapping principle.** A checkpoint is a restore point before a change of
state (§4.4.1), so each 1.0.0 label maps to the capability that makes the
change it names: changing records, devices or files → `mutate`; running
commands, orders, deployments or purchases → `execute`; transmitting →
`send`; handing work off → `delegate`; writing a result out (a
recommendation, an alert, a transcript, a classification, generated content)
→ `persist`; a label keyed on a risk level → `"*"` at that level (the lower
one when two). Labels that name no change of state (classifying, comparing)
map to nothing. Anchor kinds: the §6.5 kinds the 1.0.0 entries name, plus the
kinds of the profile's own `domain_sources` (`api`→`api`, `sensor`→`sensor`,
`database`→`record`, `human`→`human_note`, `document`→`file`,
`system_log`→`log`), in §6.5 order; entries that are properties of an anchor
or an output (`timestamp`, `confidence_score`, `time_segment`, `bounding_box`,
`query_hash`, …) are not kinds.

```rust
pub enum Level { None, Low, Medium, High }          // threshold values
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum CheckpointRule { Always, HighRisk, MediumRisk, Never }

#[derive(Debug, Clone)]
pub struct Profile {
    pub label: String,                               // domain, or "#<i>"
    auto_approve: Option<Level>,
    require_review: Option<Level>,
    require_human: Option<Level>,
    block_autonomous: BTreeSet<String>,
    checkpoint: BTreeMap<String, CheckpointRule>,    // capability id or "*"

    pub required_anchor_types: Option<Vec<String>>,
    pub minimum_confidence: Option<f64>,
    pub allowed_destinations: Option<Vec<String>>,
    pub trust_weights: BTreeMap<String, f64>,
}

#[derive(Debug, Clone, Default)]
pub struct Policy { profiles: Vec<Profile>, raw: Vec<Value> }

#[derive(Debug, Clone, Copy, Default, PartialEq, Eq)]
pub struct Raise { pub requires_checkpoint: bool, pub requires_approval: bool, pub person: bool }
```

**`src/wasm.rs`** (new, `#[cfg(feature = "wasm")]`)

```rust
//! A JSON-in, JSON-out interface for WebAssembly hosts (STANDARD v1.2 has no
//! text on it: this is the reference implementation's packaging). Three C-ABI
//! exports; no wasm-bindgen. Every buffer that crosses the boundary is a
//! `Box<[u8]>` of exactly its length: allocated with
//! `vec![0u8; len].into_boxed_slice()` and released with `Box::from_raw` on
//! a slice pointer of that length, so allocation and release use one layout.

use std::ptr;

/// A zeroed buffer of `len` bytes for the caller to fill.
#[unsafe(no_mangle)]
pub extern "C" fn acs_alloc(len: usize) -> *mut u8 {
    Box::into_raw(vec![0u8; len].into_boxed_slice()).cast::<u8>()
}

/// Release a buffer from `acs_alloc` or `acs_call`, with the length it has.
///
/// # Safety
/// `ptr` and `len` are exactly a pointer and length that `acs_alloc(len)`
/// returned, or a result of `acs_call` with `len` = 4 + its stated length,
/// not released before.
#[unsafe(no_mangle)]
pub unsafe extern "C" fn acs_free(ptr: *mut u8, len: usize) {
    // SAFETY: by the contract above, (ptr, len) is a Box<[u8]> that
    // Box::into_raw produced and nothing has freed: the same layout.
    drop(unsafe { Box::from_raw(ptr::slice_from_raw_parts_mut(ptr, len)) });
}

/// Answer the JSON request in `ptr[..len]`. The result is a new buffer: a
/// 4-byte little-endian length `n`, then `n` bytes of JSON. Release it with
/// `acs_free(result, 4 + n)`; release the request buffer as usual.
///
/// # Safety
/// `ptr[..len]` is readable and initialised (a buffer from `acs_alloc(len)`).
#[unsafe(no_mangle)]
pub unsafe extern "C" fn acs_call(ptr: *const u8, len: usize) -> *mut u8 {
    // SAFETY: the caller guarantees ptr[..len] is a live, initialised buffer.
    let request = unsafe { std::slice::from_raw_parts(ptr, len) };
    let body = dispatch(request).into_bytes();
    let body = if u32::try_from(body.len()).is_ok() { body } else { too_large() };
    let mut out = Vec::with_capacity(4 + body.len());
    out.extend_from_slice(&(body.len() as u32).to_le_bytes());
    out.extend_from_slice(&body);
    Box::into_raw(out.into_boxed_slice()).cast::<u8>()   // into_boxed_slice shrinks: len == capacity
}

pub fn dispatch(request: &[u8]) -> String;   // safe, unit-tested natively
fn too_large() -> Vec<u8>;                   // {"error":{"kind":"too_large",…}}
```

```yaml
name: Publish npm package

# Publishes packages/acs-core to npm from a tag acs-core-vX.Y.Z on main.
# - push the tag (on a commit of main); or
# - run it by hand from main with the tag (workflow_dispatch). A hand run
#   never publishes the branch it was started from: it checks out the tag.
# Either way the tag's commit must be on main, and package.json's version
# must equal the tag's. Publishing needs vars.NPM_PUBLISH_ENABLED == 'true'
# and secrets.NPM_TOKEN; otherwise the job ends with a dry run.
on:
  push:
    tags: ["acs-core-v*"]
  workflow_dispatch:
    inputs:
      tag:
        description: "Existing tag to publish (acs-core-vX.Y.Z), on main"
        required: true
        type: string

permissions:
  contents: read

env:
  RUST_TOOLCHAIN: "1.99.1"   # equal to ci.yml's (tests/test_ci_workflows.py)

jobs:
  publish:
    name: Publish @synaptiai/acs-core
    runs-on: ubuntu-latest
    # A hand-started publish runs from main, never another branch (release.yml's guard).
    if: github.event_name == 'push' || github.ref == 'refs/heads/main'
    permissions:
      contents: read
      id-token: write
    env:
      TAG: ${{ github.event_name == 'workflow_dispatch' && inputs.tag || github.ref_name }}
    steps:
      - uses: actions/checkout@v7
        with:
          ref: refs/tags/${{ env.TAG }}
          fetch-depth: 0
      - name: The tag is on main
        run: |
          case "$TAG" in acs-core-v*) ;; *) echo "not an acs-core tag: $TAG" >&2; exit 1 ;; esac
          git fetch --no-tags origin main
          git merge-base --is-ancestor "refs/tags/$TAG^{commit}" origin/main \
            || { echo "$TAG is not on main" >&2; exit 1; }
      - name: The version matches the tag
        working-directory: packages/acs-core
        run: test "acs-core-v$(node -p "require('./package.json').version")" = "$TAG"
      - name: Install Rust with the wasm32 target
        run: |
          rustup toolchain install "$RUST_TOOLCHAIN" --profile minimal --target wasm32-unknown-unknown
          echo "RUSTUP_TOOLCHAIN=$RUST_TOOLCHAIN" >> "$GITHUB_ENV"
      - uses: actions/setup-node@v7
        with: { node-version-file: site/.nvmrc, registry-url: "https://registry.npmjs.org" }
      - name: Build and test the tagged commit
        working-directory: packages/acs-core
        run: |
          npm ci --ignore-scripts
          npm run build:wasm
          npm run build
          npm test
      - name: Publish
        if: vars.NPM_PUBLISH_ENABLED == 'true'
        working-directory: packages/acs-core
        run: npm publish --provenance --access public
        env: { NODE_AUTH_TOKEN: "${{ secrets.NPM_TOKEN }}" }
      - name: Dry run
        if: vars.NPM_PUBLISH_ENABLED != 'true'
        working-directory: packages/acs-core
        run: npm publish --dry-run
```

## 9. RFC text: `spec/RFC-0010-profiles-trust-versioning-and-dialect.md`

````markdown
# RFC-0010: Domain Profiles, Trust, Versioning and Schema Dialect
**Status:** Accepted
**Target:** Standard v1.2.0
**Date:** 2026-11-15

## Summary

This RFC records the decisions of Standard 1.2.0 on domain profiles, the
authority trust model, versioning, the schema dialect of capability contracts
and entity ids, and the packaging decisions of the reference implementation
that go with them. It answers findings ACS-05, ACS-25, ACS-28, ACS-42,
ACS-56, ACS-59 and ACS-64 of the
[Standard Agents mapping](../docs/research/analysis/standard_agents_mapping/findings_agent_capability_standard.yaml).
It is Accepted by the maintainer's instruction that every remaining finding be
implemented in 1.2.0; `spec/STANDARD-v1.2.0.md` carries the text.

## Motivation

Standard 1.1.0 mentioned domain profiles twice and said neither how a run
selects one nor what its settings change; no shipped component read
`schemas/profiles/profile_schema.yaml`'s members, and the compliance documents
had called `block_autonomous` enforced. `require_human` admitted `critical`,
a level the Standard does not define, `checkpoint_policy` keys were free
labels, and none of the shipped profiles' 29 `required_anchor_types` was an
anchor kind.

§4.1 called capability contracts "JSON Schema" while the ontology writes
`type: any` and `a|b` unions, which a JSON Schema importer refuses. §7.1 and
`schemas/entity_taxonomy.yaml` gave two incompatible entity id forms. §8
required a half-life and named the factors of a trust score but left their
composition, a negative age, a floor above 0.5, unknown weights, field
authority and the conflict strategies without arithmetic; the only decay code
was a benchmark's private function. Four version lines existed, and §11 did
not say how the ontology is versioned or what a classification made elsewhere
cites. A catalog's version header is a comment, so it never reached the
executor, which takes parsed catalogs: a rule for 1.2 targets would apply in
the validator and not in a run of the same file. The skills mixed frontmatter keys of three owners, two of them under
names other than their directories. A TypeScript host had no published
package and no way to run the reference core.

## Goals

- Give domain profiles one defined effect wherever they are applied, which
  tightens flags, checks, evidence, confidence and destinations (trust
  weights replace), with diagnostics and vectors, and refuse malformed rules.
- Define the schema dialect of contracts and its Draft 2020-12 rendering.
- Choose one entity id form.
- State the trust arithmetic completely and make its vectors normative.
- Say how the ontology is versioned, how documents cite it, and what a
  Standard version consists of.
- Make the executor apply the rules of the version a catalog declares by
  its header, as the validator does.
- Record which skill frontmatter keys belong to whom.
- Publish the host-neutral TypeScript pieces and a JSON interface to the core.

## Non-goals

- Selecting a profile from a workflow: a workflow's `profile` field stays
  descriptive.
- Profiles that loosen the ontology's flags.
- New capabilities, or changes to capability flags.
- §7.2 and §7.3 (alias scoring, merge and split): unchanged and still not
  implemented.
- A Rust crate on crates.io, or bindings for languages other than TypeScript.
- Changing the repository's catalogs to a 1.2 header.

## Key decisions

### 1) Profiles are applied by hosts, layers and validators, and tighten

A host gives profiles to the executor when it starts a run (§5.21.1); they
cover nested runs and are saved with the run. A safety layer applies the
profiles its configuration names; a validator may be given them. Several
profiles combine by taking the strictest. For flags, checks, evidence,
confidence and destinations a profile only tightens; its `trust_weights`
replace the trust model's weights, higher or lower, as §8.3 always allowed
(bounded by §8.3's lower-of rule; the lowest per key across profiles).
Thresholds are sets of risk levels (`none` covers none); `auto_approve`,
`require_review`, `require_human`, `block_autonomous` and
`checkpoint_policy` raise effective flags, except that a `checkpoint` step
is never given `requires_checkpoint` (it would need a checkpoint before
itself, and `"*": always` would make every workflow invalid). A person is
required for the step itself: the request and the decision are those of an
always-ask item, so no standing mandate covers the step and an unattended
run does not ask, but the requirement is not a mark and does not pass to
the data, the steps that read it or nested runs; its records carry
`person_required`. `evidence_policy` becomes a grounding policy and a
minimum confidence (F504, `below_minimum_confidence`, and
`invalid_confidence` for a `confidence` that is not a number from 0 to 1);
`allowed_destinations` a destination policy; `trust_weights` the overrides
of §8.3. Keys are capability ids or `*`, anchor kinds, trust classes.
Loading uses S303 (malformed members, any member of the closed
`risk_thresholds` and `evidence_policy` mappings this version does not
define, the key `checkpoint`), S304, V101 (any unknown capability id,
`checkpoint_policy` keys included), V109, W602, W603 and W604 (unknown
top-level members only); no misspelled rule is ignored. `critical` is
deprecated and read as `none`. The shipped profiles are migrated to 2.0.0.
The executor, the validator (`--profile`), the Python adapter and runner
implement it, and TypeScript reaches the same implementation through the
WebAssembly core; `tests/conformance/profiles/load.json` and
`tests/conformance/profiles/effective.json` are normative.

### 2) The schema dialect is defined, with a normative rendering

§4.1.2 lists the Draft 2020-12 keywords contracts use and defines `type:
any`, `type: "a|b"`, `$ref` to a repository path with sibling keywords merged
over the target, `nullable`, and `x-` annotations; `x-acs-` is reserved. A
`$ref` that names nothing, a cycle and an over-deep chain are outside the
dialect, and an implementation refuses an ontology whose contract holds one
when it loads it. The rendering rules are normative and exact on values;
§5.4 reads a rendered `"null"` but not `nullable`, a divergence the text
states and a test pins. `schemas/generated/capability_contracts.schema.json`
is the generated rendering, keeping `x-acs-type` for `any`. A dialect
metaschema in `schemas/capability_ontology.schema.json` checks the ontology.

### 3) Entity ids are `<class>:<namespace>/<local_id>`

§7.1 takes the taxonomy's form, states its grammar (the namespace outermost
first, the taxonomy's `namespace_components` the recommended order) and
gives the examples of both files; `schemas/entity_taxonomy.yaml` 1.1.0 adds
the pattern;
`grounded_agency/entities.py` parses ids; `tests/conformance/entities/ids.json`
is normative.

### 4) The trust arithmetic is complete

`score = weight × confidence × decay`; confidence 1 when none is reported; an
age below zero counts as zero; a floor above 0.5 applies; evidence without a
static weight has no score; field authority ranks sources in §8.2 and is not
a factor. §8.2 defines six strategies (the default, `highest_score`, is new)
and tie-breaking by the model's `tie_breakers`; the authorities are the
trust model's new `field_authority.fields` (the 1.1 `examples` stay,
illustrative). The trust vectors are normative, with
`tests/conformance/trust/resolve.json` added; `grounded_agency/trust.py` is
the reference, and the benchmark resolves its conflicts with it, with
unchanged results.

### 5) The ontology's version and what documents cite

§11.6: the ontology's own SemVer with a change table, which also classifies
constraint changes (an input constraint added or tightened is MAJOR; item or
member constraints on an output field that left them open are MINOR) and
records that 2.1.0's widening of `transform.output` predates the rule.
Every 2.2.0 change is MINOR or PATCH under it. An ontology MAJOR only with a
Standard MAJOR, a MINOR with the Standard version that names it, a PATCH
alone. A document outside a workflow that names capabilities cites
`standard` and `ontology` where its format puts them; another ontology major
or an unsupported standard is V109, checked by the profile loader and the
OASF adapter through one core function. §11.7 lists the artifacts of 1.2.0
with their versions. §11.5 adds 1.2, generalises W616 to any feature newer
than a workflow's target, and makes the catalog's header an explicit value
of the start operation (a version or an explicit none), so the executor and
the validator apply the same target's rules to the same catalog.

### 5a) The header reaches the executor

A comment header is gone once a catalog is parsed, and the executor takes
parsed catalogs. In the first draft the header was an optional start
option defaulting to none; a host that left it out ran a catalog targeting
1.2 by its header under 1.1 rules, so S2a's approver `sender_check` and
`accept_trust_classes` (1.2-target fields) were ignored and the identity
requirement failed open. The start operation now takes the header as a
required value; a host that loaded the catalog from a file passes the
file's header version. The Rust `StartOptions` has no default, the host
protocol schema, the fixture format, the WebAssembly `run.start` and
TypeScript's `StartArgs` require the member, `_core.Run.start` requires the
keyword, and `WorkflowRunner` carries each file's header into its
workflows' `spec_version`. A runtime fixture pins the 1.2-header case.

### 6) Skill frontmatter follows the Agent Skills format plus Claude Code's keys

Frontmatter `name` equals the directory; `layer` is removed; ACS keeps any
data of its own under `metadata` keys `acs-*`; `skills/README.md` lists each
key's owner; a test enforces it. The Agent Skills reference validator refuses
the Claude Code keys, which the plugin's skills need. The two renamed skills
are user-invocable, so their slash commands change; the plugin release that
carries the change is a MAJOR version, 3.0.0.

### 7) A TypeScript package and a WebAssembly JSON interface

`packages/acs-core/package.json` declares `@synaptiai/acs-core`: the ontology
table, effective flags, canonical JSON and the approval digest in plain
TypeScript, and the reference validator and executor, domain profiles
included, through a WebAssembly module built from the core's `wasm` feature
(three C-ABI exports over buffers of one layout, a length-prefixed result,
JSON requests, no new dependency). There is no second, TypeScript
implementation of the profile loader. CI replays the validator, runtime and
expression fixtures through it; a job publishes it from a tag on `main`
(a hand run from `main` builds the tag, never the branch) when the
repository enables publishing.

## Backward compatibility

Profiles are opt-in: nothing changes for a run, a call or a validation
unless a profile is applied, and an applied profile only tightens flags,
checks, evidence, confidence and destinations (its trust weights replace, as
in 1.1's §8.3). No 1.1 component applied a profile, so refusing malformed
or misspelled profile rules changes no behaviour. The schema dialect, the
entity id form and the trust arithmetic clarify text that was open or
contradictory; nothing checked the entity id, and the reference trust
function changes only for a negative age. W616 is a warning and fires only
for a workflow that declares 1.0 or 1.1 and uses a 1.2 feature; rules for
1.2 targets apply only to workflows that declare 1.2. The canonical schema
changes are additive (§11.4), `ActionRecord.person_required` and
`field_authority.fields` included. The repository's catalogs keep their 1.1
header and validate as before.

**Changed.** The start operation takes the catalog's header version as a
required value (a 1.1 host passes none for a catalog without a header, and
a 1.1 workflow then runs exactly as before); direct callers of the private
`_core.Run.start` must pass the `header` keyword. An ontology whose contract
holds an unresolvable `$ref`, kept silently before, is refused at load.

**Breaking (plugin).** Two user-invocable skills are renamed to their
directory names (`/gap-analysis-workflow` → `/capability-gap-analysis`,
`/digital-twin-sync-workflow` → `/digital-twin-sync-loop`), so the plugin
release is a MAJOR version, 3.0.0. No workflow, ontology or schema is
affected.

## Alternatives considered

- *Profiles informative only*: leaves the compliance controls unenforced.
- *The workflow selects its profile*: a profile is deployment policy, and a
  workflow can declare its own flags.
- *Profiles that may loosen*: contradicts §3.3.
- *Unknown `checkpoint_policy` keys and nested members as warnings*: a
  misspelled rule would be dropped silently; errors instead.
- *A person requirement that marks data, as an always-ask item does*: it
  would spread to steps no profile covers and misstate the records.
- *An optional header start option*: fails open for 1.2-target rules.
- *A pure-TypeScript profile loader beside the core's*: a third
  implementation with no consumer.
- *Removing `critical`*: deprecated instead, so existing profiles load.
- *Rewriting the ontology in strict JSON Schema*: churn for every consumer of
  the YAML; the dialect is defined and rendered instead.
- *§7.1's entity form*: changes the canonical schema and its examples; the
  taxonomy's is machine-readable and hierarchical.
- *Refusing a negative age; forbidding a floor above 0.5*: brittle under
  clock skew; the floor's meaning is unambiguous.
- *Versioning the ontology in lockstep with the Standard*: description fixes
  should not need a Standard release.
- *wasm-bindgen*: two version-locked dependencies and generated glue for what
  a JSON interface over three exports provides.

## Open questions

1. Should Standard 2.0 drop the deprecated profile threshold `critical`, and
   make an unknown top-level profile member an error rather than W604 (this

   members of `risk_thresholds` and `evidence_policy`)?
2. Should a domain profile be able to carry its own grounding `attested`
   flag (§5.20), which this version leaves at its default?
3. Should the repository's reference catalogs move to a 1.2 header in the
   next release, together with the migrations that the 1.2-only warnings of
   other workstreams would require?
4. The skills write `allowed-tools` comma-separated and name `Git` and `Web`,

   corrected, which would change what the skills may run?
5. Should the TypeScript package also carry the trust arithmetic and entity
   ids, which today only the Python package implements?
6. If a TypeScript safety layer comes to apply profiles without
   WebAssembly, should the package then carry a plain-TypeScript profile
   loader, held to the same vectors?
7. Should a later version define recursive types in the schema dialect
````

What makes this one design: an **agent manifest** (ACS-29) says what an agent
may do; a workflow's **`agents`** (ACS-46) says which agents it may delegate
to, and is the author's explicit opt-in to manifest semantics; with both, the
validator and executor know a delegate step's **target maxima** (ACS-04) and
its **task** declaration (ACS-54), and without the manifests the executor
does not delegate. `continues` (ACS-47) and model families (ACS-17) complete
the delegation inputs. Independently, catalogs gain a
manifest and qualified ids (ACS-49), steps a domain grammar (ACS-24),
diagnostics a defined location (ACS-09), `inquire` typed answers (ACS-50),
and §4.3 a stated scope (ACS-16).

## 1. Per finding: decision, rationale, how it fixes the finding

### ACS-29 — an agent manifest (decided first: ACS-04 and ACS-54 build on it)

**Decision.** A new supporting schema, `schemas/agent_manifest_schema.yaml`
(`#/agent_manifest`, version 1.0.0), listed in §6.1 beside
`review_verdict_schema.yaml` and `agent_identity_schema.yaml`. A manifest has:

- `agent` (required): the name a `delegate` step's `agent` and a workflow's
  `agents` use. It is a target name, not a principal (§5.15 1.1 already says
  so of `agent`), compared by exact equality.
- `standard` and `ontology` (required): the Standard and ontology versions
  the manifest was written against, `MAJOR.MINOR[.PATCH]`, as S6's §11.6
  citation rule asks of every document outside a workflow that names
  capability ids. Required, not optional, because the format is new (no
  manifest predates them) and the maxima are read from the ontology the
  manifest cites.
- `capabilities` (required): every ontology capability the agent may
  exercise, **directly or through agents it delegates to and workflows it
  invokes**, so no transitive computation is needed.
- `task` (optional): the task inputs it accepts, in the form of workflow
  `inputs` (§5.1) — ACS-54.
- `version`, `description` (optional, for people); `x-` keys are vendor data;
  any other key makes the manifest invalid.

Its **maxima** are derived, never stated: the highest ontology `risk` and the
OR of `mutation`, `requires_checkpoint`, `requires_approval` over its
capabilities (low and all false for none). Its **read-only maxima** are the
same over the capabilities whose ontology `mutation` is false (so a
read-only `execute` still needs approval). The **join** of several maxima is
the highest risk and the OR of the booleans. A manifest that lists a
capability the consumer's ontology does not define has **no** maxima (the
missing capability could need anything).

Manifests are *context*, like the ontology: they describe agents a host
provides, so the caller gives them to the validator and the executor beside
the catalogs (Rust `Agents`, Python `agents=`, CLI `--agents`). A set with two
manifests for one `agent`, a manifest that does not conform to its schema,
or one whose `ontology` has another major than the consumer's ontology or
whose `standard` the consumer does not support (S6's V109 condition) is
refused when loaded (as §4.4 refuses an ontology that misuses
`mutation_overridable`), not reported as a diagnostic: it is not part of a
catalog. A capability id the consumer's ontology lacks does not refuse the
manifest: following S6's §11.6 ("an id its ontology lacks is V101 where it is
used"), it is V101 at each `delegate` step whose target maxima draw on that
manifest, and the executor, which has no maxima for it, does not delegate
there (ACS-04). One behaviour for every cited document, and a manifest
written against a later ontology minor still loads.

**Options considered.** (a) A sixth canonical schema in §6.1 — rejected: §6.1
lists what every implementation needs, and an implementation that never
delegates needs no manifest; `agent_identity_schema.yaml` set the precedent of
a supporting schema. (b) Stored maxima in the manifest — rejected: two sources
of truth that can disagree; the ontology already says what each capability
needs. (c) Manifests referenced from the workflow (`agents: [{agent, manifest:
path}]`) — rejected: the manifest describes the host's agent, which the
workflow author does not own; the run must use the host's. (d) An optional
`flags` member to raise an agent's flags — rejected as unneeded: a workflow
step can raise its own flags, and the derived maxima already cover every
capability listed.

**How it fixes the finding.** There is now a normative descriptor of the
capabilities a delegate agent may exercise and its highest risk; the
validator and executor take it as input (ACS-04, ACS-54); the SDK's
`AgentDescriptor` is built from it (`AgentDescriptor.from_manifest`,
`.manifest()`, `.maxima()`); the Standard Agents binding derives an agent's
manifest from the `acs` annotations of the tools its prompts offer
(`deriveAgentManifest`), so there is one design behind any interop
description of an agent definition and no separate annotation. Because the
manifest is the only input that raises a delegate step's flags, a manifest
derived from incomplete information would fail open: `deriveAgentManifest`
refuses to derive one when any offered tool other than a control-only tool
(S1's `control: true`) has no `acs` annotation, or when the manifest of a
subagent the agent can delegate to is not given.

### ACS-46 — a workflow declares its delegable agents

**Decision.** A standard workflow field `agents`: a non-empty list of
distinct non-empty strings (S303 otherwise), allowed only in a workflow that
**targets 1.2 or later** (§11.5): in a workflow whose target is 1.0 or 1.1,
or that declares no version, `agents` is S303 at `agents` ("declare
spec_version \"1.2\" to use it"). A workflow that declares it:

- may delegate only to listed agents: a literal `agent` not listed is V107
  (UNRESOLVED_TARGET, its existing meaning: a name that does not resolve); a
  computed `agent` that resolves to an unlisted name is refused by the
  executor before delegating (R402, an executor refusal, not retried — as for
  `invoke`'s own refusals, §5.2 `retry`);
- opts into manifest semantics (ACS-04, ACS-54).

A host that composes agents statically creates one relationship per listed
agent and SHOULD check, before the run, that it provides each; a listed agent
it does not provide is V107 at `agents[i]` (the Standard Agents binding's
`declaredAgents` and `lintDelegationTargets`).

In a workflow that **targets 1.2** and declares no `agents`, a `delegate`
step whose `agent` is not a literal is W622 (UNDECLARED_DELEGATE): a host with
static composition cannot check it before the run.

The field is a base field of 1.2, not an extension field, and it is the
author's explicit, in-document opt-in to "a delegation takes its target's
flags". Must-understand protection comes from requiring the 1.2 declaration:
a workflow that uses `agents` declares 1.2, so a 1.1 consumer refuses it
(V109) instead of ignoring the field (W604) and running its delegates without
the raised checkpoint and approval. `agents` is therefore not on S6's W616
list (it cannot appear in a workflow that targets 1.1 without being S303).
The executor sees the same declaration: it validates with the catalog's
header (S6's `StartOptions.header`), and a run of a workflow with `agents`
that declares 1.2 only in the header, started without the header, is refused
at start (S303), so the omission fails closed.

**Options considered.** (a) Document an `x-agents` vendor field only —
rejected: the maintainer asked for the standard field now, and a vendor
field gives no validator rule. (b) A new extension `agents@1` — rejected: it
splits delegation semantics across two declarations, and the 1.2
declaration, required for the field, already makes an older consumer refuse
the workflow. (c) A field allowed under any target, with W616 for a 1.1
target (the first version of this design) — rejected: a 1.1 consumer would
silently drop the protection the author opted into, which is what §11.3's
must-understand rule ("refuses the workflow instead of silently ignoring")
exists to prevent. (d) W622 for every workflow version — rejected: its remedy
(`agents`) is a 1.2 feature.

**How it fixes the finding.** The delegable agents are declared by a
documented field; a static-composition host derives relationships from it
and reports a listed agent it does not provide; the validator warns about an
unconstrained computed target and rejects an unlisted literal one; the
executor refuses an unlisted computed one; and an older consumer refuses the
workflow rather than ignore the field.

### ACS-04 — a `delegate` step's flags follow its target

**Decision.** In a workflow that declares `agents`, a `delegate` step has
**target maxima**:

- literal `agent`: that agent's manifest maxima (also for an unlisted one,
  which is V107 besides: the step still names it);
- computed `agent`: the join of the maxima of every listed agent (any may be
  chosen); known only when every listed agent has a manifest;
- a step that binds literal `read_only: true`: the read-only maxima
  (respectively their join) instead.

The target maxima are **unknown** when a manifest concerned is not given, or
lists a capability the ontology does not define (V101 at the step, ACS-29).

The step's **ontology baseline** of §5.2.1 becomes the stricter of the
`delegate` node's values and the target maxima. Everything that acts on
effective flags then follows unchanged: F501 for a raised
`requires_checkpoint` with no checkpoint before the step, approval for a raised
`requires_approval`, W602 for a declaration weaker than the raised baseline,
W606, W608, deferral.

**Fail-closed.** In a workflow that declares `agents`, an executor MUST NOT
delegate for a `delegate` step whose target maxima are unknown: it fails the
step (R402, an executor refusal before asking the host, not retried). The
step's flags were computed without the target, so delegating would fall back
to 1.1 safety on a workflow whose author opted out of it. The validator,
which may run without the host's manifests (CI), reports W621 for the step
instead; a host gives its manifests to both.

**`approval` on such a step.** In a workflow that declares `agents`, an
`approval` block on a `delegate` step is never S303: it applies whenever the
target maxima raise `requires_approval`, and whether they do depends on
manifests the author does not control. So the rule that allows `approval`
(§5.14: only where the effective `requires_approval` is true) is evaluated
without manifests and treats such a step as one that may require approval;
the same workflow is valid with and without them.

**`read_only`.** Read-only maxima rest on the host honouring `read_only`, so:

- a host that receives a delegation with `read_only: true` and cannot enforce
  it MUST refuse the delegation (`accepted` not `true`) instead of running
  it. This states what 1.1 already demands ("must not change anything") as
  a host obligation, for every workflow;
- in a workflow that **targets 1.2 or later**, an accepted delegation whose
  resolved `read_only` is `true` fails unless its host attests
  `effective.read_only: true` (R402). The executor raises it as a step error,
  never retried: the delegate already ran under read-only maxima, and a retry
  would delegate again to the host that ignored `read_only`. The check is not
  limited to workflows with `agents`, so the remedy W621 offers (bind
  `read_only: true`) is enforced wherever W621 applies.

In a workflow that **targets 1.2**, a `delegate` step whose target maxima are
unknown is W621 (UNBOUNDED_DELEGATION): when the workflow declares `agents`,
always (the executor will not delegate without the manifests); when it does
not, unless the step binds a literal `read_only: true` or its effective
`requires_approval` is true. The reference catalog's
`multi_agent_orchestration` (which raises `requires_approval`) would not warn.

**Options considered.** (a) Raise flags whenever a manifest is available,
for every workflow — rejected: a host supplying manifests would change what a
1.1 workflow does (new F501/F502), which the task rules forbid; the audit
rates mandatory derivation MAJOR. (b) Raise flags in every workflow that
targets 1.2, without a field — rejected: the target maxima need manifests,
and a 1.2 workflow written without them (every one today) would then be
refused by every executor that has none; an explicit field lets an author
opt in when the host can supply manifests. The version is still what makes
the field safe (ACS-46: `agents` requires 1.2), and since S6's
`StartOptions.header` the executor sees the header, so the `read_only`
attestation and both warnings key on the 1.2 target. (c) Keep the `delegate`
node's flags when manifests are missing at run time (the first version of
this design) — rejected: a host without manifests would delegate to a
mutating agent with no checkpoint or approval, silently undoing the opt-in.
(d) Raise the unattested-`read_only` failure as a host-response error that
`retry` may repeat — rejected: each retry hands another unchecked delegation
to a host that ignored `read_only`. (e) Warn for every version — rejected:
the delegate steps of 13 conformance fixtures and any 1.1 catalog would warn,
and the finding asks for opt-in.

**How it fixes the finding.** A delegation to an agent that can change the
world carries that agent's checkpoint and approval requirements, statically
(F501, approval checks) and at run time (the executor's effective flags);
without the manifests the executor does not delegate; `read_only` relaxes
them only when the host enforces it and attests it, and a violation is not
retried; a bare `delegate` step in a 1.2 workflow that may act on the world
unchecked is reported.

### ACS-54 — the task a target accepts

**Decision.** A manifest's `task` declares task inputs in the form of
workflow `inputs` (each a mapping with optional `required`, `type`,
`description`, …). In a workflow that declares `agents`:

- for a literal `agent` whose manifest declares `task`, a literal `task`
  mapping with a name the manifest does not declare is S303 (no `x-`
  exemption: these are the agent's inputs, not the step's fields), and one
  that misses a required input is S304 — the rules §5.12 states for
  `invoke`;
- the executor checks the resolved task against the resolved agent's
  declaration before delegating (R402, an executor refusal), so a reference,
  or a computed agent, is checked then.

The ontology's `delegate.task` stays `type: object`.

**Options considered.** (a) Per-target `$ref` in the ontology — rejected: the
ontology describes capabilities, not agents. (b) Check only at run time —
rejected: `invoke` already checks literal inputs statically, and the finding
asks for parity. (c) Type-check task values against `type` — rejected for
parity with `invoke`, whose inputs are checked by name and `required` only.

**How it fixes the finding.** A mistyped literal task is found at validation
(S303/S304), and any other at run time before the host is asked (R402),
exactly as for `invoke`; the Standard Agents binding maps a refused task to
SA's `subagent_arguments_required` (`checkTask`).

### ACS-47 — continuing an earlier delegation

**Decision.** A new optional input on `delegate` in ontology 2.2.0,
`continues`: the `task_id` of an earlier delegation whose delegate the host
continues instead of starting a new one (typically `${review_a.task_id}`, or
a workflow input). Rules:

- binding `continues` and a literal `fresh_context: true` is S303;
- a delegation whose resolved `continues` is a string fails (R402) if its
  host attests `effective.fresh_context: true`;
- `continues` resolving to null delegates anew, as if it were not bound
  (create-or-continue, the Standard Agents semantics);
- **every delegation call returns its own `task_id`**, a continuation
  included: never the `task_id` it continues (R402 if it does). `continues`
  may name the `task_id` of any earlier call in the chain (the first
  delegation or a continuation of it); the host maps it to the delegate it
  continues. So §5.13's correlation on `task_id` matches only this call's
  result, never an earlier call's, and `replaces` names one call
  unambiguously;
- a retry or loop of the step passes the same `continues` and names the
  continuation call it replaces (`replaces`, §5.13); the host cancels that
  call's work and leaves the delegate itself alone, so the new call can
  continue it;
- a host that cannot continue it refuses (`accepted` not `true`, or an
  `Error`).

A reviewer that binds `continues` never satisfies `require_fresh_context`
(§5.16): that requirement already demands a literal `fresh_context: true` of
every reviewer (F504 otherwise), and `continues` with a literal
`fresh_context: true` is S303. No quorum rule is added (the first version of
this design added an F504 that could never fire alone), and the executor's
count needs no change: a continued delegation attested as fresh fails before
the quorum counts it.

`continues` is **not** governed by `delegation@1`. The finding proposed that,
but a 1.1 workflow that binds `continues` today validates (W604) and would
then become V106 — invalid — which the task rules forbid; and a 1.1 consumer
that implements `delegation@1` does not know `continues` anyway, so the
extension adds no must-understand protection. Unlike `agents`, ignoring it
drops no safety rule: a 1.1 consumer passes it to the host (W604), which is
where it takes effect, and loses only the executor's consistency checks;
S6's W616 reports it in a workflow that targets an earlier version (§11.5).

**How it fixes the finding.** The validator sees a continuation (an input
in the contract), rejects the contradiction with `fresh_context: true`, and
so excludes a continuing reviewer from a fresh-context quorum statically; the
executor rejects a host that claims a fresh context, and a continuation's
result is matched by its own `task_id`.

### ACS-17 — model families

**Decision.**
1. State exact (code-point) equality wherever a family appears: the
   `model_family` input, `effective.model_family`, an identity's
   `model_family`, `require_model_families`. This is what the validator
   (`core/src/validate/quorum.rs`) and executor (`core/src/exec/quorum.rs`)
   already do.
2. Define a family: the name of a provider's model line, without version,
   size, date or variant, grammar `[a-z][a-z0-9_-]*` (admits every value in
   the repository, including `family_a`). A literal binding or
   `require_model_families` entry outside the grammar is W620.
3. **Derive it by one rule** (normative for a host that attests a family),
   from the identifier of the model the delegate ran on:
   1. keep the part after the identifier's last `/` (an organisation or
      path prefix: `meta-llama/Llama-3.1-8B-Instruct`, `models/gemini-2.5-pro`);
   2. of that, keep the part after the last `.` or `:` that comes before its
      first digit or `-` (a platform's prefix: `us.anthropic.`, `meta.`,
      `ft:`);
   3. the family is the leading run of ASCII letters of the rest, lowercased.
      An identifier with no leading letter gives no family (the host attests
      none).

   So `claude-opus-4-1` → `claude`, `us.anthropic.claude-opus-4-1-20250805-v1:0`
   → `claude`, `gpt-4o` → `gpt`, `o3-mini` → `o`, `chatgpt-4o-latest` →
   `chatgpt`, `gemini-2.5-pro` → `gemini`, `gemma-3-27b-it` → `gemma`,
   `meta.llama3-1-70b-instruct-v1:0` → `llama`, `Qwen/Qwen2.5-72B-Instruct`
   → `qwen`. The rule needs no list of lines, so two hosts that know the same
   model id attest the same family, also for a line nobody listed. The
   vectors `tests/conformance/families/derive.json` pin it, and the reference
   helpers (`grounded_agency.coordination.families.model_family`, the
   binding's `modelFamily`) implement it. The guide's table
   (`docs/guides/ORCHESTRATION_EXTENSIONS.md`) lists what it gives for every
   line the reference bindings and examples name, including the OpenAI
   o-series (`o`, a line of its own, not `gpt`), Gemini and Gemma.

### ACS-24 — the step field `domain`

**Decision.**
1. **Grammar.** A domain id is one or more segments joined by `.`, each
   `[a-z0-9][a-z0-9_]*` (`text`, `image.object`, `image.3d`,
   `multimodal.text_to_image`). Underscore, not hyphen, so a domain has one
   spelling (`plan_invalidation`, not also `plan-invalidation`); digits may
   lead a segment (the OASF hint `image.3d`, the guide's `3d.mesh`). Every
   shipped step value but one and every OASF `domain_hint` conform. A value
   outside it is W620 (all versions; warning-first); it is still passed to
   the host unchanged.
2. **Matching (host rule).** Exact; else the longest proper prefix ending at
   a `.`; else the implementation for no domain; else R402 with reason
   `unsupported_domain` (S2b's `Error` reason member). A step without
   `domain` takes the domain-less implementation, else R402. Exact
   code-point comparison. Vectors: `tests/conformance/domains/match.json`,
   run by the Python and TypeScript reference helpers.
3. **The workflow-level `domain`** (§5.1) is descriptive: the domain of the
   profile the workflow is written for (a profile's `domain`, such as
   `data-analysis`). It changes no validation or execution and is not a
   default for steps. It keeps the profiles' naming (kebab case), which is a
   different namespace.
4. **Migration.** `schemas/workflow_catalog.yaml` line 107
   `plan-invalidation` → `plan_invalidation`; `tools/sync_skill_schemas.py`
   regenerates the 17 bundled copies.

**Options considered.** (a) Allow `-` too — rejected: two spellings of one
domain defeat exact matching. (b) Make a bad value S303 — rejected: invalidates
1.1 workflows; warning first, error in a later MAJOR. (c) Exact matching only
— rejected: hierarchical ids exist so that a generic `image` pipeline can
serve `image.object` when no specific one exists. (d) Fall back to the
domain-less implementation for a step without `domain` and otherwise pick any —
rejected: that is the non-determinism the finding reports.

**How it fixes the finding.** `domain` has a grammar with a migration, two
hosts select the same implementation for one workflow (testable by vectors),
and the step field is distinguished from the workflow field and from profile
names.

### ACS-49 — catalog manifest, qualified names, visibility

**Decision.**
- **Manifest.** A catalog MAY carry a manifest under the top-level key
  `catalog`, when its value is a mapping without `steps`: `id` (required;
  dot-separated lowercase segments `[a-z0-9][a-z0-9_-]*`, e.g.
  `acs.reference`), `version` (required; SemVer 2.0.0), `ontology` (optional;
  `major.minor[.patch]`, a different major than the validator's ontology is
  V109), `exports` (optional; names of workflows other catalogs may invoke;
  default none; each must name a workflow of the catalog, else V107),
  `description`. Unknown fields W604 (`x-` exempt). The manifest has no
  `standard`: the Standard version a catalog targets is its header (§11.5),
  as today, which is how the catalog manifest meets S6's §11.6 citation rule
  (S6 records this); its `ontology` is optional because the header's Standard
  version already fixes the ontology major. A manifest in a file whose header
  targets 1.0 or 1.1 is W616 (S6's generalised rule).
- **Workflow names.** SHOULD be identifiers (`[A-Za-z_][A-Za-z0-9_-]*`, the
  `store_as` grammar) other than `catalog`; otherwise W620. A top-level
  `catalog` mapping *with* `steps` is still a workflow (1.1 meaning), with
  W620. A name containing `/` is S303 only when the catalog is validated as
  part of a set (opt-in), where it would collide with qualified ids.
- **Catalog set.** A validator or executor is given one catalog and, optionally,
  others; each other MUST have a manifest with an `id`, and ids are unique —
  else the set is refused (an API error, like an unloadable ontology). How a
  host finds catalogs is out of scope; there is no dependency list in the
  manifest (an open question).
- **Qualified id**: `<catalog id>/<workflow name>`. Resolution of an `invoke`
  target: (1) a workflow of the invoker's own catalog with that name; (2) a
  qualified id with the invoker's own catalog id: its workflow (no such
  workflow: V107); (3) a qualified id of another catalog of the set: that
  workflow if exported (not exported, or no such workflow: V107); (4)
  otherwise — a bare name the catalog lacks, or a qualified id of a catalog
  not loaded — W607 (cannot be checked, as for a bare name in 1.1) and R402 at
  run time. V107 is thus only for a qualified id whose catalog is loaded; no
  1.1 target changes from W607 to V107. A bare name never searches other
  catalogs. V105,
  V107 (triggers), S303/S304 (literal inputs), W608 and W606 propagation all
  work over resolved targets across the set. The executor resolves a
  computed target the same way and refuses an unexported or missing one
  (R402).
- **Diagnostics** about another catalog of the set carry `location.catalog`
  (its id) and a `path` into that catalog's document (ACS-09).
- **Profiles** may list qualified ids in `workflows` (informative schema,
  owned by S6).

**Options considered.** (a) A separate manifest file (`package.json`-like) —
rejected: the catalog file is the unit every tool validates, and an in-file
key keeps single-file catalogs self-describing; a separate file needs
discovery rules. (b) A different reserved key (`$catalog`, `x-acs-catalog`)
— rejected: `x-` is vendor data by definition, and `$` keys are unusual in
YAML; the "mapping without `steps`" rule makes `catalog` unambiguous and
keeps any 1.1 workflow named `catalog` a workflow. (c) `exports` default
"all" — rejected: the finding asks that only exported workflows be
addressable; an explicit list is the safe default. (d) A merge tool instead
of native sets — rejected as the reference design (it would give the wrong
`path` and lose catalog-scoped resolution for computed targets), but the set
is implemented as a merged namespace internally (part 5). (e) Dependency
declarations with version ranges in the manifest — deferred (open question):
not needed to resolve or check qualified ids, and a version-resolution
algorithm is a package-manager design of its own.

**How it fixes the finding.** Catalogs have a manifest (id, version,
ontology version, exports; Standard version by header), a qualified id
addresses another catalog's workflow, visibility is enforced statically and at
run time, the name grammar is decided, and profiles may name qualified ids.
The duplicated example (`examples/digital_twin_sync_loop.workflow_catalog.yaml`
copying three reference workflows) can then invoke
`acs.reference/world_model_build`; that migration waits on the reference
catalog targeting 1.2 (part 8, S6).

### ACS-09 — the keys of `location`

**Decision.**
- §9.8 gets a table that defines every location key the reference and the
  other workstreams use, so their meaning is normative: `workflow` (the key
  in the catalog), `step` (zero-based index in list order, handlers
  included), `capability`, `field` (path relative to the step if `step` is
  present, else the workflow, else the document; keys joined by `.`, indices
  `[n]`; for people), and the others (`ref`, `prerequisite`,
  `expected_type`, `actual_type`, `input_key`, `store_as`, `first_step`,
  `wait_step`, `column`; S2b's `mate`; S6's `profile`; S1's `tool`, `call`
  and `action`). The audit's correction is adopted: without `step`, `field`
  is relative to the workflow (`triggers[0].schedule.cron`), and without
  `workflow` to the document (`catalog.exports[0]`).
- **Other documents.** A finding about a document other than a catalog — a
  domain profile (S6), a tool binding record or a tool declaration (S1, and
  the SDK's existing W602 from the tool mapper, `{tool, capability, field}`)
  — carries the key that names that document (`profile`, `tool`), has
  `field` relative to that document, and has no `path`. So S6's profile
  diagnostics folded into a catalog report keep `{profile, field}` and get
  no pointer into the catalog.
- New `path`: an RFC 6901 JSON Pointer from the root of the catalog document
  (`/review/steps/1/gates/0/when`); present on every finding about the
  catalog document (`""` for the document as a whole); absent for a finding
  about the version header (`field` `# Standard version`, as today) and for
  one about another document. It names the same member as `field`, exactly,
  also where `field` is ambiguous (keys containing `.`, `[` or `]`): the
  reference builds both from the same list of segments where a diagnostic is
  made, so neither is parsed back from the other.
- New `catalog`: the id of the set member a finding is in (ACS-49).
- `column`: 1-based, in Unicode code points (the reference counts bytes
  today; identical for ASCII).
- §9.1: an implementation's own codes MUST NOT have the form of a standard
  code and SHOULD carry a prefix naming the implementation. (S1 already turns
  the binding's three lint codes into standard codes.)
- The projection to a dot/bracket path (Standard Agents' `DefinitionIssue.path`)
  is stated in §9.8 and implemented in the binding (`issuePath`).

**Options considered.** (a) A top-level `path` member of the diagnostic —
rejected: a new top-level member changes the §9.8 object; `location` MAY
already carry keys. (b) Redefine `field` with escaping — rejected: changes
existing output for no gain once `path` exists. (c) Compute `path` from
`field` by splitting at `.` — rejected: ambiguous. (d) Resolve `field`
against the document, longest key first (the first version of this design)
— rejected: with sibling keys `a` (holding `b`) and `a.b`, a finding about
`a`→`b` gets `/a.b`; a stated tie-break would make `path` exact only "usually".
(e) Structured segments — chosen: each diagnostic whose `field` holds a key
the document chose (an input name, an unknown field, a correlate key, a task
input name) is made with a segment list that yields both `field` and the
pointer; any other `field` consists only of names this Standard defines and
indices, which contain no `.`, `[` or `]`, so splitting it is exact.

**How it fixes the finding.** `step` counts from zero, `field`'s base is
stated for catalog findings and for findings about other documents, a
consumer gets one exact path string, and the binding projection is defined.

### ACS-16 — `conflicts_with` across runs and agents

**Decision.** State in §4.3 (and EDGE_TYPES.md §5, the ontology's edge-type
text) that the rule applies within one workflow's step list and does not
reach across runs or agents; name the cases: two runs a host executes at
once (those a schedule trigger starts with `overlap: allow_all`, those event
triggers start, those a host starts itself) and a `delegate` the workflow
does not wait for. Add a host SHOULD: a host that lets runs or delegates act
on the same state at once serialises each `rollback` with every `mutate` and
`persist` on the state it restores, or fails the later step (R402). Add W623
(CONCURRENT_RUN_CONFLICT): a workflow with an `overlap: allow_all` trigger
that **exercises** both capabilities of a `conflicts_with` pair. A workflow
exercises the capabilities of its steps (handlers included), `rollback` when
a gate or failure mode has `action: rollback` (it rolls back state like the
capability), and, transitively, those of the workflows it invokes by literal
target (as W608 follows `workflows_that_wait`): the nested runs of
overlapping runs overlap too. RUNNING_WORKFLOWS.md states that the reference
executor runs a `parallel_group`'s steps one at a time in list order.

Event triggers are not part of W623, and §4.3 and §9.7 say why: an event
trigger declares no overlap policy, so whether a host starts a run for an
event while another runs is the host's choice, governed by the host SHOULD
above; W623 flags only what the workflow itself asks for, a schedule that
allows overlapping runs. Flagging every event-triggered workflow with a
conflicting pair would warn about what the author cannot change in the
workflow (an `overlap` for event triggers is an open question).

**Options considered.** (a) Require hosts to serialise conflicting steps of
runs on one checkpoint scope (MUST) — rejected: "same state" is host
knowledge, there is no conformance class or fixture that can express two runs
(the fixture format scripts one run), and S1 already declines to enforce
`conflicts_with` over calls (§5.18.5); a MUST nobody can test would be a
promise only. (b) Out of scope with no warning — rejected as incomplete: the
Standard itself offers `allow_all`, so it can at least flag the combination it
cannot check.

**How it fixes the finding.** §4.3 says whether `conflicts_with` applies across
runs or agents (it does not), names the cases, tells hosts what to do, and the
validator flags the combination a workflow asks for, also when the
conflicting step is in a workflow it invokes or is a recovery `rollback`.

~~~~markdown
#### 5.1.1 Catalog Manifests and Qualified Names

A catalog MAY carry a manifest, its `catalog` entry:

```yaml

  version: 1.4.0

| `exports` | No | Names of its workflows that other catalogs may invoke; default none. Each MUST name a workflow of the catalog, else V107 |
| `description` | No | For people |

manifest, and no two catalogs of a set may have the same `id`; an
implementation refuses such a set instead of validating or running it. How a
host finds the catalogs of a set is outside this standard. In a catalog

3. otherwise, for a qualified id of another catalog of the set, that

   catalog has but does not export is V107, and a name it does not have is

catalog does not have (as in 1.1), and a qualified id whose catalog is not in
the set, which may be present where the workflow runs and so cannot be
checked. V107 is only for a qualified id whose catalog is the invoking
catalog or another catalog of the set. A bare name never resolves in another
catalog, also inside a workflow of a catalog loaded beside another. The rules
of §5.10 and §5.12 for an `invoke` (V105 for
cycles, now across the catalogs of the set; V107 for a target whose triggers
include no `invoke`; S303 and S304 for a literal input) apply to every
resolved target, and an invoked workflow of another catalog is a nested run
like any other (§5.13, §5.14, §5.17). The executor resolves a target computed
at run time the same way, and refuses one that resolves to nothing, or to a
workflow its catalog does not export, before the nested run starts (R402).
~~~~

### 2.11 New §5.13.1 Answers to an Inquiry (ACS-50)

~~~~markdown
#### 5.13.1 Answers to an Inquiry

`inquire` returns the questions to put to someone. Its output carries
`inquiry_id`, naming the inquiry, and each question an `id`, unique within
the inquiry, and an `answer_type`: `text` (the answer is a string), `choice`

- capability: receive
  purpose: Wait for the owner's answers.
  store_as: answers_out
  timeout: 2h
  wait:
    event_type: inquiry.answered
    correlate: {inquiry_id: "${questions_out.inquiry_id}"}
~~~~

### 2.13 New §5.15.1 Agent Manifests (ACS-29)

~~~~markdown
#### 5.15.1 Agent Manifests

An **agent manifest** (`schemas/agent_manifest_schema.yaml#/agent_manifest`)
states what an agent that a `delegate` step names may do:

```yaml
agent: db-writer
standard: "1.2"
ontology: "2.2"
capabilities: [retrieve, checkpoint, mutate]
task:
  table: {type: string, required: true}
  rows: {type: array}
```

| Field | Required | Description |
|-------|----------|-------------|
| `agent` | Yes | The name a `delegate` step's `agent` and a workflow's `agents` use: a target name, not a principal (§5.15) |
| `standard`, `ontology` | Yes | The Standard and ontology versions the manifest was written against, `MAJOR.MINOR[.PATCH]` (§11.6) |
| `capabilities` | Yes | Every ontology capability the agent may exercise, directly or through agents it delegates to and workflows it invokes |
| `task` | No | The task inputs it accepts, in the form of workflow `inputs` (§5.1) |
| `version`, `description` | No | For people |

Its **maxima** are, over its capabilities' ontology values, the highest
`risk` and the OR of `mutation`, `requires_checkpoint` and `requires_approval`
(`low` and false for no capability). Its **read-only maxima** are the same
over those of its capabilities whose ontology `mutation` is false. The
**join** of several maxima is the highest risk and the OR of each boolean.
A manifest that lists a capability the ontology does not define has no
maxima. `tests/conformance/agents/maxima.json` gives vectors (§10.3).

Manifests are given to a validator and an executor beside the catalogs they
check or run, as the ontology is. A manifest that does not conform to its
schema, whose `ontology` has another major than the consumer's ontology or
whose `standard` the consumer does not support (V109, §11.6), or that names
an `agent` another manifest of the same set names MUST be refused when loaded.
A capability the ontology does not define is V101 where the manifest is used
(§11.6): at each `delegate` step whose target maxima draw on it (§5.15.2).
How a host obtains its manifests is outside this standard; it SHOULD derive
them from what each agent can actually call, and MUST NOT give a manifest
that leaves out a capability the agent can exercise.
~~~~

### 2.14 New §5.15.2 Delegation Targets (ACS-46, ACS-04, ACS-54)

~~~~markdown
#### 5.15.2 Delegation Targets

A workflow that targets 1.2 or later (§11.5) MAY declare `agents`, the agents
its `delegate` steps may delegate to: a non-empty list of distinct, non-empty
strings (else S303). In a workflow that targets an earlier version or
declares none, `agents` is S303: declaring it is an opt-in that an older
consumer must refuse (V109), not ignore.

```yaml
agents: [reviewer-a, db-writer]
```

A host that composes agents statically creates its relationships from it,
and SHOULD check before the run that it provides every listed agent; a listed
agent it does not provide is V107 at `agents[i]`.

In a workflow that declares `agents`:

- **Only listed agents.** A literal `agent` that is not listed is V107. The
  executor refuses a computed `agent` that is not listed, before delegating
  (R402).
- **Target maxima.** A `delegate` step's *target maxima* are, for a literal
  `agent`, its manifest's maxima, and for a computed one, the join of the
  maxima of every listed agent. A step that binds a literal `read_only: true`
  takes read-only maxima instead. The target maxima are *unknown* when the
  manifest of an agent concerned is not given or lists a capability the
  ontology does not define (V101 at the step's `agent`, §5.15.1).
- **Flags.** For such a step, the ontology values of §5.2.1 are the stricter
  of the `delegate` node's and the target maxima. So a delegation to an agent
  that may `mutate` needs a checkpoint running before it (F501) and an
  approval (§5.14), and a declaration weaker than the target maxima is W602.
- **Unknown targets.** An executor MUST NOT delegate for a step whose target
  maxima are unknown: it fails the step before asking the host (R402). Its
  flags were computed without its target.
- **Approval.** An `approval` block on a `delegate` step is not S303 even
  where the target maxima the validator was given do not raise
  `requires_approval`: whether they do depends on the host's manifests. It
  applies whenever they do.
- **Tasks.** For a literal `agent` whose manifest declares `task`, a literal
  `task` mapping that gives a name the manifest does not declare is S303
  (with no `x-` exemption: these are the agent's inputs), and one that lacks a
  required input is S304. The executor refuses both before delegating
  (R402), so a `task` given by reference, and a computed `agent`, are checked
  then.
- **When.** The executor makes these refusals once the step's inputs are
  resolved, before it asks for approval or uses a checkpoint, as it checks a
  `send` destination (§4.4.2): a delegation it will refuse is never put to
  an approver and uses no checkpoint (RECONCILIATION C24).

A workflow that does not declare `agents` keeps the `delegate` node's flags
for its delegate steps, as in 1.1.

**Read-only.** A host that receives a delegation with `read_only: true` and
cannot enforce it MUST refuse the delegation (`accepted` not `true`) instead
of running it. In a workflow that targets 1.2 or later, an accepted
delegation whose resolved `read_only` is `true` fails (R402) unless its host
attests `effective.read_only: true`; `retry` does not apply to this failure
(§5.2): the delegate has already run without the checkpoint and approval its
flags were relaxed from, and another attempt would hand its host another
unchecked delegation.

In a workflow that targets 1.2 or later:

- a `delegate` step whose target maxima are unknown is W621
  (`UNBOUNDED_DELEGATION`) when the workflow declares `agents` (the executor
  will not delegate there without the manifests), and, in a workflow that
  does not, when the step binds no literal `read_only: true` and its
  effective `requires_approval` is false (the delegate may act on the world
  with no checkpoint or approval). Declare `agents` and give their manifests,
  bind `read_only: true`, or require approval;
- a `delegate` step whose `agent` is not a literal, in a workflow that
  declares no `agents`, is W622 (`UNDECLARED_DELEGATE`): a host that composes
  agents statically cannot check the target before the run.
~~~~

### 2.15 New §5.15.3 Continuing a Delegation (ACS-47)

~~~~markdown
#### 5.15.3 Continuing a Delegation

A `delegate` step may bind `continues`: the `task_id` of an earlier delegation
(`${review_a.task_id}`, or an input) whose delegate the host continues
instead of starting a new one. The delegate keeps what it did before, so:

- a step that binds `continues` and a literal `fresh_context: true` is S303.
  A reviewer that binds `continues` therefore never satisfies a quorum's
  `require_fresh_context` (§5.16), which asks every reviewer for a literal
  `fresh_context: true`;
- a delegation whose resolved `continues` is a string fails (R402) if its
  host attests `effective.fresh_context: true`.

`continues` that resolves to null delegates anew, as if it were not bound.

Every delegation call returns a `task_id` of its own, a continuation
included: never the `task_id` it continues (the step fails, R402, if it
does). `continues` may name the `task_id` of any earlier call that started
or continued the delegate; the host maps it to that delegate. So the
correlation of a waiting delegate (§5.13) matches only this call's result,
and `replaces` names one call. A host that cannot continue the delegate
refuses (`accepted` not `true`, or an `Error`). A retry or loop of the step
passes the same `continues` and names the call it replaces; the host cancels
that call's work, not the delegate it continued.
~~~~

### 2.20 §9.8 Diagnostic Format — full replacement (ACS-09)

~~~~markdown
### 9.8 Diagnostic Format

Diagnostics MUST be returned in this format:

```json
{
  "code": "W604",
  "name": "UNKNOWN_FIELD",
  "severity": "warning",
  "message": "unknown field 'requires_aproval' is ignored",
  "location": {
    "workflow": "my_workflow",
    "step": 3,
    "capability": "observe",
    "field": "requires_aproval",
    "path": "/my_workflow/steps/3/requires_aproval"
  },
  "suggestion": "did you mean 'requires_approval'?"
}
```

`location` says where the finding is. Most findings are about the catalog
document: a workflow, a step, or the catalog's manifest or header. Some are
about another document: a domain profile (§5.21), a tool binding record or a
tool the host offers (§5.18). Its keys have these meanings:

| Key | Meaning |
|-----|---------|
| `catalog` | The `id` of the catalog the finding is in, when that is not the catalog being validated but another of its catalog set (§5.1.1) |
| `workflow` | The workflow's name, its key in the catalog. Present whenever the finding concerns a workflow or anything in it |
| `step` | The step's zero-based index in the workflow's `steps` list, in list order (handlers included), whatever the order of checking. Present whenever the finding concerns a step or anything in it |
| `capability` | The capability concerned: the step's `capability`, when it is a string, or a tool's capability (§5.18) |
| `profile` | A finding about a domain profile: its `domain`, or `#<i>`, its zero-based position among the profiles given (§5.21.2). Such a finding has no `workflow` |
| `tool` | A finding about a tool: the name the host offers it under (§5.18). Such a finding has no `workflow` or `step` |
| `call` | The host's identifier of the tool call a safety layer refused (§5.18.8) |
| `action` | The host action tied to the tool (§5.18.3) |
| `field` | The member the finding is about, as a path relative to the step when `step` is present, else to the workflow when `workflow` is present, else to the document the finding is about (the catalog, or the profile or tool record that `profile` or `tool` names): keys joined by `.`, list indices as `[n]` (`gates[0].when`, `input_bindings.task`, `triggers[0].schedule.cron`, `catalog.exports[1]`, `risk_thresholds.auto_approve`). It is written for people, and a key that contains `.`, `[` or `]` makes it ambiguous. A finding about the version header has `field` `# Standard version` |
| `path` | The member `field` names, as an RFC 6901 JSON Pointer from the root of the catalog document (`/review/steps/1/gates/0/when`): for a member that is missing, where it would be; for a finding about a whole workflow or step, that workflow or step; `""` for the document as a whole. Exact where `field` is ambiguous. Present on every finding about the catalog document, and absent from one about the version header or about another document |
| `column` | For a finding in an expression or reference at `field`: the 1-based position, in Unicode code points, of the character it concerns |
| `ref` | The `${...}` reference the finding concerns, as written |
| `prerequisite` | V102: the capability that must run before the step or tool |
| `expected_type`, `actual_type` | B203: the type required and the type found, in the annotation grammar of §5.3 |
| `input_key` | B203 on an input: its `input_bindings` key |
| `store_as`, `first_step` | V104: the name used twice, and the index of the step that used it first |
| `wait_step` | W608: the index of the wait between the checkpoint and the step |
| `mate` | W619: the index of the group mate whose store the step reads (§5.2.3) |

A validator MUST give these keys these meanings, and MUST set `workflow`,
`step`, `profile`, `tool` and `path` as stated. `location` MAY carry further
keys, under names this table does not use. A consumer that needs one path
string for a finding about the catalog uses `path`; one that needs the
dot-and-bracket form of another format writes `workflow`, then
`.steps[step]` when `step` is present, then `.` and `field` when `field` is
present (`review.steps[1].gates[0].when`).

A single error MAY be wrapped as `{"error": {...}}` and a list as
`{"errors": [...]}`, as in 1.0.
~~~~

### 3.4 New supporting schema `schemas/agent_manifest_schema.yaml` (full content)

```yaml
schema:
  name: agent_manifest
  version: 1.0.0
  description: What an agent that a delegate step names may do (Standard v1.2
    §5.15.1, RFC-0007) - the ontology capabilities it may exercise and the task
    inputs it accepts. Its maxima are derived from the ontology, never stated
    here. A manifest is given to a validator or an executor beside the
    catalogs it checks or runs; one that does not conform to this schema,
    that cites another ontology major or an unsupported standard, or that
    names an agent another manifest of the same set names is refused when
    loaded. A capability the ontology does not define is V101 where the
    manifest is used, and the manifest then has no maxima.
agent_manifest:
  type: object
  required:
  - agent
  - standard
  - ontology
  - capabilities
  additionalProperties: false
  patternProperties:
    ^x-: {}
  properties:
    agent:
      type: string
      minLength: 1
      description: The name a delegate step's agent input and a workflow's
        agents list use. A target name, not a principal, compared by exact
        (code-point) equality.
    standard:
      type: string
      pattern: ^[0-9]+\.[0-9]+(\.[0-9]+)?$
      description: The Standard version the manifest was written against,
        MAJOR.MINOR[.PATCH] (Standard v1.2 §11.6); one the consumer does not
        support refuses the manifest (V109).
    ontology:
      type: string
      pattern: ^[0-9]+\.[0-9]+(\.[0-9]+)?$
      description: The ontology version the manifest was written against,
        MAJOR.MINOR[.PATCH] (Standard v1.2 §11.6); another major than the
        consumer's ontology refuses the manifest (V109).
    version:
      type: string
      description: The version of the agent definition, for people.
    description:
      type: string
      description: What the agent is for, for people.
    capabilities:
      type: array
      uniqueItems: true
      items:
        type: string
        pattern: ^[a-z][a-z0-9-]*$
      description: Every ontology capability the agent may exercise, directly
        or through agents it delegates to and workflows it invokes. Its maxima
        are the highest risk and the OR of mutation, requires_checkpoint and
        requires_approval over these capabilities' ontology values; its
        read-only maxima the same over those whose mutation is false.
    task:
      type: object
      additionalProperties:
        $ref: '#/agent_task_input'
      description: The task inputs the agent accepts, in the form of workflow
        inputs (Standard §5.1). A literal task that gives a name not declared
        here, or lacks a required one, is S303 or S304 in a workflow that
        declares agents; the executor refuses both (R402).
agent_task_input:
  type: object
  additionalProperties: true
  properties:
    type:
      oneOf:
      - type: string
      - type: array
        minItems: 1
        items:
          type: string
      description: Data type of this input, a JSON Schema type name or a list
        of them.
    required:
      type: boolean
      description: Whether the task must give this input.
    description:
      type: string
      description: What the input is, for people.
    properties:
      type: object
      additionalProperties: true
      description: Sub-properties of this input.
    ref:
      type: string
      description: Reference to an external schema.
```

A manifest file is a YAML (or JSON) document whose root is an
`agent_manifest`. Repository convention: `*.agent.yaml`.

## 4. New diagnostic codes

All four are warnings (§9.1: W6xx). Final numbers: FOUNDATION.md part C.

| Code | Name | Severity | Meaning | Raised by, where |
|---|---|---|---|---|
| W620 | NONCANONICAL_NAME | warning | A workflow name that is not an identifier `[A-Za-z_][A-Za-z0-9_-]*` or is `catalog`; a step `domain` that is not a domain id; a literal `model_family` binding or `require_model_families` entry outside `[a-z][a-z0-9_-]*` (§5.1, §5.2.4, §5.15). All spec versions | Validator: `validate_catalog_set` (names, location `{workflow}`), `check_step_fields` (`field: domain`), `delegation::check` (`input_bindings.model_family`), `quorum::check` (`quorum.require_model_families[i]`) |
| W621 | UNBOUNDED_DELEGATION | warning | In a workflow that targets 1.2 or later, a `delegate` step whose target maxima are unknown: with `agents`, always (the executor refuses to delegate there); without, when it binds no literal `read_only: true` and its effective `requires_approval` is false (§5.15.2) | Validator: `delegation::check_targets` (`field: input_bindings.agent`; the message names the agents without a manifest, or the three remedies) |
| W622 | UNDECLARED_DELEGATE | warning | In a workflow that targets 1.2 or later and declares no `agents`, a `delegate` step whose `agent` is not a literal (§5.15.2) | Validator: `delegation::check_targets` (`field: input_bindings.agent`) |
| W623 | CONCURRENT_RUN_CONFLICT | warning | A workflow with a trigger whose `overlap` is `allow_all` exercises both capabilities of a `conflicts_with` pair: through its steps (handlers included), a gate's or failure mode's `rollback` action, or the workflows it invokes by literal target, transitively; event triggers excluded (§4.3). All spec versions; once per (workflow, pair), at the first such trigger | Validator: `semantics::concurrent_conflicts` over `semantics::exercised(ns)` (`field: triggers[i].schedule.overlap`; the message names the invoked workflow a capability comes from) |

Existing codes whose meaning grows (no severity change):

| Code | New cases |
|---|---|
| V101 | An agent manifest that lists a capability the ontology does not define, at each `delegate` step whose target maxima draw on it (`field: input_bindings.agent`; S6's §11.6 rule) |
| V107 | A literal delegate `agent` not in `agents`; a listed agent a host composing agents statically does not provide (the binding's `lintDelegationTargets`, `field: agents[i]`); a manifest `exports` entry naming no workflow of the catalog; a qualified invoke target of the invoking or another loaded catalog that lacks the workflow or does not export it |
| V109 | A catalog manifest whose `ontology` major differs from the validator's ontology (an agent manifest that does is refused when loaded) |
| V105 | Invoke cycles across the catalogs of a set |
| W607 | Unchanged for a bare name; also a qualified id whose catalog is not loaded |
| S303 | `agents` not a non-empty list of distinct non-empty strings, or in a workflow that does not target 1.2 or later; manifest `id`/`version`/`exports` malformed; `continues` with literal `fresh_context: true`; a literal task name the manifest does not declare; a workflow name with `/` in a catalog validated with others |
| S304 | Manifest without `id` or `version`; a literal task without an input the manifest requires |
| W602 | A `delegate` declaration weaker than its target maxima |
| W616 (S6) | A 1.2 feature of part 2.22 (`continues`, a qualified invoke target, a catalog manifest) in a workflow (or a manifest in a file) that targets 1.0 or 1.1. Not `agents` (S303 instead) |
| R402 | Executor refusals before asking the host (not retried): unlisted computed agent; unknown target maxima; task undeclared/missing; qualified target unresolved or not exported. After the host answers: continued delegation attested fresh, or returning the `task_id` it continues (retryable); an accepted delegation in a 1.2 workflow whose `read_only` is not attested (a step error, **not** retried); model_id mismatch with identity (retryable, as the existing identity checks) |

The F504 for a `require_fresh_context` reviewer that binds `continues` of the
first version is dropped: such a reviewer is already S303 or F504 (part 1,
ACS-47).

**`src/names.rs`** (new; hand-written matchers, the crate has no regex
dependency)
- `pub fn is_domain_id(s) -> bool`: `split('.')`, every segment non-empty,
  first byte `[a-z0-9]`, rest `[a-z0-9_]`.
- `pub fn is_model_family(s) -> bool`: `[a-z][a-z0-9_-]*`.
- `pub fn model_family(model_id: &str) -> Option<String>`: §5.15's
  derivation (after the last `/`; after the last `.` or `:` before the first
  ASCII digit or `-`, or anywhere if there is neither; the leading ASCII
  letters, lowercased; `None` if empty). Used by the vectors test; the executor does not derive families.
- `pub fn is_catalog_id(s) -> bool`: segments `[a-z0-9][a-z0-9_-]*`.
- `pub fn is_workflow_name(s) -> bool`: `refs::is_identifier(s) && s != "catalog"`.
- `pub fn split_qualified(s) -> Option<(&str, &str)>`: exactly one `/`, left
  `is_catalog_id`, right `refs::is_identifier`.
- `pub fn is_semver(s) -> bool`: SemVer 2.0.0 (numeric identifiers without
  leading zeros, optional `-pre` and `+build` identifier lists).
- `pub fn parse_cited(s) -> Option<(u64, u64, Option<u64>)>`:
  `MAJOR.MINOR[.PATCH]` (S6's `semantics::parse_version` if public; one
  function).
- `pub fn canonical_domain_hint(s) -> Option<String>`: lowercased, `-`→`_`,
  returned only if the result `is_domain_id` (used for W620's suggestion).

**`src/agents.rs`** (new; shared by validator and executor)
- `#[derive(Clone, Copy, Debug, PartialEq, Eq)] pub struct Flags { pub risk: Risk, pub mutation: bool, pub requires_checkpoint: bool, pub requires_approval: bool }`;
  `Flags::NONE` (low, false ×3); `Flags::of(&Capability)`; `Flags::join(self, other)`.
- `pub struct Manifest { pub agent: String, pub capabilities: Vec<String>, pub unknown: Vec<String>, pub task: Option<Map<String, Value>> }`
  (`unknown`: listed ids `ontology.get` does not know, in list order);
  `Manifest::maxima(&self, ontology: &Ontology, read_only: bool) -> Option<Flags>`
  (`None` when `unknown` is non-empty; else fold `join` over capabilities,
  skipping `mutation: true` ones when `read_only`).
- `#[derive(Clone, Default)] pub struct Agents { by_agent: BTreeMap<String, Manifest>, raw: Vec<Value> }`;
  `Agents::load(values: &[Value], ontology: &Ontology, supported: &[(u64, u64)]) -> Result<Agents, String>`
  refuses: a root that is not a mapping; `agent` missing, not a string or
  empty; `standard` or `ontology` missing or not `MAJOR.MINOR[.PATCH]`;
  `ontology` major ≠ `ontology.version`'s major, or `standard` not in
  `supported` ("… V109: the manifest cites ontology 3.0; this implementation
  uses 2.2"); `capabilities` missing, not a list of strings, or with a
  duplicate; `task` not a mapping or an entry not a mapping;
  `version`/`description` not strings; any other key not starting `x-`; two
  manifests for one `agent`; more than `MAX_MANIFESTS = 1000`. Unknown
  capability ids are **not** refused (kept in `unknown`). Messages name the
  agent and the member. `get(&self, agent)`, `is_empty()`,
  `digest_value() -> Value` (the raw manifests sorted by `agent`).
- `pub fn declared(wf: &Map<String, Value>, target: Option<(u64, u64)>) -> Option<Vec<&str>>`:
  the workflow's `agents` if the target is at least `(1, 2)` and it is a
  non-empty list of distinct non-empty strings; `None` otherwise (both are
  S303 in the validator, and the executor never starts an invalid workflow).
- `pub fn literal_agent(step) -> Option<&str>`: `input_bindings.agent` when a
  string with no `${`.
- `pub fn binds_read_only(step) -> bool`: literal `input_bindings.read_only == true`.
- `pub enum Target { Free, Known(Flags), Unknown { missing: Vec<String>, unknown: Vec<(String, String)> } }`
  and `pub fn target_maxima(agents, ontology, declared: Option<&[&str]>, step) -> Target`:

## 9. RFC text: `spec/RFC-0007-delegation-catalogs-and-diagnostics.md`

~~~~markdown
# RFC-0007: Delegation, catalogs and validator diagnostics
**Status:** Accepted
**Target:** Standard v1.2.0
**Date:** 2026-11-15

## Summary
This RFC records the decisions behind eleven changes in Standard 1.2.0, made
on the maintainer's instruction to implement every remaining finding of the
Standard Agents mapping
(`docs/research/analysis/standard_agents_mapping/findings_agent_capability_standard.yaml`:
ACS-04, ACS-09, ACS-16, ACS-17, ACS-24, ACS-29, ACS-46, ACS-47, ACS-49,
ACS-50, ACS-54). It adds an agent manifest (`schemas/agent_manifest_schema.yaml`)
and a workflow field `agents`, with which a `delegate` step takes the safety
flags of what its target may do, is not delegated without its target's
manifest, and has its task checked; enforcement of `read_only` in 1.2
workflows; a `delegate` input `continues`; a catalog manifest with qualified
workflow ids for `invoke`; a grammar and a host selection rule for a step's
`domain`; typed answers to `inquire`; a defined diagnostic `location` with an
RFC 6901 `path`; the scope of `conflicts_with`; and the comparison and
derivation of model families. Four warnings are new (W620–W623); no error
code is. Every behaviour change is opt-in or a warning; the text is in
`spec/STANDARD-v1.2.0.md` §4.3, §5.1, §5.1.1, §5.2, §5.2.4, §5.13.1,
§5.15–§5.17 and §9.

## Motivation
Mapping ACS against the Standard Agent Specification found places where a
host had to guess or where the Standard knew less than a binding needed:

1. A `delegate` step validates and runs with `risk: medium` and no checkpoint
   or approval, whatever the target agent does (ACS-04). Nothing describes
   what an agent may do (ACS-29), so a validator cannot know, and a task is
   checked only when the host refuses it (ACS-54).
2. A workflow cannot declare the agents it delegates to, which a host that
   composes agents statically needs (ACS-46), and cannot continue an earlier
   delegation, so the validator cannot see that a reviewer is not fresh
   (ACS-47). Model families are compared exactly by the reference
   implementation, but no text says so or says how a host names one (ACS-17).
3. A catalog is a flat mapping; an `invoke` names a workflow by bare name in
   the one loaded catalog, so a workflow cannot call one from another catalog
   and nothing says which workflows a catalog offers (ACS-49).
4. A step's `domain` has no grammar and no matching rule, so two hosts can
   dispatch one workflow differently (ACS-24).
5. `inquire`'s questions have no required key and no typed answer (ACS-50).
6. §9.8 shows `location` only by example; a consumer that needs one path
   string guesses the projection (ACS-09).
7. §4.3 says conflicting capabilities "may not run concurrently" and
   enforces one parallel group, while the Standard itself offers concurrent
   runs (`overlap: allow_all`) and delegates that run beside their delegator
   (ACS-16).

## Goals
- A delegation carries the checkpoint and approval requirements of what its
  target may do, when the workflow author opts in, without changing any 1.1
  workflow.
- One descriptor of an agent's capabilities and task, used by the validator,
  the executor, the Python SDK and the Standard Agents binding.
- Catalogs that can be published and invoked from other catalogs, with
  stated visibility.
- Deterministic domain dispatch and a stated meaning for every diagnostic
  location key.
- Language-neutral vectors for every rule a host implements.

## Non-goals
- Dependency declarations and version resolution between catalogs (open
  question 1); finding catalogs is the host's.
- Enforcing `conflicts_with` across runs (no fixture can express two runs;
  "same state" is host knowledge).
- A registry of model families.
- What a delegator's checkpoint covers across a delegation (RFC-0009,
  ACS-18).
- Tool-call delegation scopes (RFC-0005).

## Key decisions

### 1) An agent manifest is a supporting schema, and context
`agent_manifest` has `agent`, `standard` and `ontology` (the versions it
cites, per §11.6), `capabilities` (everything the agent may exercise, also
through its own delegates and invoked workflows) and an optional `task` in
the form of workflow `inputs`. Its maxima are derived from the ontology: the
highest risk and the OR of `mutation`, `requires_checkpoint` and
`requires_approval`; read-only maxima use only the capabilities whose
`mutation` is false; a manifest listing a capability the ontology lacks has
none, and that id is V101 where the manifest is used. Manifests are given to
the validator and executor beside the catalogs, like the ontology; a
malformed one, one citing another ontology major or an unsupported standard,
and a duplicate are refused when loaded. Stored maxima, a canonical (§6.1)
schema and workflow-side manifest references were rejected (see
Alternatives).

### 2) `agents` is the author's explicit opt-in, and needs 1.2
A workflow field `agents` lists the agents its delegate steps may delegate
to. It is allowed only in a workflow that targets 1.2 or later (S303
otherwise), so a workflow that uses it declares 1.2 and a 1.1 consumer
refuses it (V109) instead of ignoring the field and running its delegates
without the raised checkpoint and approval. Declaring it: restricts targets
(V107 static, R402 at run time; a static host reports a listed agent it does
not provide as V107); raises a delegate step's ontology baseline to its
target maxima (a literal agent's, or the join of every listed agent's for a
computed one; read-only maxima with a literal `read_only: true`), so F501,
approval, W602, W606 and W608 follow; stops the executor from delegating for
a step whose target maxima are unknown (R402, fail-closed); allows an
`approval` block on any of its delegate steps, so validity does not depend
on the manifests given; and checks tasks (S303/S304 static, R402 at run
time). A field, rather than the version alone, because raising flags needs
manifests: making every 1.2 workflow subject to them would refuse every 1.2
delegation a host has no manifest for. The field is the author's statement
that the host can supply them.

### 3) `read_only` is enforced in 1.2 workflows
Read-only maxima, and W621's `read_only` remedy, rest on the host honouring
`read_only`. A host that cannot enforce it refuses the delegation. In a
workflow that targets 1.2, an accepted delegation whose resolved `read_only`
is true fails unless the host attests `effective.read_only: true`; the
failure is a step error that `retry` does not repeat, because the delegate
has already run and a retry would hand the same host another unchecked
delegation. The executor knows the target from `spec_version` or the header
it is given (S6's start option).

### 4) Two warnings for 1.2 workflows only
In a workflow that targets 1.2, W621 reports a delegate step whose target
maxima are unknown: always where the workflow declares `agents` (the
executor will not delegate there), and otherwise when it binds no literal
`read_only: true` and requires no approval. W622 reports one whose target is
computed in a workflow without `agents`. Their remedies are 1.2 features, so
they do not apply to 1.1 workflows.

### 5) `continues` is a base input, and every call has its own `task_id`
A delegation that continues an earlier one never has a fresh context: S303
with a literal `fresh_context: true` (so such a reviewer never satisfies
`require_fresh_context`, which already requires the literal), R402 when the
host attests a fresh context; null delegates anew. Every delegation call,
a continuation included, returns its own `task_id`, so a waiting delegate's
correlation and `replaces` name one call; `continues` may name any earlier
call of the chain. It is not governed by `delegation@1`: that would make a
1.1 workflow that bound it (W604) invalid (V106), and a 1.1 consumer of
`delegation@1` does not know it anyway; S6's W616 reports it in a workflow
that targets an earlier version.

### 6) Model families: exact, lowercase, derived by one rule
Families compare by exact code-point equality everywhere. A host derives a
family from the model's identifier: after the last `/`, after the last `.`
or `:` before the first digit or `-`, the leading ASCII letters, lowercased
(`claude-opus-4-1` → `claude`, `o3-mini` → `o`). The rule needs no list of
lines and is pinned by vectors; a literal outside `[a-z][a-z0-9_-]*` is
W620. An identity (and the world state's copy of it) and `effective` may
carry the `model_id`, checked against each other under `identity@1`.

### 7) Catalog manifests and qualified ids
A top-level `catalog` mapping without `steps` is the manifest (`id`,
`version`, `ontology`, `exports`; its Standard version is the file header);
with `steps` it stays a workflow. A qualified id `<catalog id>/<name>` names
a workflow of another catalog of the set an implementation is given; only
exported workflows resolve from outside their catalog, and a bare name
always means the invoker's own catalog. A qualified id of the invoking or
another loaded catalog that lacks the workflow, or hides it, is V107; every
other unresolved target, a bare name included, stays W607, so no 1.1 target
changes code. Cycles, triggers, inputs, waits and unattended propagation work
across the set. The executor resolves computed targets the same way.
Workflow names SHOULD be identifiers (W620).

### 8) Domain ids and selection
A domain id is lowercase segments joined by dots, underscores inside a
segment (one spelling per domain), digits allowed first (`image.3d`). A host
selects the exact implementation, else the longest prefix at a dot, else the
domain-less one, else fails the step with R402 and reason
`unsupported_domain`; a step without `domain` takes the domain-less one. The
workflow-level `domain` is descriptive.

### 9) Answers to `inquire`
The ontology adds `inquiry_id`, a question `id` and `answer_type`, and
`receive` items' `inquiry_id` and `answers` (`{question_id, value}`). A host
that produces `inquire` output MUST give ids; answers are keyed by `id` (or
`parameter`), typed by `answer_type`, never for an unasked question or twice.
Requiring `parameter` was rejected as a MAJOR change.

### 10) Diagnostic locations
§9.8 defines every location key, those of the other 1.2 workstreams
included: `step` is a zero-based index in list order; `field` is relative to
the step, else the workflow, else the document the finding is about; a
finding about a profile or a tool names it (`profile`, `tool`) and has no
`path`; `path` is an RFC 6901 pointer from the catalog root, present on
every finding about the catalog; `catalog` names the set member; `column`
counts code points. The reference builds `field` and `path` from the same
segments where a diagnostic is made, so `path` is exact even for keys that
contain `.`. Implementation-defined codes may not take the standard form
(§9.1).

### 11) `conflicts_with` is per workflow
The rule keeps conflicting steps out of one `parallel_group`; it does not
reach across runs or agents. §4.3 names the cases, a host SHOULD serialise a
`rollback` with `mutate` and `persist` on the same state, and W623 flags an
`allow_all` trigger on a workflow that exercises both capabilities of a pair,
through its steps, a `rollback` action, or the workflows it invokes. Event
triggers are left to the host: they declare no overlap policy.

## Backward compatibility
Standard 1.2.0 is a MINOR release. No workflow valid under 1.1 becomes
invalid, and no 1.1 workflow runs differently, unless it opts in:

- by declaring 1.2 (W621, W622, the `read_only` attestation) and, in such a
  workflow, `agents` (target maxima, V107, no delegation without manifests,
  task checks, executor refusals); `agents` in a workflow that does not
  declare 1.2 is S303, which a 1.1 workflow could only meet by carrying an
  unknown key of that name (none in the repository);
- by binding `continues` (its S303 and R402), a new optional input (§11.4);
- by being given with other catalogs or using a qualified id (catalog sets);
  a single catalog validates and runs exactly as before, a bare name that
  does not resolve stays W607, and a `catalog` mapping with `steps` is still
  a workflow.

W620 and W623 are new warnings for every version, phased in before any
error. A host that cannot enforce `read_only` refuses the delegation, which
states 1.1's "must not change anything" as a host rule; a host derives model
families by the rule of §5.15. The ontology (2.2.0),
`agent_identity_schema.yaml` (1.1.0) and the canonical
`world_state_schema.yaml` (1.2.0, whose `AgentIdentity` copies the identity
schema and gains the same optional `model_id`) change only by optional
members and descriptions. The executor's snapshot digest is unchanged for a
single catalog without manifests. The one repository change a new warning
requires is the step domain `plan-invalidation` in
`schemas/workflow_catalog.yaml`, renamed `plan_invalidation` with its bundled
copies. The Python SDK's `AgentDescriptor.identity()` now refuses a
non-canonical model family, `DelegationProtocol.delegate()` refuses a task
that does not fit the agent's declaration, and `effective_flags` raises for
a delegate step whose target maxima are unknown.

## Alternatives considered
- **Raising every `delegate` step's flags whenever a manifest is available.**
  Rejected: a host supplying manifests would make 1.1 workflows fail F501 or
  ask for approval they did not ask for before.
- **Raising flags in every workflow that declares 1.2, with no field.**
  Rejected: the executor sees the header (S6's start option), so the version
  alone would work mechanically, but target maxima need manifests, and
  every 1.2 delegation a host has none for would then be refused. `agents`
  is the author's explicit opt-in that the host can supply them; the 1.2
  declaration it requires is what makes older consumers refuse it. The
  `read_only` attestation and the two warnings do key on the version alone.
- **`agents` under any target, with W616 for a 1.1 target.** Rejected: a 1.1
  consumer would ignore the field (W604) and run the delegates with 1.1
  flags, silently dropping the protection the author opted into.
- **Delegating with the `delegate` node's flags when manifests are missing
  at run time.** Rejected: it fails open.
- **Retrying a delegation whose `read_only` was not attested.** Rejected:
  every retry is another unchecked delegation to a host that ignored it.
- **A new extension (`agents@1`, `delegation@2`) for `agents` and
  `continues`.** Rejected: the 1.2 declaration `agents` requires already
  makes an older consumer refuse the workflow, and a second declaration
  would split delegation semantics.
- **A continuation that reuses the `task_id` it continues.** Rejected: a
  waiting delegate correlates on `task_id`, so the earlier call's result
  would match the continuation's wait, and `replaces` would name two calls.
- **A quorum F504 for a reviewer that binds `continues`.** Rejected: such a
  reviewer is already S303 or F504, so the rule could never add a finding.
- **A canonical agent schema in §6.1, stored maxima, or manifests referenced
  from the workflow.** Rejected: not every implementation delegates; two
  sources of truth; the workflow author does not own the host's agents.
- **A separate package manifest file, `exports` defaulting to all, or a
  merge tool for catalogs.** Rejected: a catalog file should describe
  itself; the safe default is explicit; a merge loses catalog-scoped names
  and exact locations.
- **Dependency declarations with version ranges.** Deferred (open question
  1).
- **Hyphens in domain ids; an error for a bad domain; exact domain matching
  only.** Rejected: two spellings; invalidates 1.1 workflows; prevents a
  generic implementation serving a specific domain.
- **Case-insensitive family comparison, a family registry, or a table of
  lines with a fallback.** Rejected: changes what the executor counts; goes
  stale; two editions of a table could disagree on one model id, which a
  rule over the id alone cannot.
- **Requiring `inquire.parameter`.** Rejected: a MAJOR change to an output
  contract.
- **A top-level `path` member, or a re-escaped `field`.** Rejected: changes
  the §9.8 object or existing output; `location` already admits keys.
- **Deriving `path` by resolving `field` against the document.** Rejected:
  sibling keys `a` and `a.b` make it wrong; segments make it exact.
- **Hosts MUST serialise conflicting steps across runs.** Rejected: not
  testable, and "same state" is host knowledge.
- **W623 for event triggers.** Rejected: they declare no overlap policy, so
  the warning would report what the author cannot change in the workflow.

## Open questions
1. Should a catalog manifest declare the catalogs it depends on, with version
   ranges, and how would a host resolve them (the domain-profile marketplace
   on the roadmap)?
2. Should W621 and W622 become errors in a later MAJOR, and should a host's
   agent manifests be published somewhere a validator can fetch them?
3. Does `answer_type` need more types (a score on a scale, several choices),
   and should a question carry a JSON Schema for its answer?
4. Should a host conformance class (RFC-0006) make cross-run serialisation of
   `rollback` against `mutate` and `persist` a MUST with a stated scope, once
   runs and their scopes are part of the host protocol?
5. Should the step `domain` grammar become S303 in Standard 2.0, and should a
   domain registry accompany the ontology?
6. Should event triggers gain an `overlap` policy, so that W623 can cover the
   runs they start?
7. (Resolved by S6, RECONCILIATION C4.) The start operation always takes
   the header's version or an explicit none (§11.5, §5.19.2), and a host
   that loaded the catalog from a file MUST pass it, so a 1.2-by-header
   workflow is never run as one that declares no version.
8. Should the model family rule be revisited when a provider names a line
   whose identifiers do not start with its name (none of the lines in the
   vectors does)?
~~~~

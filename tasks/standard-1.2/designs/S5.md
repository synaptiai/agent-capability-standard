What makes this one design: a checkpoint is the host's copy of the state
within a scope (§4.4.1). Everything else follows from what that copy can and
cannot restore: a transmission (ACS-19) and a delegate's changes outside the
scope (ACS-18) are listed as `not_covered`, so they are prevented before they
happen (destination policy, approval, at most one effect per approval:
ACS-52, ACS-19); and memory written by `persist` (ACS-27, ACS-48) is restored
only when a checkpoint captured it.

## 1. Per finding: decision, rationale, how it fixes the finding

### ACS-26 — checkpoint content and the meaning of `restored: true` (decided first: ACS-19 and ACS-18 build on it)

**Decision.**

1. **Definition** (§2, §4.4.1). A checkpoint is a copy, kept by the host, of
   the state within its scope, from which that state can be restored. The
   `checkpoint` step's `scope` input names what to capture in the host's
   naming (`*`: everything the host can restore); a `CreateCheckpoint`
   (executor-requested, §5.2.2) covers what the step may change, as far as
   the host can tell, else everything it can restore.
2. **Promoted outputs** (ontology 2.2.0, all optional): `checkpoint` gains
   `mechanism`, `captured`, `excluded`, `digest`, `expires_at`; `rollback`
   gains `unrestored`, `not_covered`, `changes_reverted`, `verification`.
   The skills' `restore_command` and `pre_mutation_state.summary` stay
   skill-level (they are model aids, not contract): `restore_command`
   assumes a shell, and a host-neutral contract cannot type it.
3. **Retention vs validity.** `expires_at` on a checkpoint is when the host
   may discard the content (retention). Validity (S1's §5.2.2) limits what a
   checkpoint authorises; retention limits what it can restore. A used or
   invalidated checkpoint can still be restored while its content is kept
   (agrees with S1's "an expired or used checkpoint can be restored").
4. **What `restored: true` asserts:** every item the rollback concerns is
   back in its checkpointed state; `unrestored` is then empty. Items the
   checkpoint never covered (a transmission, a delegate's change elsewhere,
   anything outside its scope) are reported separately in `not_covered`
   and do not make `restored` false. The one exception is an item the
   rollback's own `scope` names that the checkpoint never captured: the
   workflow asked for it explicitly and it cannot be restored, so it is in
   `unrestored` with reason `not_captured`, and `restored` is false (a
   rollback that names `b.txt` from a checkpoint that captured only `a.txt`
   is not a success).
5. **Is `restored: false` F503? No.** A `rollback` step completes whether
   or not `restored` is true; the workflow decides what follows (after-gate
   `stop`, or a failure mode with `when` that escalates). Rationale:
   (a) a 1.1 run whose rollback step returns `restored: false` completes
   today, and making it fail would change what 1.1 workflows do;
   (b) F503 is not in the `on_error` list (§5.7), so a run would end with no
   chance for the workflow's own escalation; (c) the step form exists so the
   workflow decides what follows, unlike the executor's own rollback. To phase
   the check in, W624 (`UNCHECKED_ROLLBACK`) reports, in a workflow that
   targets 1.2, a rollback step whose `restored` no condition, gate or
   failure-mode `when` reads. F503 stays the code of the executor's own
   `Rollback` (gate/failure-mode action): the host answers `RolledBack` only
   on a full restore and an `Error` otherwise (the run ends F503), exactly as
   in 1.1, now stated.
6. **`RolledBack.not_covered`** (optional response member, §5.19.1): a host
   that restored the checkpoint can still report changes it never covered;
   the executor records them in the `rolled_back` trace event and, in S2b's
   record mode `actions`, in the rollback record's `details`. An entry with a
   reason other than `transmitted`, `delegated`, `outside_scope` or `x-…` is
   refused as malformed (an in-scope failure is an `Error`, not a
   `RolledBack`).
7. **The conversation record is never within a rollback's reach**: the run's
   stores, trace, action records, approval decisions, evidence and audit
   records, the transcript of the agents involved, and the host's own
   records of what it did and may do (its audit log, its checkpoint and
   approval state, its idempotency keys, its saved runs). A rollback changes
   the world back, not the account of it; an audit trail a rollback could
   erase would not be one, a consumed checkpoint a rollback could bring back
   would authorise a second change, and an idempotency key a rollback could
   erase would let a send go twice. A host whose checkpoint would otherwise
   capture such a record (a file under the same directory) leaves it out and
   reports it in `excluded`. Data `persist` wrote is restored only when a
   checkpoint captured it.
8. **Skills** (`checkpoint`, `rollback`) are rewritten host-neutrally:
   mechanisms by kind (version-control snapshot, file copy, store snapshot,
   savepoint, provider snapshot), no `.checkpoints/` assumption. The git
   example takes the checkpoint with one plain call, `git stash create
   "checkpoint:<id>"` (what S1's classifier counts as `checkpoint`, and which
   leaves the working tree unchanged): its printed sha is the restore point,
   and an empty output means a clean tree, whose restore point is `HEAD`
   (`git rev-parse HEAD`, read-only). Untracked files, which `git stash
   create` does not capture, are listed in `excluded` (`git ls-files
   --others --exclude-standard`). The rollback restores the worktree from the
   sha and the index from its index parent (`git restore`), removes the files
   created in scope since the checkpoint, and reports what it could not
   restore. (Verified on git 2.x: `git stash create` on a clean tree prints
   nothing and `git stash store ""` exits 1; `git stash apply <sha>` aborts
   with "local changes would be overwritten" once a file it touches changed
   since, which is the usual case for a rollback; `git restore` leaves
   untracked files in place.)
9. **Reference host.** `grounded_agency/state/snapshots.py`
   `FileSnapshotStore` (content-addressed file copies with a manifest and a
   digest; protected paths no caller can remove: `.claude/**`, its own
   store, the tracker's directories, and every path registered with the
   Host; default exclusion of secret-bearing file names; objects and
   manifests 0600 in 0700 directories); `CheckpointTracker(snapshots=…)`
   captures content, registers its own directories as protected, and gains
   `restore_checkpoint()` and `checkpoint_output()`; `Host.rollback` restores
   and answers `RolledBack` (with `not_covered` for the run's own
   transmissions, destinations redacted) or `Error` F503;
   `Host.invoke_capability` performs `checkpoint` and `rollback` steps when a
   snapshot store is configured.

**Options considered.**
- `restored: false` → F503 always: rejected (changes 1.1 runs; F503 cannot be
  caught by `on_error`).
- `restored: false` → F503 only for `spec_version: "1.2"`: rejected; the
  executor does not reliably see a file header (`Run::prepare` validates
  without it; S2b and S3 reached the same conclusion), so validator and
  executor could disagree on a workflow's version.
- A new opt-in input `require_restored` (as S2b's `audit.require_record`):
  rejected as unnecessary. A gate or failure mode reading `restored` is the
  existing mechanism and gives the author the choice of stop or escalate;
  W624 makes the omission visible. (S2b's case differs: ACS-20 asked for a
  defined diagnostic for a required capture.)
- One list `unrestored` with in-scope and out-of-scope reasons: rejected; two
  lists keep the invariant `restored` ⇔ `unrestored` empty, which a reader
  can check without knowing the reasons.
- Output `scope` (object) on `checkpoint`, as the skill had: rejected; it
  would share a name with the string input `scope` while meaning something
  else. `captured`/`excluded` say what they are.
- A rollback `scope` item the checkpoint never captured as `not_covered`
  (`outside_scope`): rejected (review); `not_covered` does not make
  `restored` false, so a rollback asked to restore something it cannot would
  report success. `not_captured` in `unrestored` keeps the invariant.
- Recording the git restore point with `git update-ref
  refs/checkpoints/<id> "$sha"` and having S1's classifier count that command
  as `checkpoint` (proposed by the review): declined. It names a commit the
  caller chooses, which is the reason S1 stopped counting `git stash store`:
  a model could mint a "checkpoint" from any commit. Run after `git stash
  create`, it would also be a gated `mutate` in the plugin and use up the
  marker the `create` just wrote, so the change it was meant to protect
  would then fail F501. The fallback the review asked for is kept (an empty
  `create` output means the restore point is `HEAD`). Retention of the
  unreferenced stash commit is git's (`gc.pruneExpire`, two weeks by
  default), far beyond a checkpoint's validity; the skill reports no
  `expires_at` for it, and a host that must keep it longer pins it outside
  the agent's commands (open question 6).

**How it fixes the finding.** The Standard says what is saved (the state
within the scope, reported as `captured`, `excluded`, `digest`), what
`restored: true` asserts, what `restored: false` does (the step completes;
the executor's own rollback fails F503), and that the conversation record is
outside a rollback's reach; the skills' fields are ontology outputs with
`unrestored[]` and reasons; the skills no longer assume git or a project
directory; the Python SDK stores content and restores it.

### ACS-19 — `send` requires a checkpoint, but rollback of a transmission is undefined

**Decision.**

1. **Text** (§3.3, §4.4, §4.4.2, §12.1): for `send`, the checkpoint records
   the intent and the agent's own state before the transmission; it is not an
   undo. §12.1's decision tree, which implied a checkpoint helps where it
   cannot restore, is rewritten: an irreversible effect is made safe before it
   happens (constrain, approval, destination policy, at most once).
2. **Idempotency key: host-derived, executor-issued.** Every
   `InvokeCapability` carries `idempotency_key` = `<run_id>:<n>`, where `n`
   is the `id` (S2b §5.19.1) of the pass's first `InvokeCapability`. So it is
   the same for every attempt of one pass (retries, and the action a restored
   run issues again) and different for every other pass of every step,
   nested runs included (recovery loops and invoke runs start new passes). A
   `delegate` attempt that names `replaces` asks for a new delegation and gets
   a key of its own (its own `id`). The key is built from S2b's normative
   action numbering, so another executor computes the same value and fixtures
   can pin it.
3. **Host duty** (§4.4.2): a host MUST NOT transmit twice for one key. Given
   a key it already transmitted under, it answers with that transmission's
   output; where it cannot tell whether an earlier attempt transmitted and the
   destination does not de-duplicate by the key, it does not transmit and
   answers `Error` with reason `outcome_unknown` (R402, so `on_error` and
   escalation apply). A host SHOULD pass the key to a destination that accepts
   one (an `Idempotency-Key` header, a message de-duplication id), and SHOULD
   apply the rule to any other capability whose effective `mutation` is true,
   except a delegation that `replaces`. One approval therefore authorises at
   most one transmission: retries share the pass's decision and its key.
   **A key is unique only if the `run_id` is**: a host that keeps keys across
   runs or restarts depends on S2b's §5.19.2 MUST (a `run_id` is unique among
   the runs whose records or keys the host keeps), which §4.4.2 cites. As a
   second line of defence, a host never answers an attempt with an earlier
   output whose capability or inputs differ: the inputs of a pass are fixed
   (the executor resolves them once, in `ready()`, and a retry goes back to
   `Stage::Execute` without resolving them again; verified in
   `core/src/exec/machine.rs`), so a difference means the key was reused,
   and the host answers `Error` reason `key_conflict` without acting. Since a
   restored run issues its pending attempt again (§5.19.4), a host that saves
   runs keeps its keys at least as durably as the runs, or the rule fails
   across its restarts.
4. **Compensation:** optional `send` output `compensation` in the form of
   `world_state_schema.yaml` `TransitionRule.rollback` (`strategy`,
   `inverse_effects`). Nothing performs it automatically, a rollback
   included: compensating is a step of its own (a `send` with its own
   checkpoint and approval).
5. **Rollback reporting:** a rollback (step output or `RolledBack`) lists
   the run's transmissions since the checkpoint in `not_covered` with reason
   `transmitted` (SHOULD, for a host that performed them); never another
   run's, and never a secret in the `item` (S4's §6.7: a destination URL can
   hold credentials).
6. **Records:** `ActionRecord.idempotency_key` (world_state 1.2.0, optional);
   the executor writes it on the record of a step's pass once the step calls
   its capability.
7. **Reference host:** `grounded_agency/workflows/idempotency.py`
   `IdempotencyLog.perform(action, effect)`, which keeps with each key the
   capability and the SHA-256 of the RFC 8785 canonical inputs and answers
   `key_conflict` on a mismatch; `Host` uses it for its own transmissions
   log, which `Host.rollback` reads for `not_covered` (the run's own keys,
   prefix `<run_id>:`, destinations redacted). Without a `path` the log is
   in memory; `WorkflowRunner.advance`/`drive` with `save=` refuse a host
   whose log is in memory (a host that saves runs needs durable keys).
8. **Restored version-1 states:** a pending `InvokeCapability` restored
   from a state that predates keys gets `idempotency_key` = `<run_id>:<id>`
   (its own id), set on the action and on the step's state, beside S2b's
   `run_id` fill; later attempts of that pass reuse it. (Attempt 1 of that
   pass, made by a 1.1 executor, carried no key, so no host could have
   de-duplicated on it; from the restore on, the pass has one key.)

**Options considered.**
- An optional `idempotency_key` *input* on `send` (author-supplied): rejected
  as the fix. It fixes nothing unless every author binds it, and a workflow
  has no binding for the run or pass to build one from. It would add
  cross-run de-duplication, which the finding does not ask for; recorded as
  open question 2.
- Key = (`run_id`, `frame`, `step`): rejected; `frame` names workflows, not
  instances, so it repeats across recovery loops and repeated invokes (the
  audit's own observation).
- Key from a new pass counter: rejected; it would make every EX executor
  count passes (skipped steps included) the same way. The `id` of the pass's
  first `InvokeCapability` is already normative (S2b) and so is free.
- Reusing S2b's (`run_id`, `id`) key: it covers re-delivery after a restore,
  not retries, which are new actions with new ids.
- Automatic compensation on rollback: rejected; a compensation is itself a
  transmission that needs a checkpoint, an approval and a policy check.
- A key mismatch answered with `outcome_unknown` (offered by the review):
  rejected for a token of its own, `key_conflict`. The host *knows* what
  happened (another request used the key), and the operator's remedy differs
  (find the reused `run_id`, not check the destination for a delivery).

**How it fixes the finding.** The Standard says what restoring a `send`'s
checkpoint does to transmitted data (nothing; it is listed as `transmitted`);
a retry after R401 carries the same key, and a host may not deliver twice
under one approval; a cancel handle has a defined form; §12.1 no longer
contradicts the clarification.

### ACS-18 — checkpoint and rollback scope across a delegation

**Decision.** New §5.15.4 *Checkpoints Across a Delegation*:

1. **Authorisation.** A run's checkpoints authorise its own steps (§5.2.2),
   those of runs it invokes included (§5.13), and never what a delegate does,
   except where a safety layer orders the delegate's calls in the
   delegator's scope (§5.18.5; item 5). The duty is stated by scope: before
   each change, a delegate MUST have a checkpoint valid in the scope where
   that change is checked (§5.2.2 for a workflow, §5.18.6 for calls): its own
   where it runs in a scope of its own, or, in a shared scope, one taken in
   that scope that no other change has used. A checkpoint a `delegate` step
   itself needs (S3's raised flags, §5.15.2) is the delegator's restore point
   before it hands the change over.
2. **Restoration.** A rollback restores what its checkpoint captured
   (§4.4.1), whoever changed it; it reaches nothing outside that and neither
   recalls a delegation nor stops a delegate. A host that knows of such
   changes lists them in `not_covered`, reason `delegated`. A delegate that
   works on state the delegator's checkpoint captured (a subagent in the same
   working tree) has its changes to that state restored.
3. **All or nothing** needs `read_only: true` (§5.15) or an explicit undo
   step: a `delegate` step that `continues` the delegation (S3's §5.15.3) and
   asks for the reversal, or a step that restores the changed system.
4. **Attestation:** optional `delegate.effective.checkpointed` (boolean): the
   host attests that, before each change, the delegate has a checkpoint valid
   in the scope where that change is checked.
5. **Tool-calling hosts:** a safety layer that orders a delegate's calls in
   the delegator's scope (S1's §5.18.5, "unless the layer orders them with the
   delegator's against one set of records, which it states") applies that
   scope's rules to both: one checkpoint taken in the scope authorises one
   change, whichever agent makes it, and the next change, by either, needs
   another. This is the Python adapter's stated scope ("this adapter
   instance (all sessions and subagents it serves)", S1): the mapper
   classifies `Task`/`Agent` as `delegate`, its subagents share the parent's
   working directory and its tracker, and a checkpoint the adapter's host
   takes (with the new `FileSnapshotStore`) restores their file changes too.
   So the SDK's sharing is a stated, conformant design under the qualified
   bullet 1, not a divergence; no re-keying of `CheckpointTracker` is
   needed. An adapter test pins it: a subagent's `Write` uses up the
   shared-scope checkpoint, so the parent's next `Write` is refused F501
   until a new checkpoint is taken.
6. A normative runtime fixture pins that a failure-mode rollback after a
   plain `delegate` sends only `Rollback {checkpoint_id}` and that the host's
   `not_covered` (`delegated`) is recorded.

**Options considered.** "A delegator's checkpoints do not cover a delegate's
effects" as a flat rule: rejected as false for a subagent in the same working
tree, whose changes a whole-tree checkpoint does restore; the rule is stated
in terms of what the checkpoint captured. Requiring `effective.checkpointed:
true` for every mutating delegation (R402 otherwise): rejected for 1.2 (it
would need an opt-in, and S3's `agents` already raises the delegator's flags);
recorded as open question 3. Keying the SDK tracker by `(session_id,
agent_id)`: rejected; S1 states one scope per adapter, which §5.18.5 allows,
and the snapshot store makes the shared checkpoint restore subagent changes.

**How it fixes the finding.** §5.15 now relates a delegator's checkpoints and
rollbacks to a delegate's changes; the delegate's checkpoint duty is stated
by the scope its changes are checked in, so it holds for a separate scope
and a shared one without contradiction; all-or-nothing has two named
mechanisms; the `effective` member the finding suggested exists; the SDK
behaviour the audit flagged is the shared-scope case of the rule, pinned by
a test.

### ACS-27 — `persist`/`recall` storage scope and `ttl` grammar

**Decision.**

1. Optional `scope` input on `persist` and `recall`: `run`, `session`,
   `user`, `project`, `global`, or an `x-` name; each defined by who can read
   an entry and how long it lasts (§4.5 table). Without it, the host's stated
   default (`session` RECOMMENDED: §11.3 requires a sensible default, and the
   host's own default keeps 1.1 behaviour). `run` is the run the host started
   (one `run_id`, §5.19.2) and every run nested in it: what the protocol
   identifies, since every frame of a run carries the same `run_id` (S2b), so
   entries a nested run stores are visible to its parent and to a later
   invocation of the same nested workflow within that run. (Keying by frame
   instance was the alternative; rejected because the protocol does not
   identify frame instances, so a host could not implement it from the
   actions alone, and because a nested run is part of its parent's work.)
2. Output `scope` on both: the scope used. A host that does not provide the
   requested scope answers `Error` reason `unsupported_scope` (R402). The
   executor fails a step that binds `scope` (resolved non-null) unless the
   output's `scope` equals it (R402, reason `unsupported_scope`): a 1.1 host
   that does not know the input would otherwise store elsewhere silently.
3. `ttl`: a §5.10.1 duration longer than zero. A literal outside the grammar
   (or zero) is W614 (the existing code for an unenforceable duration). A host
   given a `ttl` it cannot parse, or that cannot end entries, does not store
   (`Error`, `unsupported_ttl`). The entry ends `ttl` after `stored_at`
   (`expires_at` in the output); from then on `recall` reports `found: false`.
4. One name for the storage time: `stored_at` on both (`persist` gains it);
   `persist.timestamp` stays as a deprecated alias (same instant), and a
   reference to it is W603 (§11.2 requires a warning for a deprecation).
5. W626 for a literal `scope` that is neither defined nor `x-`.

**Options considered.** Scope as a closed enum in the ontology: the
dialect's `CARRIED` keywords include `enum`, but an enum cannot admit `x-`
names, and `pattern` is not in the dialect (S6's ACS-28); the grammar is in
the description and W626 checks literals. A runtime refusal of an invalid
`ttl` by the executor: rejected (it would change what a 1.1 workflow with a
free-text `ttl` does); W614 statically and the host at run time instead.
Renaming `timestamp`: MAJOR (§11.4); alias plus deprecation instead.
Scopes `agent`/`thread`: `session` covers a thread; an agent's own long-term
memory is `user` or `project` depending on the host; hosts may add `x-`.

**How it fixes the finding.** Visibility and lifetime are defined per scope,
echoed, and enforced (host refusal, executor echo check); `ttl` has the
§5.10.1 grammar with a static warning and a host duty; one name, `stored_at`.

### 2.4 §4.4.1 Checkpoints and Rollback *(new)*

```markdown
#### 4.4.1 Checkpoints and Rollback

A **checkpoint** is a copy, kept by the host, of the state within its
**scope**, from which that state can be restored. Only the host knows what it
can copy and put back, so the host says what a checkpoint covers:

- A `checkpoint` step's `scope` names what to capture, in the host's naming
  (paths or patterns, keys, resource identifiers; for instance a
  white-space-separated list); `*` asks for everything the host can
  restore. A checkpoint the executor has its host take (`CreateCheckpoint`,
  §5.2.2) covers what the step it precedes may change, as far as the host can
  tell, and otherwise everything the host can restore.
- A host SHOULD report what a checkpoint holds: `mechanism` (how it was
  taken: `vcs_snapshot`, `file_copy`, `store_snapshot`, `savepoint`, or an
  `x-` name), `captured` (what it holds), `excluded` (what the scope named
  that it does not hold, such as a secret the host will not copy or a system
  it cannot copy), `digest` (of the captured content, as
  `<algorithm>:<lowercase hex>`, e.g. `sha256:…`) and `expires_at` (when the
  host may discard the content).
- A host SHOULD keep a checkpoint's content at least until the run that
  took it ends; a rollback to content the host has discarded reports it
  `discarded`. Validity (§5.2.2) limits what a checkpoint authorises;
  retention limits what it can restore. A checkpoint that was used up or is
  no longer valid can be restored while its content is kept.
- A checkpoint never captures the record of what happened (below), even
  where the scope names it, as `*` does: the host leaves it out and reports
  it in `excluded`.

A **rollback** returns what a checkpoint captured to the state it had when
the checkpoint was taken, whoever changed it since. A `rollback` step's
`scope` may name part of what was captured; the rollback then concerns that
part only. An item the rollback's `scope` names that the checkpoint did not
capture (never in its scope, or `excluded` from it) is concerned too, and
cannot be restored: it is in `unrestored` with reason `not_captured`. Its
output reports the outcome:

| Field | Meaning |
|-------|---------|
| `restored` | `true` only if every item the rollback concerns is back in its checkpointed state; otherwise `false` |
| `unrestored` | The items the rollback concerns that are not back in their checkpointed state, each with a `reason`: `failed` (restoring it failed), `conflict` (it was changed since in a way the host will not overwrite), `discarded` (the checkpoint's content for it is gone), `not_captured` (the rollback's `scope` names it and the checkpoint did not capture it), or an `x-` reason. Empty or absent exactly when `restored` is `true` |
| `not_covered` | Changes made since the checkpoint that it never covered, which no rollback to it restores, each with a `reason`: `transmitted` (data a `send` delivered, §4.4.2), `delegated` (a change a delegate made, §5.15.4), `outside_scope` (any other change outside what the checkpoint captured), or an `x-` reason. They do not make `restored` false |
| `changes_reverted` | What the rollback undid: each `item`, with the `operation` it undid (`create`, `modify`, `delete` or `other`) |
| `verification` | The `digest` of the restored content, computed as the checkpoint's was, and whether it `match`es the checkpoint's `digest` |

A host MUST NOT report `restored: true` for a rollback it did not complete,
and SHOULD list in `unrestored` and `not_covered` what it knows of: a host
that performed `send` steps of the run after the checkpoint lists each
transmission (§4.4.2), and only the run's own. An item holds no secret
(§6.7). An `x-` reason is the letters `x-`, then a lowercase letter or
digit, then at most 61 lowercase letters, digits, `_`, `.` or `-`.

**What a rollback does not restore.** The record of what happened is never
within a rollback's reach: the run's stores, trace, action records and
approval decisions, evidence and audit records (§6.4), the conversation or
transcript of the agents involved, including what a model was told and what
it answered, and the host's own records of what it did and may do: its
audit log, its checkpoint and approval state (a used checkpoint stays used),
its idempotency keys (§4.4.2) and its saved runs (§5.19.4). A rollback
changes the world back; it does not change the account of it. A host whose
checkpoint would otherwise capture one of these (a file under the directory
the checkpoint copies) leaves it out of the checkpoint, and a rollback
neither overwrites nor removes it. Data `persist` wrote (§4.5) is restored
only when the checkpoint captured it.

**At run time.** A `rollback` step completes whether or not `restored` is
true: its output says what happened, and the workflow decides what follows,
with an after-gate that stops or a failure mode whose `when` escalates
(§12.5, *Checked Rollback*). A `rollback` step in a workflow that targets 1.2
or later whose `restored` no `condition`, gate `when` or failure-mode `when`
of the workflow reads is W624 (`UNCHECKED_ROLLBACK`): a rollback that did not
restore would go unnoticed. A host that cannot perform a `rollback` step at
all answers with an `Error` (§5.19.1). The executor's own rollbacks (a gate's
or a failure mode's `rollback`, §5.6, §5.12) are `Rollback` actions: the host
answers `RolledBack` only when everything the checkpoint captured is
restored, and otherwise an `Error`, and the run ends F503. `RolledBack` may
list `not_covered` (§5.19.1).
```

### 2.5 §4.4.2 Transmissions *(new)*

```markdown
#### 4.4.2 Transmissions

`send` delivers data to a recipient outside the run, and once delivered it
cannot be recalled. The checkpoint `send` requires (§4.3) is the restore
point for the agent's own state, which the run goes on changing around the
transmission: it records the intent and the local state before it, and is
not an undo of it. A rollback to it lists each transmission made since in
`not_covered`, reason `transmitted` (§4.4.1). What keeps a transmission safe
is what happens before it: the policy check (`constrain`, §4.3), an approval
that shows the destination and the payload (§5.14), the destination policy,
and performing it at most once.

**At most once per approval.** Every `InvokeCapability` action carries an
`idempotency_key` (§5.19.1): `<run_id>:<n>`, where `<n>` is the `id` of the
pass's first `InvokeCapability`. It is therefore the same for every attempt
of one pass (its retries, §5.2, and the action a restored run issues again,
§5.19.4), and different for every other pass of every step of the run,
nested runs included. A `delegate` attempt that names the delegation it
`replaces` (§5.13) asks for a new delegation, and its key is built from its
own `id`. A host MUST NOT transmit twice for one key. Given an attempt whose
key it has already transmitted under, it answers with the output of that
transmission instead of transmitting again. Where it cannot tell whether an
earlier attempt under the key transmitted, and the destination does not
de-duplicate by the key, it does not transmit and answers an `Error` with
reason `outcome_unknown` (R402). A host SHOULD pass the key to a destination
whose protocol accepts one (an `Idempotency-Key` header, a message
de-duplication id). One approval therefore authorises at most one
transmission: the attempts of a pass share its decision and its key. A host
SHOULD apply the same rule to every other capability whose effective
`mutation` is true, except a delegation that names one it `replaces`.

A key is unique only while `run_id` is. A host that keeps keys across runs
or across its own restarts MUST NOT reuse a `run_id` (§5.19.2). The inputs
of a pass do not change between its attempts, so a host MUST NOT answer an
attempt with the output kept under its key when the attempt's capability or
inputs differ from those the key was first used with: it does not act, and
answers an `Error` with reason `key_conflict` (R402). Since a restored run
issues its pending attempt again (§5.19.4), a host that saves runs keeps the
keys it acted under at least as long as it keeps the runs.

**Compensation.** A host that knows how a transmission's effect can be
compensated (a message recalled, an order cancelled) MAY report it as
`compensation` in the output, in the form of `world_state_schema.yaml`'s
`TransitionRule.rollback`: a `strategy` and its `inverse_effects`. Nothing
performs it automatically, a rollback included. A workflow that compensates
does so in a step of its own, such as a `send` to the cancelling endpoint,
with its own checkpoint and approval.

**Destination policy.** A destination policy is a list of destination
patterns. A pattern is a non-empty string of one of three forms, compared
with a destination by code point, without case folding or Unicode
normalisation:

- with no `*`: it matches a destination equal to it;
- `<prefix>*`, where the last character of `<prefix>` is `/`, `:`, `@`, `.`,
  `?` or `#`, and where, if `<prefix>` contains `//`, a `/`, `?` or `#`
  occurs after its first `//` (so that the authority it names is complete):
  it matches a destination that starts with `<prefix>`;
- `*<suffix>`, where `<suffix>` has at least two characters and starts with
  `@` or `.`: it matches a destination that ends with `<suffix>` and whose
  part before `<suffix>` is non-empty and consists only of ASCII letters,
  digits, `.`, `-`, `_` and `+`.

Any other pattern (an empty one, `*` alone, a `*` elsewhere or twice, a
prefix that ends otherwise or stops inside an authority, such as
`https://hooks.example.com:*` or `https://hooks.example.*`) is invalid, and
a policy that holds one MUST be refused when it is loaded. A policy allows a
destination when one of its patterns matches it; an empty policy allows
none. A send is allowed when every policy in force allows its destination.
The vectors in `tests/conformance/destinations/match.json` are normative.

The suffix form names host or domain suffixes (`*.example.com`) and address
domains (`*@example.com`), not URLs: `https://evil.net/?.example.com` and
`a@evil.net,b@example.com` match neither. To allow URLs, use the prefix
form with a complete authority (`https://hooks.example.com/*`).

The policies in force for a run are those its host gives the executor when it
starts the run (§5.19.2) and the `allowed_destinations` of each domain
profile applied to the run (§5.21.3). The executor checks a `send` step,
whenever any policy is in force, once its inputs are resolved, before it asks
for approval or uses a checkpoint: a `destination` that is not a string, or
that a policy in force does not allow, fails the step with F504 and reason
`destination_not_allowed` (an executor refusal, not retried, §5.2). A safety
layer applies the policies in force for it to every `send` call, before
approval and the checkpoint (§5.18.10). A host whose own policy refuses a
send answers an `Error` with reason `destination_not_allowed`. With no
policy in force, the behaviour of 1.1 is kept: the destination is the
host's to check.

A destination policy is checked where the data leaves the run. A host SHOULD
also confine what a send can reach below the agent, with credentials scoped
to the allowed origins (a token only those services accept, an egress
allow-list), so that a send the check misses still fails.

**The destination in the approval.** The approver of a `send` SHOULD see
where the data goes. Without `shows`, the shown value is the step's inputs
(§5.14), which hold the destination. A `send` step in a workflow that targets
1.2 or later, whose `approval.shows` leaves out a destination given by
reference, is W625 (`DESTINATION_NOT_SHOWN`): each reference in `destination`
must be a `shows` reference, or have one whose root is the same and whose
path is a prefix of its path (`${request}` shows `${request.url}`). A literal
destination is part of the workflow the approver acts under and needs no
`shows` entry.
```

### 2.6 §4.5 Memory *(new, after §4.4)*

```markdown
### 4.5 Memory

`persist` stores data under a key, and `recall` reads it back. A host that
performs them follows these rules.

**Scope.** Both take an optional `scope`, which says who can read an entry
and how long it lasts:

| Scope | Visible to | Lasts until |
|-------|-----------|-------------|
| `run` | The run the host started (one `run_id`, §5.19.2) and every run nested in it (§5.13), whichever of them stored it | That run ends; a run that ended `deferred` keeps it until it is resumed and ends, or is cancelled (§5.14.1, §5.19.5) |
| `session` | Every run and agent the host groups into one session, such as a conversation or a thread | The session ends |
| `user` | Every session the host runs on behalf of one principal (§5.15) | The host's retention ends it |
| `project` | Every session the host serves for one project, such as a workspace or a repository | The host's retention ends it |
| `global` | Everything the host serves | The host's retention ends it |

A host MAY provide other scopes, named as `x-` reasons are (§4.4.1), and
states what each means. A literal `scope` that is none of these is W626
(`UNKNOWN_MEMORY_SCOPE`). Without `scope`, the host uses its default scope,
which it states; `session` is RECOMMENDED. An entry is visible only within
its scope: a `recall` in another session, for another principal or for
another project MUST NOT find it. Keys are compared by code point, and one
key in two scopes names two entries.

A host that does not provide the scope asked for neither stores nor looks
up: it answers an `Error` with reason `unsupported_scope` (R402). The output
of `persist` and of `recall` carries `scope`, the scope used. When a step
binds `scope` and it resolves to a value, the executor fails the step (R402,
reason `unsupported_scope`) unless the output's `scope` equals that value: a
host that does not know the input would use another scope without saying so.

**`stored: true`** asserts that the data is stored under the key in the
scope: from the time the `persist` step completes, a `recall` of that key in
that scope returns the data (`found: true`) until the entry ends. The data
round-trips as I-JSON (RFC 7493): a recall returns a value equal to the one
stored, object member order aside. When `key` is not bound, the host chooses
one and returns it as `key`. A `persist` to a key that holds an entry
replaces it. **`stored: false`** asserts that nothing changed: no entry was
written or replaced. The step completes either way, and a workflow that
depends on the write checks `stored` (§12.5). A host that refuses a write
SHOULD answer an `Error` instead, so that retries and failure modes apply;
when it refuses for size or capacity, the reason is `over_capacity` and the
message names the limit. Data or a key that holds a secret the host
recognises is refused, not stored (§6.7): the host answers an `Error` with
reason `secret_in_data`, and its message does not repeat the secret.

**Expiry.** `ttl` is a duration (§5.10.1) longer than zero. The entry ends
`ttl` after its `stored_at`, which the output reports as `expires_at`; from
then on a `recall` does not find it. A literal `ttl` outside the duration
grammar, or of zero, is W614. A host given a `ttl` it cannot parse, or that
cannot end entries, does not store: it answers an `Error` with reason
`unsupported_ttl` (R402). Without `ttl`, an entry lasts as long as its scope.

**`recall`.** `found` is `true` when a live entry has the key in the scope;
`data` is then its data, and `stored_at` (and `expires_at`, when it has one)
its times. Otherwise `found` is `false` and `data` is the step's `default`,
or null without one. `stored_at` is the name both capabilities use for the
time an entry was stored; `persist` also returns it as `timestamp`, which is
deprecated (a reference to it is W603).

**Ending entries.** This version defines no operation that deletes an entry.
An entry ends when it expires, when its scope ends, or under the host's
retention policy; once it has ended, a `recall` does not find it.

**What a host states.** A host that performs `persist` and `recall` states,
for each scope it provides, whether entries survive a restart of the host,
its retention policy, and its limits on the size of a value and the number
of entries. A host that states it implements this section passes the vectors
in `tests/conformance/memory/store.json` for the scopes it provides.
```

### 2.7 §5.15.4 Checkpoints Across a Delegation *(new, after S3's §5.15.3)*

```markdown
#### 5.15.4 Checkpoints Across a Delegation

A delegate is another party. What it changes is its own action, under its
own safety rules, not a step of the delegating run.

- **Authorisation.** A run's checkpoints authorise its own steps (§5.2.2),
  those of the runs it invokes included (§5.13), and never what a delegate
  does, except where a safety layer orders the delegate's calls in the
  delegator's scope (§5.18.5; last item below). Before each change, a
  delegate that changes anything MUST have a checkpoint valid in the scope
  where that change is checked: §5.2.2 when it runs a workflow, §5.18.6 on a
  tool-calling host. In a scope of its own, that is a checkpoint it takes;
  in a shared scope, one taken in that scope that no other change has used.
  A host that runs the delegate so attests it as `effective.checkpointed:
  true`. A checkpoint that a `delegate` step itself needs (its effective
  `requires_checkpoint`, as §5.15.2 raises it for a target that may change
  state) is the delegator's restore point, taken before it hands the change
  over.
- **Restoration.** A rollback restores what its checkpoint captured
  (§4.4.1), whoever changed it. It does not reach what a delegate changed
  outside that, and it neither recalls a delegation nor stops a delegate. A
  host that knows of such changes lists them in `not_covered`, reason
  `delegated`. Where a delegate works on state the delegator's checkpoint
  captured, such as a subagent in the same working tree, the rollback
  restores that state, the delegate's changes to it included.
- **All or nothing.** To keep a delegation from leaving changes no rollback
  reaches, bind `read_only: true` (§5.15), so that the delegate changes
  nothing, or undo its changes explicitly: a later step that asks the
  delegate to reverse them (a `delegate` step that `continues` the
  delegation, §5.15.3), or one that restores the system the delegate changed.
- **Tool-calling hosts.** A safety layer that orders a delegate's calls in
  the delegator's scope (§5.18.5) applies that scope's rules to both: a
  checkpoint taken in the scope authorises one change, whichever agent makes
  it, and the next change, by either agent, needs another checkpoint.
```

### 2.12 §12.1 When to Use Checkpoints — replace the decision tree and the examples table

````markdown
Use this decision tree:

```
Does the step change anything outside the run?
├── No → No checkpoint
└── Yes → Can a saved copy of what it changes be put back
          (a file, a record, a configuration)?
    ├── Yes → A checkpoint is REQUIRED before it: it is the restore point
    │         (`mutate`, or raise `requires_checkpoint`)
    └── No: it transmits (a message, a payment, a published event) →
              `send`: a checkpoint is still REQUIRED, but it restores only
              the agent's own state. Prevent a wrong transmission instead:
              `constrain` before it, an approval that shows the destination
              and the payload, a destination policy, and at most one
              transmission per approval (§4.4.2)
```

**Examples:**

| Operation | Checkpoint Required? | Reason |
|-----------|---------------------|--------|
| Read file contents | No | No mutation |
| Write to database | Yes | The checkpoint restores the rows it captured |
| Send HTTP GET | No | Read-only |
| HTTP POST that delivers a message or an order (`send`) | Yes, with approval | The checkpoint restores local state, not the delivery; the idempotency key keeps a retry from delivering twice (§4.4.2) |
| Rename file | Yes | May overwrite existing file |
| Append to log | Optional | Append-only, can ignore duplicate |
````

### 2.13 §12.5 Common Patterns — add two patterns after *Recovery Loop*

````markdown
**Pattern: Guarded Send**

A send whose destination comes from the request (declaring `approval@1`).
The host also enforces the list as a destination policy (§4.4.2), which fails
the step with F504 before anyone is asked; `constrain` records the check in
the run, and `shows` puts the destination in front of the approver.

```yaml
- capability: constrain
  purpose: Check the destination against the allowed destinations.
  input_bindings:
    target: ${request.destination}
    constraints:
      - allowed_destinations: ["https://hooks.example.com/*", "*@example.com"]
    action_on_violation: block
  store_as: policy_out
- capability: checkpoint
  purpose: Save a restore point for the agent's own state.
  input_bindings:
    scope: report_state
  store_as: checkpoint_out
- capability: send
  purpose: Deliver the report.
  input_bindings:
    destination: ${request.destination}
    payload: "${report_out.content: object}"
  gates:
    - when: ${policy_out.compliant} == false
      action: stop
      message: The destination is not allowed.
  approval:
    approver: {kind: human, role: ops}
    shows: ["${request.destination}", "${report_out.content}"]
  store_as: send_out
```

**Pattern: Checked Rollback**

A rollback reports whether it restored everything (§4.4.1); the step
completes either way, so the workflow checks.

```yaml
- capability: rollback
  purpose: Restore the configuration.
  input_bindings:
    checkpoint_id: ${checkpoint_out.checkpoint_id}
  gates:
    - when: ${rollback_out.restored} == false
      phase: after
      action: stop
      message: The rollback did not restore everything; see unrestored.
  store_as: rollback_out
```

To call a person instead of stopping, use a failure mode whose `when` is the
same expression and whose action escalates to a handler (§5.12).
````

### 5.1 Rust core

**`core/src/destination.rs` (new; `pub mod destination;` in `lib.rs`)**

The API agreed with S6 (whose profile loader calls `Policy::parse` and
whose `Policy::destinations()` returns `Vec<Vec<String>>`):

```rust
//! Destination policies (STANDARD v1.2 §4.4.2).
#[derive(Debug, Clone, PartialEq, Eq)]
pub enum Pattern { Exact(String), Prefix(String), Suffix(String) }
#[derive(Debug, Clone, Default)]
pub struct Policy { patterns: Vec<Pattern> }
impl Policy {
    /// Every pattern checked; Err lists (index, message) for each invalid one
    /// (S6 reports each as S303 at `allowed_destinations[i]`).
    pub fn parse<S: AsRef<str>>(patterns: &[S]) -> Result<Policy, Vec<(usize, String)>>;
    pub fn allows(&self, destination: &str) -> bool;
}
pub fn check_pattern(p: &str) -> Result<Pattern, String>;
pub fn check_policies(policies: &[Vec<String>]) -> Result<(), String>;  // first error, "policy i, pattern j: …"
/// Every policy allows the destination. An invalid pattern matches nothing
/// (fail closed); callers have refused invalid policies when loading them.
pub fn allowed(policies: &[Vec<String>], destination: &str) -> bool;
```

- `check_pattern`: empty → Err; no `*` → `Exact`; more than one `*` → Err;
  ends with `*`: prefix = all but the last char, non-empty, last char in
  `/:@.?#`, and, if `prefix.find("//")` is `Some(i)`,
  `prefix[i + 2..].contains(['/', '?', '#'])` (else Err "the prefix starts
  an authority it does not finish: put '/', '?' or '#' after the host, as in
  https://hooks.example.com/*") → `Prefix`; starts with `*`: suffix = the
  rest, at least 2 chars, first char `@` or `.` → `Suffix`; otherwise Err.
  Messages say which form was expected.
- Matching: `Exact` `==`; `Prefix` `destination.starts_with(prefix)`;
  `Suffix`: `destination.len() > suffix.len() &&
  destination.ends_with(suffix) &&
  destination[..destination.len() - suffix.len()].bytes().all(|b|
  b.is_ascii_alphanumeric() || matches!(b, b'.' | b'-' | b'_' | b'+'))`
  (the slice is at a char boundary because `suffix` is a whole `str`; str
  comparison is byte-wise on UTF-8, i.e. by code point; no normalisation).
- `allowed`: `policies.iter().all(|p| p.iter().any(|pat|
  check_pattern(pat).is_ok_and(|q| q.matches(d))))` (an empty slice of
  policies → true; an empty policy → false).
- Unit test `vectors()` reads
  `include_str!("../../tests/conformance/destinations/match.json")`, asserts
  the text `is_ascii()` (the NFD case stays an escape), and checks every
  entry through both `check_pattern`/`allowed` and `Policy::parse`/`allows`.

```python
@dataclass(frozen=True, slots=True)
class Capture:
    checkpoint_id: str
    mechanism: str               # "file_copy"
    captured: list[str]          # root-relative POSIX paths
    excluded: list[str]
    digest: str                  # "sha256:<hex>"
    taken_at: datetime
    expires_at: datetime | None
    size: int
    def output(self) -> dict[str, Any]   # the checkpoint capability's output fields

@dataclass(frozen=True, slots=True)
class Restore:
    restored: bool
    unrestored: list[dict[str, str]]
    changes_reverted: list[dict[str, str]]
    verification: dict[str, Any]          # {"digest", "match"}
    def output(self, not_covered: list[dict[str, str]] = ()) -> dict[str, Any]

ALWAYS_EXCLUDED: tuple[str, ...] = (".claude/**",)   # the plugin's audit log and checkpoint marker
SECRET_PATHS: tuple[str, ...] = (                     # informative defaults (S4's §6.7)
    ".env", ".env.*", "**/.env", "**/.env.*", "*.pem", "**/*.pem", "*.key", "**/*.key",
    "*.p12", "**/*.p12", "*.pfx", "**/*.pfx", "**/id_rsa*", "**/id_ecdsa*", "**/id_ed25519*",
    "**/.ssh/**", "**/.netrc", "**/.npmrc", "**/.pypirc", "**/.git-credentials",
    "**/.aws/credentials", "**/.docker/config.json",
)
DEFAULT_EXCLUDE: tuple[str, ...] = (".git/**", *SECRET_PATHS)

class FileSnapshotStore:
    def __init__(self, root: str | Path, store_dir: str | Path, *,
                 exclude: Sequence[str] = DEFAULT_EXCLUDE,
                 protected: Iterable[str | Path] = (),
                 max_file_bytes: int = 50 * 2**20,
                 retention: timedelta | None = None, clock: Callable[[], datetime] | None = None) -> None
    def protect(self, path: str | Path) -> None        # add a path no capture or restore touches; never removable
    @property
    def protected(self) -> frozenset[str]              # root-relative POSIX paths ("" prefix = outside root, ignored)
    def capture(self, checkpoint_id: str, scope: Sequence[str]) -> Capture
    def restore(self, checkpoint_id: str, scope: Sequence[str] | None = None) -> Restore
    def discard(self, checkpoint_id: str) -> None
```

- **Never within reach** (§4.4.1): `ALWAYS_EXCLUDED`, `store_dir`, and every
  `protected` path (a file, or a directory and everything under it) are
  skipped by `capture` and by every part of `restore` (never overwritten,
  never unlinked as "created since"). The set only grows: `protect()` adds,
  nothing removes; `exclude` (a caller may replace the default) is applied
  on top of it, never instead of it. Who registers: `CheckpointTracker`
  registers its `checkpoint_dir` (tracker state, archive) and its
  `marker_dir`; `Host` registers its `memory.path`, its `idempotency.path`
  and each of its `protected_paths` (where it saves runs); the adapter
  registers `config.audit_log_path`. Paths outside `root` need no
  protection and are ignored.
- **Private copies:** `store_dir`, `objects/` and `manifests/` are created
  with mode 0o700 (and `os.chmod` to 0o700 when they exist with wider
  bits); objects and manifests are written through
  `os.open(tmp, O_WRONLY | O_CREAT | O_EXCL | O_NOFOLLOW, 0o600)` then
  `os.replace`, so a 0600 key file in scope never becomes a readable copy.
  A restored file gets the mode its manifest entry recorded.
- `capture`: walk `root` with `os.walk(followlinks=False)`, pruning the
  never-within-reach paths; a regular file whose root-relative POSIX path
  matches a `scope` pattern (`fnmatch`; `*` matches all) is copied into
  `store_dir/objects/<sha256>` (written once, atomically, 0600) and recorded
  in the manifest `{path: {sha256, mode, size}}`; a matching file over
  `max_file_bytes`, or matching `exclude`, goes to `excluded` by path; each
  never-within-reach directory the scope covers goes to `excluded` once, as
  `"<dir>/"` (its files are not listed); symlinks are recorded as excluded
  (not followed). The manifest (`store_dir/manifests/<id>.json`, atomic
  write, 0600, with the scope patterns, the `excluded` list and `taken_at`)
  and `digest` = SHA-256 of the sorted lines `"<path>\0<sha256>\n"`.
  `checkpoint_id` must match `^[A-Za-z0-9_.:-]{1,128}$` (no path tricks).
- `restore`: missing manifest → `Restore(False, [{"item": "*", "reason": "discarded"}], [], {})`;
  **not captured** (§4.4.1): each entry of the restore `scope` is checked
  first: an entry that matches a path in the manifest's `excluded` list, or
  a never-within-reach path, or that matches no manifest path and (for an
  entry with no glob character) is not covered by the manifest's scope
  patterns → `{"item": <entry>, "reason": "not_captured"}` in
  `unrestored`; (a literal path the checkpoint's scope covered but that did
  not exist then is captured as absent: restoring it removes it); then for
  each manifest entry within the restore scope: a path whose parent
  resolves outside `root` (symlinked directory) → `failed`; an object missing →
  `discarded`; content differs or file missing → write the object atomically
  (`os.replace`), set mode, record `modify` (or `delete` when it was missing);
  then every regular file under `root` matching the manifest's scope patterns
  (and the restore scope), not excluded, not never-within-reach and not in
  the manifest → unlink, record `create`; an `OSError` → `failed`. Recompute
  the digest over the manifest paths: `verification = {"digest", "match"}`.
  `restored = not unrestored`.
- `discard`: remove the manifest; objects no manifest refers to are removed
  (`gc()` helper).

```python
class IdempotencyLog:
    """At most one effect per idempotency key (STANDARD v1.2 §4.4.2).

    Keys are unique only while run_ids are (§5.19.2). Without a path the log
    is in memory and its keys do not survive a restart: a host that saves
    runs (§5.19.4) must give it a path.
    """
    def __init__(self, path: str | Path | None = None, clock: Callable[[], int] | None = None,
                 redactor: Redactor = DEFAULT_REDACTOR) -> None
    @property
    def path(self) -> Path | None
    @property
    def durable(self) -> bool                     # path is not None
    def perform(self, action: Mapping[str, Any], effect: Callable[[], dict[str, Any]]) -> dict[str, Any]
    def performed_since(self, since_ms: int, *, run_id: str, capability: str | None = "send") -> list[dict[str, Any]]
```

- Each entry: `{key, capability, inputs_sha256, state: "started" | "done",
  at, destination?, value?}`, where `inputs_sha256` =
  `hashlib.sha256(_core.canonical_json(action["inputs"]).encode()).hexdigest()`
  (RFC 8785, S1's `_core.canonical_json`) and `destination` is the action's
  `inputs.destination` passed through `redactor.redact_text` (the log is a
  host record: no secret in it, §6.7).
- `perform`: no `idempotency_key` on the action → `effect()`. An entry under
  the key whose `capability` or `inputs_sha256` differs from the action's →
  `{"kind": "Error", "code": "R402", "reason": "key_conflict", "message":
  "idempotency key '<k>' was first used for another <capability> request,
  so a run_id was reused; nothing was done (STANDARD §4.4.2, §5.19.2)"}`
  (never a replay). A matching `done` entry → `{"kind": "Output", "value":
  <stored value>}`. A matching `started` entry → `{"kind": "Error", "code":
  "R402", "reason": "outcome_unknown", "message": …}`. Otherwise record
  `started` and persist it *before* calling `effect()`; an `Output` → record
  `done` with the value; an `Error` → remove the entry (contract: `effect`
  returns `Error` only when nothing took effect, and raises otherwise); an
  exception leaves `started` (outcome unknown) and propagates.
- A delegation that names `replaces` is passed straight to `effect()`.
- With `path`: one JSON Lines file, appended with `O_APPEND` and fsync per
  entry, 0600, loaded with `O_NOFOLLOW` and a size cap (the tracker's
  pattern); the last entry per key wins.
- `performed_since(since_ms, run_id=…)` lists the `done` entries since a
  time whose key starts with `f"{run_id}:"` (the run's own; nested runs share
  the `run_id`), for `not_covered`.

### 5.4 Skills (informative bodies; S1 edits the frontmatter hooks of `send` and `rollback`)

- `skills/checkpoint/SKILL.md`: Procedure step 2 lists mechanisms by kind
  (`vcs_snapshot`, `file_copy`, `store_snapshot`, `savepoint`, provider
  snapshot) without a default directory. Step 3's git form (`vcs_snapshot`),
  each a separate plain Bash call, because S1's classifier counts exactly
  the plain `git stash create` command as `checkpoint` and gates any line
  with `$(` as `mutate`:
  1. `git stash create "checkpoint:<id>"` — saves the tracked state
     (worktree and index) as an unreferenced stash commit and prints its
     sha, leaving the working tree unchanged. **An empty output means a
     clean tree** (verified: it prints nothing, and `git stash store` would
     fail with "Cannot update refs/stash"); then
  2. `git rev-parse HEAD` (read-only) — the restore point is `HEAD`. The
     skill records `restore_point` (the sha) and `restore_kind`
     (`stash` or `head`); in shell terms, `sha=${sha:-$(git rev-parse HEAD)}`.
  3. `git ls-files --others --exclude-standard -- <paths>` (read-only) —
     untracked files in scope, which `git stash create` does not capture:
     listed in `excluded` (or copied with `file_copy`, a gated call of its
     own); ignored files are outside the checkpoint and the skill says so.
  The skill does **not** run `git stash store` or `git update-ref`: either
  names a commit the caller chooses (S1 counts neither as a checkpoint), and
  as a gated `mutate` it would use up the marker the `create` just wrote.
  Retention: the stash commit is kept by git until `gc.pruneExpire` (two
  weeks by default); no `expires_at` is reported for it. "Store checkpoint
  metadata in `.checkpoints/`" becomes "Keep checkpoint content where the
  host keeps it (outside the files in scope)". Output Contract:
  `mechanism`, `captured`, `excluded`, `digest`, `expires_at` (ontology
  names); `restore_command`, `pre_mutation_state.summary` kept as
  skill-level aids; `scope` object and `type` renamed. Validity vs
  retention sentence (§4.4.1). The worked examples use a clean tree and a
  dirty one.
- `skills/rollback/SKILL.md`: restore by mechanism. Git form (each step a
  separate call; the restore is one compound line, a gated `mutate` under
  S1, which in the plugin needs its own fresh checkpoint and approval: it
  overwrites the current state):
  1. Read-only: `git diff --name-status <sha> -- <paths>` (tracked changes
     since, for `changes_reverted`); `git ls-files --others
     --exclude-standard -- <paths>` (untracked files now). Files **created
     since** = untracked now − the checkpoint's `excluded` list; untracked
     files that were in `excluded` were never captured.
  2. Restore, for `restore_kind: stash`: `git restore --source=<sha>
     --worktree -- <paths> && git restore --source=<sha>^2 --staged --
     <paths>` (worktree from the stash commit, index from its index parent;
     tracked files added since are removed, files deleted since come back;
     verified); for `restore_kind: head`: `git restore --source=<sha>
     --staged --worktree -- <paths>`. Then, only when the created-since list
     is non-empty, `rm -f -- <created paths>` in the same line (never `git
     clean` with an empty path list, which removes every untracked file).
     `git stash apply <sha>` is not used: it aborts with "Your local changes
     would be overwritten" once a file it touches changed since the
     checkpoint (verified), the usual case for a rollback.
  3. Read-only verification: `git diff --quiet <sha> -- <paths>` and the
     untracked list again → `verification`.
  Report: `unrestored` lists each path the restore failed for (`failed`),
  each created-since file not removed (`failed`), and each item the
  rollback's `scope` names that the checkpoint did not capture, untracked
  files in `excluded` included (`not_captured`); `not_covered` lists
  changes to excluded files when no scope named them (`outside_scope`) and,
  when `HEAD` moved since the checkpoint, `{item: "HEAD", reason:
  outside_scope, detail: "commits made since are not undone"}`. Files form:
  copy back, remove files created in scope since. Output Contract uses
  `unrestored`, `not_covered`, `changes_reverted` (`item`, `operation`),
  `verification` (`digest`, `match`); "`restored` is true only if …; the
  step completes either way: say so, and list what was not restored"; the
  record of what happened (including `.claude/` and the host's state) is
  never rolled back; a transmission is reported `transmitted`.
- `skills/send/SKILL.md`: step 2 "the checkpoint restores the agent's own
  state, not the transmission (§4.4.2)"; step 3 "Validate destination"
  references the destination policy (enforced by code where one is in force)
  and the `constrain` step (§12.5 Guarded Send), replacing "allowlist";
  step 6 "Retry" → "a retry carries the same idempotency key; never transmit

- `skills/persist/SKILL.md`: inputs table gains `scope`; procedure writes an
  entry `{key, scope, data, stored_at, expires_at}` exactly (a JSON record in
  the scope's store: `project` a file the project keeps, `session` the

## 9. RFC-0009 (full text of `spec/RFC-0009-checkpoint-rollback-send-memory.md`)

````markdown
# RFC-0009: Checkpoint, rollback, send and memory

**Status:** Accepted
**Target:** Standard v1.2.0
**Date:** 2026-11-15

## Summary

This RFC defines what a checkpoint holds and what a rollback restores, what
a transmission's checkpoint can and cannot do, how a delegation relates to
the delegator's checkpoints, and what a memory store guarantees. It settles
findings ACS-18, ACS-19, ACS-26, ACS-27, ACS-48 and ACS-52 of the Standard
Agents interoperability review in Standard 1.2.0 (§4.4.1, §4.4.2, §4.5,
§5.15.4) and capability ontology 2.2.0. It was accepted by the maintainer's
instruction that every remaining finding be implemented in 1.2.0, and is
implemented in the same change: the reference validator and executor, the
Python package, the Standard Agents binding, the skills and conformance
fixtures and vectors.

## Motivation

Standard 1.1 required a checkpoint before `mutate`, `send` and `rollback`
without saying what a checkpoint saves. The ontology's `rollback` returns a
required `restored`, which the Standard never mentioned, and a rollback step
that returned `restored: false` completed with no diagnostic. The skills
assumed git and a `.checkpoints/` directory, and the Python tracker stored
metadata and no content.

For `send`, restoring the checkpoint does nothing to data already delivered,
and nothing said so; §12.1 implied the opposite. The reference executor
retried a `send` after R401 with identical inputs under one approval, and the
host had nothing to tell the second attempt from a new transmission. The send
skill told the model to check an allow-list that no schema or setting
defined.

Across a delegation, nothing related the delegator's checkpoints or rollback
to what a delegate changes, so each binding decided alone.

`persist` and `recall` had no storage scope, `ttl` had no grammar (strict
validation accepted "five fortnights"), the two capabilities named the
storage time differently, and nothing said what `stored: true` guarantees.

## Goals

- Define a checkpoint, a rollback, `restored`, and what lies outside a
  rollback's reach, host-neutrally.
- Make a transmission safe where it can be: before it, and at most once per
  approval, with a defined way to report it after a rollback.
- Relate delegation to checkpoints and rollback.
- Give memory a scope, an expiry grammar, and testable guarantees.
- Define a destination policy with one grammar, normative vectors and a
  diagnostic, applied by executors, safety layers and profiles.
- Change no 1.1 workflow's validity or behaviour except by opt-in or a new
  warning.

## Non-goals

- Making `restored: false` or `stored: false` fail a step (a later major may;
  see Open questions).
- A delete operation for memory.
- How a host captures or restores state; the Standard defines the contract
  and the report, the host the mechanism.
- URL-aware destination matching (origins, case-insensitive hosts).
- How a domain profile is selected and applied in general (RFC-0010); this
  RFC defines only `allowed_destinations` and what it puts in force.
- Concurrency of conflicting steps across runs (RFC-0007, ACS-16).

## Key decisions

### 1) A checkpoint is the host's copy of the state within a scope

The `checkpoint` step's `scope` names what to capture in the host's naming;
an executor-requested checkpoint covers what the step may change, as far as
the host can tell. Optional outputs report `mechanism`, `captured`,
`excluded`, `digest` and `expires_at`. Retention (what can be restored) is
separate from validity (what is authorised), so a used checkpoint can still
be restored (§4.4.1).

### 2) `restored` and two lists

`restored: true` asserts that everything the rollback concerns is back;
`unrestored` (reasons `failed`, `conflict`, `discarded`, `not_captured`) is
then empty. An item the rollback's own `scope` names that the checkpoint
never captured is `not_captured`, so asking to restore what was never saved
is not a success. `not_covered` (reasons `transmitted`, `delegated`,
`outside_scope`) lists changes the checkpoint never covered and does not
affect `restored`. The executor's `RolledBack` may carry `not_covered`; an
in-scope failure is an `Error`, and the run ends F503 as in 1.1.

### 3) A rollback step completes; the workflow checks

`restored: false` is not F503: changing that would alter 1.1 runs, and F503
cannot be matched by `on_error`. §12.5 shows the check (a gate or an
escalating failure mode), and W624 reports an unchecked rollback in a
workflow that targets 1.2.

### 4) The record of what happened is outside a rollback's reach

Stores, trace, action records, approvals, evidence, audit records and the
transcript are never restored, nor the host's own records: its audit log,
checkpoint and approval state, idempotency keys and saved runs. A checkpoint
leaves them out even when its scope covers them, so a rollback can neither
erase the tail of an audit log, nor bring back a used checkpoint, nor let a
send go twice. Memory is restored only when a checkpoint captured it.

### 5) A transmission's checkpoint restores the agent's own state

§3.3, §4.4.2 and §12.1 say so; a rollback lists transmissions as
`not_covered`, `transmitted`; a `compensation` in the form of
`TransitionRule.rollback` may be reported, and is performed only by an
explicit step.

### 6) At most one effect per approval: an executor-issued idempotency key

Every `InvokeCapability` carries `idempotency_key` = `<run_id>:<n>`, `n` the
`id` of the pass's first `InvokeCapability`: one key per pass, kept across
retries and restores, new for loops, invoked runs and replacing delegations.
A host MUST NOT transmit twice per key; when unsure, it answers `Error`
reason `outcome_unknown`. Keys are unique because `run_id` is (§5.19.2, a
MUST for a host that keeps records or keys); a host never replays a key
whose capability or inputs differ from the first use (`key_conflict`), and
a host that saves runs keeps its keys as long. A pending action restored
from a version-1 state gets `<run_id>:<id>`.

### 7) Delegation

A run's checkpoints never authorise a delegate's changes, except where a
safety layer orders the delegate's calls in the delegator's scope; before
each change a delegate needs a checkpoint valid in the scope where that
change is checked (its own, or in a shared scope one no other change has
used), and its host may attest it (`effective.checkpointed`); a rollback
restores what its checkpoint captured, whoever changed it, and reaches
nothing else; all-or-nothing needs `read_only: true` or an explicit undo
step (§5.15.4).

### 8) Memory scopes, `ttl`, guarantees

`run` (the run the host started and every run nested in it), `session`,
`user`, `project`, `global` and `x-` names, defined by visibility and
lifetime, echoed in the output and enforced by the executor when a step
binds a scope. `ttl` is a §5.10.1 duration (W614 otherwise). `stored: true`
means read-after-write and an I-JSON round trip; `stored: false` means
nothing changed. Data holding a secret the host recognises is refused
(`secret_in_data`, §6.7). `stored_at` is the shared name; `persist`'s
`timestamp` is deprecated (W603). Hosts state durability, retention and
limits and pass the memory vectors (§4.5).

### 9) Destination policy

Patterns of three forms (exact; `<prefix>*` after a delimiter, with a
complete authority when the prefix holds `//`; `*<suffix>` from `@` or `.`,
preceded only by host-name or local-part characters), normative vectors
including every known bypass, intersection of the policies in force (the
host's at start plus each applied profile's `allowed_destinations`). The
executor fails a disallowed `send` with F504 before approval or checkpoint
whenever a policy is in force; safety layers refuse calls with F504, and
the TypeScript binding applies a layer-wide policy to every `send` tool;
W625 reports a 1.2 `send` whose approval hides a referenced destination;
credentials scoped to allowed origins are recommended.

## Backward compatibility

Every ontology and canonical schema change is an optional field or a
description (§11.4). The executor's behaviour for a 1.1 workflow is unchanged
unless a host opts in: a host that gives destination policies, or a step that
binds the new `scope` input (a key that was W604 in 1.1). W624 and W625 apply
only to workflows that target 1.2; W626 and the new W614 and W603 cases apply
to all versions and hit nothing in the repository. New host duties
(at-most-once per key and no replay under a reused key, memory guarantees
and the refusal of secrets, a delegate's checkpoint in the scope its change
is checked in, a checkpoint that never captures the host's own records)
are MINOR: they constrain hosts, not workflows. A destination policy
applies only when a host or an applied profile supplies one; the tightened
pattern grammar is new in 1.2, so no existing policy changes meaning. No repository catalog needs
migrating; the edits that would clear W624 if a catalog moved to 1.2 are
listed in the design.

## Conformance test updates

- Runtime fixtures (normative for class EX): one key across a retry, a new
  key per loop and per replacing delegation, `outcome_unknown`, destination
  refusals (F504, before approval and checkpoint; policy intersection; a
  profile policy with no host policy; a URL against a suffix pattern;
  `on_error: F504`), rollback steps that do not restore (complete; checked
  by a gate), `RolledBack` with `not_covered` (transmitted, delegated),
  memory scope echo and its absence, `stored: false`.
- Validator fixtures for W624, W625, W626, the W614 `ttl` case and the W603
  `timestamp` case, and their exemptions.
- `tests/conformance/destinations/match.json` (normative for any destination
  policy) and `tests/conformance/memory/store.json` (normative for a host that
  states it implements §4.5), run by the Rust core, the Python package and
  the TypeScript binding.
- Unit tests for the snapshot store (a rollback leaves the audit log, the
  tracker state, the marker, the idempotency log and saved runs
  byte-identical; secret paths excluded; private modes; `not_captured`),
  the idempotency log (`key_conflict`, durability, the run's own keys), the
  memory store (`secret_in_data`), the Python host's defaults, the
  executor's version-1 restore, the adapter's shared-scope checkpoint and
  destination checks, and the binding's layer-wide destination policy.

## Alternatives considered

- **`restored: false` as F503**, always or for `spec_version: "1.2"`:
  rejected (1.1 runs would change; the executor cannot rely on a header; F503
  is not matchable by `on_error`). **A `require_restored` input**: rejected
  as unnecessary; a gate is the existing mechanism, and W624 makes the
  omission visible.
- **One `unrestored` list with mixed reasons**: rejected; two lists keep
  `restored` ⇔ `unrestored` empty.
- **An author-supplied `send.idempotency_key` input** as the fix: rejected;
  it helps only when bound and a workflow cannot name its run or pass. **A
  key from run, frame and step**: repeats across loops and invocations. **A
  pass counter**: would oblige every executor to count passes alike; the
  first action's `id` is already normative.
- **Automatic compensation on rollback**: rejected; a compensation is a
  transmission needing its own checks.
- **"A delegator's checkpoint never covers a delegate's effects"** as a flat
  rule: false for a subagent in the same working tree; stated instead in
  terms of what the checkpoint captured. **Requiring
  `effective.checkpointed`**: deferred.
- **Scope as a closed enum**: cannot admit `x-` names; the dialect has no
  `pattern`. **Renaming `timestamp`**: breaking; aliased and deprecated.
- **Profiles as the only source of a destination policy**: a host without a
  profile needs one too. **Glob patterns**: `*` anywhere lets
  `https://*.example.com/*` match another host. **Unrestricted suffix and
  prefix forms** (this RFC's first draft): a suffix matched any string
  ending with it (`https://evil.net/?.example.com`,
  `a@evil.net,b@example.com`) and a prefix could stop inside an authority
  (`https://hooks.example.com:*` allowed userinfo to another host); both
  restricted. **A per-tool policy in TypeScript**: a tool defined without it
  escaped; a layer-wide policy instead. **W625 for every version**: would
  hit a contributed 1.1 fixture kept as sent.
- **Recording a git checkpoint with `git update-ref` and counting it as a
  checkpoint**: it names any commit the caller chooses, as `git stash
  store` does, and would use up the marker of the `git stash create` before
  it; the one plain `git stash create`, with `HEAD` on a clean tree, is the
  checkpoint.
- **A reused key answered `outcome_unknown`**: the host knows the key was
  reused, and the remedy differs; `key_conflict`.
- **Keying the `run` memory scope by frame instance**: the protocol does not
  identify frame instances, and a nested run is part of its parent's work.

## Open questions

1. Should a future major release make `restored: false` (and `stored:
   false`) fail the step, retiring W624?
2. Should `send` take an author-supplied idempotency key for
   de-duplication across runs (the same invoice never sent twice by two
   runs)?
3. Should a workflow or profile be able to require
   `effective.checkpointed: true` of a delegation, as quorum's
   `require_read_only` requires `read_only`?
4. Should memory gain a delete operation, or is expiry with retention
   enough?
5. Should destination patterns gain URL-aware matching (scheme and host
   normalisation, ports, internationalised names)? The 1.2 forms are
   deliberately ASCII and fail closed: an internationalised host must be
   written in its ASCII (punycode) form, and an address whose local part
   uses characters outside letters, digits, `.`, `-`, `_` and `+` needs an
   exact pattern.
6. Should the Standard say how a version-control checkpoint is kept for its
   retention (a ref the host pins outside the agent's commands), or is the
   tool's own pruning, reported as `expires_at` when known, enough?
````

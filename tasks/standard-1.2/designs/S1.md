Summary of the shape:

- A new §5.18 "Tool-Calling Hosts" states every rule a **safety layer** applies
  to calls: tool bindings, unbound tools, classification by effect,
  composite tools, scope and concurrency, checkpoints, approval, refusals and
  records, fail-closed loading, text-only results and per-capability checks.
- A new §5.2.2 states the checkpoint-use rules for steps (the reference
  executor's existing behaviour), so steps and calls follow one rule.
- A new conformance class **SL** (§10.4), separate from validator levels
  L1–L4, with normative binding fixtures and call-sequence fixtures run by the
  Python adapter and the Standard Agents binding.
- One host-neutral record, `schemas/interop/tool_binding.schema.json`; the SDK
  metadata and the Standard Agents `acs` annotation become carriers of it.
- Five new codes: V110, V111, F506, R407, W617. Everything else reuses
  existing codes (V101, V102, V105, V107, V109, S303, S304, R402, F501–F504,
  W601, W602).
- No workflow that is valid under 1.1 becomes invalid, and no 1.1 workflow
  runs differently on the reference executor: nothing in this design changes
  the validator or the executor. The ontology does not change.

## 1. Per-finding decisions

### ACS-01 — No normative rules for a safety layer over tool calls

**Decision.** Add §5.18 (Tool-Calling Hosts) to the Standard, the §2 terms
*tool-calling host*, *call*, *tool binding*, *safety layer*, *scope* and
*execution boundary*, and a conformance class SL (§10.4) whose statement
names the calls the layer covers. Answer RFC-0005 open question 8
(placement): a section of the Standard, not a separate profile, and a
separate class, not a fifth level. Answer ACS-Q01:

- History counts over the scope's lifetime (it is what `requires` reads); a
  checkpoint's power to authorise ends sooner, at the next execution
  boundary or its maximum age (§5.18.6).
- `requires` refuses: a missing checkpoint is F501, F503 for `rollback`, any
  other missing prerequisite V102 (§9.1 now says V102 is also a layer's
  refusal of a call; ontology 2.x has only `checkpoint` requires-edges, so
  this rule is tested with a test ontology, not a fixture).
- `soft_requires` never refuses (a layer MAY report W601).
- `precedes` and `conflicts_with` are neither enforced nor reported over
  calls (reasons in §5.18.5).
- A layer MUST make check-and-use atomic per scope (lock, reservation, or
  a stated host guarantee of one call at a time).
- A layer fails closed (R407 when it cannot complete a check).

**Rationale.** §5.2.1 already places a MUST on "safety layers" without
defining one; four layers in this repository disagreed. A section of the
Standard (rather than a profile) is where §5.2.1's MUST already points, and
the conformance class must be separate because a layer validates no catalog
and a validator checks no call. Ignoring `precedes` over an open call
sequence is the only coherent choice: at the earlier call the layer cannot
know whether the later one will come, and when it comes the earlier call has
had its effect, so a refusal protects nothing; reporting it would need a new
warning with no remedy for the reader.

**How it fully fixes the finding.** The term is defined, the scope is fixed,
each edge type's meaning over calls is stated, the F501/F502/F503 refusals
and fail-closed behaviour are normative, a claim must name the calls it
covers (§10.4 statement), and language-neutral call-sequence fixtures plus
two runners exist.

### ACS-02 — Checkpoint single use, expiry and missing-checkpoint behaviour

**Decision.** The executor's rules become normative for steps (§5.2.2) and
the same rules apply to calls (§5.18.6). Answer ACS-Q02:

1. **One checkpoint per gated step or call is normative for every host.**
   The one used is the most recently taken of the valid checkpoints, so an
   earlier valid one authorises the next call once the latest is used (the
   executor's `iter().rev().find(valid)` rule; the Python tracker changes to
   match, the TypeScript binding already does).
2. **Used up before the effect**: when every check has passed and the step or
   call is allowed to start. A call that started uses it whatever its outcome.
   A layer that must hold a checkpoint while a host prompt it does not run
   decides the call holds it (a reservation), and checks the checkpoint is
   still valid when the call is allowed; a hold it cannot resolve (it lapses,
   the process crashes, the host never reports a refusal) counts as used.
3. **Validity ends** at the next execution boundary (for steps: the end of a
   wait or delay, §5.13; for calls: a boundary the layer names, such as a turn
   ending) and, for calls, at a maximum age the layer states, **capped at 30
   minutes** (the longest default in the repository; the TypeScript binding's
   10 minutes is within it).
4. **With none valid**: the executor has its host take one (as it does
   today; F501 if the host fails); a safety layer refuses with F501 and
   **does not take one itself** (it cannot know what the call will change;
   the model takes one with a visible `checkpoint` call).
5. **Rollback.** A `rollback` call needs a checkpoint taken earlier (valid or
   not, expired or used) and uses none; with none, F503. For workflows,
   §5.2.2 states the executor's existing split: a gate or failure-mode
   rollback restores the latest checkpoint taken in the run (F503 with none);
   a `rollback` step is a capability call that restores the checkpoint its
   `checkpoint_id` input names and uses none up.

**Rationale.** These are the reference executor's and the TypeScript
binding's existing rules; the Python adapter's after-success rule loses
safety on a crash between effect and record, and a call that reports an
error may still have changed something. The cap of 30 minutes makes layers
comparable without forcing the TypeScript binding to change.

**Alignment.**

- Python adapter: the checkpoint is used up when the call is allowed (host
  callback allow, through an atomic `consume_if_valid` that re-checks the
  hold, the age and validity; or PostToolUse / PostToolUseFailure for a call
  that bypassed the callback); PostToolUseFailure consumes instead of
  releasing; holds are per checkpoint, persisted, and a hold that lapses or
  is found on reload counts as used; the permission-prompt-tool path
  reserves too; the checkpoint used is the newest valid unused one, history
  included; Stop is an execution boundary for the adapter's one scope;
  `expiry_minutes` is capped at 30; a `rollback` call without a checkpoint
  is F503; only a call classified `checkpoint` takes one (`Skill` is always
  `invoke`); the skill tracker no longer invalidates checkpoints after
  `rollback` (rollback uses none).
- Plugin hook: the marker is used up by the gated call it authorises
  (atomic rename); a Stop hook ends the marker's validity; a Bash line that
  is exactly one `git stash pop|apply` command is a rollback call (F503 when
  no checkpoint was ever taken in the project); a successful `git stash
  create` writes the marker; a line that is one command on a read-only list
  that is a subset of the SDK mapper's no longer needs a marker. The plugin does not claim class SL (host gaps stated in
  SECURITY.md §5.5).
- Rollback skill: "checkpoint has not expired" removed; an expired or used
  checkpoint can be restored (§5.2.2).
- The executor needs no change; §5.2.2 states what it does.

**How it fully fixes the finding.** Single use, use-up time, validity,
missing-checkpoint behaviour, and rollback are normative for steps and
calls; the run-time conditions of F501 and F503 are stated; every
implementation in the repository is aligned or (plugin) states its
deviation from a class it does not claim; fixtures pin each rule.

A catalog of `checkpoint`, `mutate`, `mutate` remains valid (no new
warning): §5.2.2 states that the executor has a restore point taken before
the second `mutate`. A warning would hit catalogs to no safety benefit.

### ACS-03 — Approval for tool calls outside a workflow

**Decision** (§5.18.7). Answer ACS-Q03:

- Shown and hashed: `[{"action": <tool name>, "capability": <id or null for
  an unbound tool>, "args": <arguments the call will run with>}]`, with the
  §5.14 digest. (The TypeScript binding's existing shape; the `object`
  vector of `tests/conformance/approval/digests.json` already pins it.)
- **One decision per call**, used up when the call is allowed to start; an
  identical later call needs a new one (§5.14 "has not been used before").
- **Order is the layer's**: each refusal names a check the call failed, and
  nothing is used up until both pass. Informative guidance: approval first
  for decisions recorded while the call waits; checkpoint first for a prompt
  answered within the call.
- Expiry and `min_approvers` come from the binding's optional `approval`
  member (default 1 approver; expiry the layer states). A rejection by any
  approver rejects.
- A host prompt that shows the tool and the arguments and decides that call
  alone is a valid `in_session` one-approver decision; every gated call goes
  to it (no allow-list, no remembered choice); `min_approvers` > 1, and a
  `role` the prompt cannot verify, cannot be met by such a prompt (F502).
- A layer relies on a host prompt only where it knows the prompt reaches a
  person. Where the host may answer the prompt itself (a mode that approves
  every call, or lets a classifier answer), the layer refuses with F502.
- The arguments that run are the arguments decided on: when the host
  answers a prompt with changed arguments, the layer classifies the call
  again and refuses it (F502) if the changed call requires approval, or
  (F501, F503, V102) if it needs a checkpoint or prerequisite the original
  did not hold.
- No one to ask: F502. Standing mandates, `skip`, `defer_to_queue` are not
  defined for calls.
- Every layer records the §5.14 digest of the shown value with the decision,
  even when the decision came from a prompt.

**Implementation.** Python adapter: computes the digest with the reference
canonicaliser (`_core.approval_digest`), records it, wraps a host denial of a
gated call as `F502 APPROVAL_REQUIRED: ...`, refuses `min_approvers > 1` and
any `approval.role`; answers `ask` only in the permission modes `default`,
`acceptEdits` and `plan` (F502 in `bypassPermissions`, `auto`, `dontAsk`
and any mode it does not know); re-classifies an `updated_input`. Plugin
hook: answers `permissionDecision: "ask"` with an F502 reason for gated
calls in those three modes and blocks F502 in the others (opt-out
`ACS_HOOK_APPROVAL=off`, documented as leaving approval to Claude Code's
permission rules and recorded in every audit line). `send` skill prompt
hook: the "user approved", "checkpoint exists", "allowlist" and "rate
limits" conditions are removed (code decides them; §5.18.10). TypeScript
binding: unchanged rules, digest already conformant.

**How it fully fixes the finding.** Approval for a call is defined (object,
digest, use, expiry, approvers, prompt equivalence, F502), implemented in
the adapter, the plugin and the binding, with vectors and fixtures, and the
model-judged approval check is gone.

### ACS-08 — Reporting a tool-call denial

**Decision** (§9.8 paragraph, §5.18.8). A refusal is the §9.8 diagnostic;
`location` holds `tool`, `capability` (absent for an unbound tool) and
optionally `call` (the host's call id), never `workflow` or `step`. On a
text-only channel the text is `<CODE> <NAME>: <message>`. Every refusal has
a code: rate limits and other host policies use F504 CONSTRAINT_VIOLATED;
a failure of the layer itself, or a tool reached without a layer decision,
is the new R407 SAFETY_CHECK_FAILED. The adapter keeps the §9.8 object in
its records (`adapter.call_records`) and sends the text form; the plugin's
ERR trap reports R407 instead of F501; the TypeScript binding's internal
failure result becomes an R407 diagnostic.

### ACS-36 — Skill-scoped frontmatter hooks

**Decision.** §5.18.10 states the capability checks host-neutrally, with a
row for each of the six skills' capabilities (`audit`, `checkpoint`,
`persist`, `rollback`, `send`, `transform`) and for `mutate` and `execute`,
and the rule that a check this Standard requires is decided by code from
records and arguments; a model's judgement may add a refusal but never
satisfies or replaces a required check. SECURITY.md §5.4 gains a mapping
(part 7) that takes **every condition** of the six skills' hooks, command
and prompt, to either a §5.18.10 row (or §5.18.8 for logging) or "model-judged
addition, not required". The prompt hooks lose the conditions that code
decides: `send` (allowlist, user approved, checkpoint exists, rate limits),
`rollback` (checkpoint exists and valid, not expired); content judgements
(sensitive data, scope, format) stay, labelled as model-judged additions. A
host that loads a skill's text without its hooks is told it must apply
§5.18.10 by other means. The `exit 1` and `{{tool_input}}` parts were
already fixed.

The send destination policy (ACS-52, S5) and the secrets rule (ACS-23, S4,
§6.7) are referenced from the table, not defined here; the `persist` secret
row (F504) and the `transform` row cite §6.7.

### ACS-38 — Host-neutral tool binding record

**Decision.** Publish `schemas/interop/tool_binding.schema.json` (full text
in part 3) and §5.18.1. Rules: unknown capability V101 (record not loaded,
tool stays unbound); effective flags are the stricter of declaration and
ontology (W602 for a weaker declaration, `mutation: false` honoured only on
a `mutation_overridable` capability and only when the record names no other
capability); the record's `ontology` major must be supported (V109);
duplicate records V110; the record describes and the layer's code is
authoritative; copies in a carrier (an annotation's `layer` or effective
flags) are ignored.

Carriers:

- Python tool `metadata`: the record's members except `tool` and `ontology`
  (the adapter supplies both); the flat legacy keys (`capability_id`,
  `risk`, `mutation`, `requires_checkpoint`, `requires_approval`) stay
  accepted.
- Standard Agents `acs` annotation: the record's members plus `standard` and
  informative copies (`layer`, effective flags). The generated annotation
  schema now makes the copies optional and rejects a copy inconsistent with
  `capability` (`layer` must be the capability's; each copied flag at least
  the ontology's), so `{capability: mutate, layer: PERCEIVE,
  requires_checkpoint: false}` is invalid. Old annotations stay valid.

### ACS-39 — Multi-capability, input-dependent, control-only tools; remote writes

**Decision** (§5.18.3). Classification by effect, with a normative table
(answer ACS-Q07):

| Effect | Capability |
|---|---|
| Reads, looks up or queries only (an HTTP POST that only queries included) | `retrieve`, `search` or `observe` |
| Changes a resource that can be read back, local or remote (file, row, config, issue state, remote record via API, pushed branch) | `mutate` |
| Delivers a message, notification or event to a recipient outside the scope (e-mail, chat or issue comment, webhook, published event) | `send` |
| Both | `capability` the primary one, the other in `additional_capabilities` |
| Writes the store the host provides for the agent's own memory, read by `recall` | `persist`; anywhere else `mutate` |
| Gives an agent a task, or further instructions on a task already delegated | `delegate` |
| Only signals the host (ends a turn, reports status) | control-only (`control: true`) |

- `additional_capabilities`: strictest flags across all, flag by flag, plus
  every capability's `requires` prerequisites.
- `classifier`: a layer may classify each call from its arguments; the
  record's capability and flags are the worst case; the classifier narrows
  only for arguments it recognises, never below each returned capability's
  ontology flags. **Answer ACS-Q08: "cannot weaken" does not extend to a
  tool's declared worst case** — a declaration bounds what a tool may do,
  not what each call does.
- Control-only: a record with `control: true` and none of `capability`,
  `domain`, `flags`, `additional_capabilities`, `classifier`, `invokes`,
  `approval` (else S303); its calls are never refused (no gate, no rate
  limit; a failure to record one is reported, not a refusal) and are
  recorded. F506 GATED_CONTROL_ACTION is defined by the binding, as the
  implementations already check it: a host action that takes effect
  whenever a tool is called (stop, session end, status) tied to a tool that
  is not control-only and is unbound, has a prerequisite, or has an
  effective `requires_checkpoint` or `requires_approval`. (The first
  revision's "a tool no rule can refuse" named an empty set, since R407 and
  F504 can refuse any call that is not control-only.) A bound ungated tool
  may still be tied; the guide recommends a control-only tool.
- An HTTP request whose effect the binding does not know is `send` (the
  mapper's existing class for `curl -X POST` and the like), never a read.

### ACS-41 — Capability output over a text-only result channel

**Decision** (§5.18.9). On a string result channel a capability output is
the I-JSON text of the output object, nothing before or after; the consumer
parses and checks it is an object with every required field (R402); the
producer checks the I-JSON limits first (R402); validated structure (a
submit tool's arguments) is preferred where the host has it. The rule binds
**every producer and consumer of a capability output carried as a string**,
whether or not a safety layer runs: a tool, a sub-prompt, and a host that
answers an executor's capability call from a model's or a sub-prompt's
string (the case ACS-41 names). §5.18's opening sentence says so, so the
"binds a safety layer" scope does not exempt workflow hosts.
Implementation: `grounded_agency.capabilities.output`
(`encode_capability_output`, `decode_capability_output`) and
`examples/standard_agents/src/acs/output.ts` (`encodeCapabilityOutput`,
`decodeCapabilityOutput`); `groundedTool` uses the encoder. The executor's
host protocol carries JSON values: a host decodes a string by this rule
before it answers. The outputs paragraph of `docs/guides/RUNNING_WORKFLOWS.md`
and the "Running ACS workflows" section of `docs/integrations/standard_agents.md`
cite §5.18.9 and the two helpers (part 7), which closes ACS-41's remaining
item.

### ACS-55 — Audit of every call, fail-closed loading, configuration record, concurrency

Already done: the audit hook logs every call. **Decisions** for the rest:

- **Required layer / fail-closed loading** (§5.18.8): a host that claims a
  conforming layer runs no covered call without the layer's decision; a
  missing, unloaded, failing or silent layer means refusal, by the host or by
  the tool itself. Where the host cannot guarantee it, the statement names
  the gap. Implementation: `create_grounded_mcp_server(..., require_layer=True)`
  wraps each tool's handler so it refuses with R407 unless the adapter's
  layer allowed this exact call (tool name + argument digest); the
  TypeScript binding already enforces inside the tool.
- **ACS-55's "required hook", resolved here** (not deferred): the
  requirement is met by two rules together. (1) §5.18.8's required layer: a
  host that claims a conforming layer runs no covered call without the
  layer's decision, and refuses when the layer is missing, fails to load,
  fails or is silent. (2) §5.18.10's skill-hook sentence: the checks a
  skill's hooks implement belong to the capability; a host that loads a
  skill's text without running its hooks applies them by other means, or
  its layer does not cover the skill's calls (and its statement says so).
  Together they make every required check a requirement on the host that
  claims the class, whatever mechanism declared it, which is what a
  "required hook" was asked to achieve. No frontmatter key is added: a key
  would only re-declare what §5.18.10 already requires of every host. The
  first revision's deferral to ACS-59 is withdrawn (ACS-59 is about naming
  and key ownership and does not cover this).
- **Configuration record** (§5.18.8): each record a layer writes names the
  layer and its configuration — name, version, and a digest of the bindings
  and settings applied, or the settings listed, in the action record's
  `recorded_by` member (§6.4; RECONCILIATION C14). Plugin audit lines, which
  become action records (S2b), carry
  `recorded_by: {name, version, config_sha256, settings}`: `config_sha256` is the
  sha256 of `hooks/hooks.json`, and `settings` lists the effective values of
  the environment settings that change the hooks' decisions
  (`ACS_HOOK_APPROVAL`, `ACS_CHECKPOINT_MAX_AGE`). Adapter records and
  TypeScript trace entries gain `recorded_by: {name, version, config_sha256}`
  with the digest over bindings and settings.
- **Concurrency** (§5.18.5): check-and-use atomic per scope; each layer's
  statement says how (Python: lock and per-checkpoint reservation, with
  use-at-allow re-checked atomically; TypeScript: `serially` plus the
  runtime's one execution per thread; plugin: atomic rename).
- **Scope of the Python adapter** (review item 16). Of the two options, the
  adapter keeps **one scope per adapter instance**: all sessions and
  subagents it serves share one set of records, and the Stop of any session
  it serves is an execution boundary for all of them. Per-session scopes
  would need per-session active checkpoints throughout CheckpointTracker and
  the evidence store, and S5's §5.15.4 already relies on one scope per
  adapter. The statement and the guide say so, and that sessions which must
  not share boundaries use separate adapters; a two-session test pins it
  (session B's Stop makes session A's checkpoint unusable: F501).

### ACS-57 — A binding cannot declare the bindings it invokes

**Decision** (§5.18.4). `invokes` lists the bindings a composite may call;
effective flags are the strictest over its own and, transitively, its
invokes'. Unresolved name V107; cycle V105. Answer to the remaining
question: **a nested call is covered by the composite's checkpoint and
approval** — a layer that can attribute it to the running composite applies
no further checkpoint or approval (but records it with `covered_by`); it
still checks the nested call's prerequisites (a composite's prerequisites
exclude those of its invokes, so waiving them would let a nested `rollback`
run with no checkpoint ever taken). A layer that cannot attribute it checks
it as a call of its own. **Attribution needs proof that the composite's own
code made the call**: same thread or scope is not enough, since an endpoint,
an effect or a parallel tool call of the same step can call a listed tool
while the composite runs. A nested call to a binding not listed is refused
with F504 by a layer that can attribute it, and a host that can enforce the
list SHOULD. The list bounds named invocation only, so the computed flags
are a lower bound. A call a host makes to perform an executor step is
covered by the step in the same way.
Implementation: TypeScript `groundedTool({invokes})` passes the composite's
`execute` a state whose `invokeTool` issues a one-shot **nesting token**
(thread, non-null `flowId`, tool name, argument digest) before calling the
runtime; the invoked grounded tool is covered only if it consumes a matching
token. Every grounded tool gets the wrapper (an empty `invokes` refuses every

### 2.6 New §5.2.2 Checkpoint Use (after §5.2.1)

```markdown
#### 5.2.2 Checkpoint Use

A checkpoint authorises one step whose effective `requires_checkpoint` is
true; two such steps never share one. The same rule holds for calls
(§5.18.6).

- **When it is used up.** Once everything that can stop the step before it
  acts has passed (its condition, before-gates, delay and approval),
  immediately before the capability is called. A step that is skipped,
  deferred, refused approval or stopped by a gate uses nothing. A step that
  started uses it whatever its outcome; a `retry` of the step runs under the
  checkpoint the step used.
- **Which one.** The most recently taken of the run's valid checkpoints:
  once the latest is used, an earlier one that is still valid authorises
  the next step.
- **None valid.** When a step that requires a checkpoint is about to act and
  no valid checkpoint exists (each was used up, or a wait or delay ended
  after it), the executor has its host take one and uses it; if the host
  fails, the step fails with F501. The static rule still applies: a
  `checkpoint` step must run before the step (§4.3, §5.2.1). A catalog with
  one `checkpoint` step before two `mutate` steps is therefore valid, and at
  run time a restore point is taken before the second.
- **Validity.** A checkpoint stops authorising anything when a wait or delay
  ends (§5.13) or its run is resumed (§5.14.1), and is never valid again.
  Saving and restoring a run (§5.19.4) changes nothing.
- **Rollback.** A gate action `rollback` (§5.6) or a failure-mode action
  `rollback` (§5.7) restores the latest checkpoint taken in the run, valid
  or not, and uses none up; with none, the run fails with F503, as when the
  host fails the rollback. A `rollback` step is a capability call like any
  other: it restores the checkpoint its `checkpoint_id` input names, valid,
  expired or used, and uses none up; what happens when that checkpoint
  cannot be restored is the capability's output and the host's error
  (§5.19). Validity limits what a checkpoint authorises, not what it
  restores.

These rules state the reference executor's behaviour since 1.1.0 and apply
to workflows of every version.
```

### 2.8 New §5.18 Tool-Calling Hosts (after §5.17)

```markdown
### 5.18 Tool-Calling Hosts

On a tool-calling host (§2) a model chooses each call, and no step list is
known in advance. This section states how the capability ontology applies
to calls. §5.18.1–§5.18.8 and §5.18.10 bind a **safety layer**: a host that
runs none has no obligation under them, and a layer's conformance is claimed
under §10.4. §5.18.9 binds every producer and consumer of a capability
output carried as a string, whether or not a safety layer runs, a host that
answers an executor's capability call included. When a host performs a
workflow step by making calls (the executor's capability call), those calls
are part of the step: §5.2–§5.17 govern the step, and the step's approval
and checkpoint cover its calls as a composite's cover its nested calls
(§5.18.4).

#### 5.18.1 Tool Bindings

A **tool binding** is a record (`schemas/interop/tool_binding.schema.json`):

| Member | Required | Meaning |
|--------|----------|---------|
| `tool` | Yes | The name the host offers the tool under |
| `ontology` | Yes | The ontology version the record was written against (`major.minor.patch`) |
| `capability` | Yes, unless `control` | The capability the tool performs |
| `domain` | No | The capability's domain parameter |
| `flags` | No | Declared safety flags: `risk`, `mutation`, `requires_checkpoint`, `requires_approval` (§5.2.1) |
| `additional_capabilities` | No | Other capabilities the same call performs (§5.18.3) |
| `classifier` | No | Names the classifier a layer applies to each call (§5.18.3) |
| `invokes` | No | Names of the bindings the tool may call while it runs (§5.18.4) |
| `approval` | No | `min_approvers` (integer ≥ 1, default 1), `role`, `expires` (a duration, §5.10.1) for calls that require approval (§5.18.7) |
| `control` | No | `true`: the tool only signals the host (§5.18.3) |

Members whose name starts with `x-` are vendor data. A **carrier** is a
host's own form of the record (tool metadata, an annotation): it states the
same members under its own names and is read as the record.

- A `capability`, or an entry of `additional_capabilities`, that the
  ontology does not define is V101, and the record is not loaded. A member
  of the wrong type or value, or an unknown member whose name does not
  start with `x-`, is S303, a missing required one S304, and the record is
  not loaded: a record a layer cannot read in full could declare something
  stricter, so its tool is treated as unbound rather than read in part.
- A record's **effective flags** are the strictest, flag by flag, of its
  declared `flags` and the ontology's flags of `capability` and of each
  entry of `additional_capabilities` (booleans OR-ed, `risk` the highest
  level), and of each binding in `invokes` (§5.18.4). A declared flag
  weaker than the ontology's has no effect and is W602, except
  `mutation: false` on a `mutation_overridable` capability (§4.4) in a
  record that names no other capability. A layer MAY refuse to load a
  record with a W602, as strict validation treats a warning as an error.
- A call's **prerequisites** are the `from` capabilities of the `requires`
  edges (§4.3) of every capability its record names.
- A record whose `ontology` major version the layer does not support is
  V109 and is not loaded. Any other is read against the layer's own
  ontology.
- Two records for one `tool` in one set are V110, and neither is loaded.
- A record describes; it does not enforce. A layer computes effective flags
  from its own ontology and the record's members, and ignores copies a
  carrier holds (such as an annotation's `layer` or effective flags). A
  record is not evidence that any layer enforces it.
- A tool whose record is not loaded is unbound (§5.18.2).

#### 5.18.2 Unbound Tools

A call of a tool with no loaded binding is treated as a call of no
capability with `risk: high`, and `mutation`, `requires_checkpoint` and
`requires_approval` true: a layer cannot know that an unknown tool only
reads.

A host that knows the tools it offers a model SHOULD check them before the
model runs, and report:

- each offered tool with no binding (W617);
- each binding whose `tool` is not the name the host offers it under (V111);
- each tool that requires a capability no offered tool can perform, through
  a prerequisite or through its effective `requires_checkpoint` (V102: its
  calls could never run). An offered tool with a `classifier` counts as able
  to perform any capability, and a host that takes checkpoints itself
  (§5.18.6) counts as performing `checkpoint`;
- each host action tied to a tool that is not control-only and is unbound,
  has a prerequisite, or has an effective `requires_checkpoint` or
  `requires_approval` (F506, §5.18.3).

#### 5.18.3 Classification

A binding classifies a tool by its effect, not by its transport or its name:

| What the call does | Capability |
|--------------------|------------|
| Reads, looks up or queries without changing anything, whatever the protocol (an HTTP POST that only queries included) | `retrieve`, `search` or `observe` |
| Changes a resource that can be read back: a file, a database row, a configuration, an issue's state, a remote record through an API, a pushed branch | `mutate` (`domain`: the system changed) |
| Delivers a message, notification or event to a recipient outside the scope: an e-mail, a chat or issue comment, a webhook, a published event; and any request to another system whose effect the binding does not know | `send` |
| Both of the above in one call | `capability` the primary effect, the other in `additional_capabilities` |
| Writes the store the host provides for the agent's own memory, which `recall` reads | `persist`; a write anywhere else is `mutate` |
| Gives an agent a task, or further instructions on a task already delegated to it | `delegate` |
| Only signals the host (ends a turn or a session, reports a status) and has no other effect | Control-only (`control: true`) |
| Carries only the values of an executor's host-protocol action to the party that performs or decides it (§5.19.6) | Not a `send`: protocol traffic, covered by the step whose action it performs (RECONCILIATION C38) |

**Several capabilities.** A tool that performs several capabilities in one
call names the others in `additional_capabilities`; its effective flags and
prerequisites are those of all of them (§5.18.1). The same holds for one
call a classifier reads as several actions (a shell line of several
commands): its classification is the strictest flags and the union of the
prerequisites of every action it recognises.

**Classifiers.** A layer MAY classify each call of a tool from its
arguments (`classifier` names how), as a shell command may only read. The
record's `capability`, `additional_capabilities` and `flags` are then the
tool's worst case. A classifier returns a classification only for arguments
it recognises; for any other argument, or when it fails, the worst case
applies. A classification it returns is a capability and declared flags,
subject to §5.18.1, so it is never weaker than that capability's ontology
flags; it may be weaker than the worst case, which bounds what the tool may
do, not what each call does.

**Control-only tools.** A record with `control: true` has none of
`capability`, `domain`, `flags`, `additional_capabilities`, `classifier`,
`invokes` and `approval` (else S303). Its calls return no capability output
and are never refused: no check of this section, no host policy such as a
rate limit, applies to them, and a layer that cannot write the record of
one reports the failure and does not refuse the call (§5.18.8). They are
recorded. A tool that signals the host and also has an effect is not
control-only: bind it by its effect.

A host action that takes effect whenever a tool is called, whatever the
call's result (such as ending the turn or the session, or reporting a
status), MUST NOT be tied to a tool that is not control-only and is
unbound, has a prerequisite, or has an effective `requires_checkpoint` or
`requires_approval`: the action would follow a call the layer refused
(F506). A host SHOULD tie such an action to a control-only tool: a bound
tool without those gates can still be refused by a host policy (F504) or a
failure of the layer (R407).

#### 5.18.4 Composite Tools

A tool that calls other tools while it runs (a **composite**) names the
bindings it may call in `invokes`. Its effective flags include, transitively,
those of each binding listed (§5.18.1). A name in `invokes` that no binding
of the set has is V107, and a cycle through `invokes` is V105; either way
the composite is not loaded.

- A call the composite's own code makes while it runs, to a binding it
  lists, is a **nested call**. The composite's approval and checkpoint
  cover it: a layer that attributes it to the running composite applies no
  further checkpoint or approval to it, and records it with the call that
  covered it. Every other check still applies to it, its prerequisites
  (§5.18.5) included. A layer that cannot attribute it checks it as a call
  of its own.
- A layer attributes a call to a composite only on evidence that the
  composite's own code made it, such as an invocation the layer itself
  passed to the composite. That a call comes from the same thread, session
  or execution while the composite runs is not such evidence: other code
  (an endpoint, an effect, a parallel call of the same step) can make the
  call at the same moment. Each invocation covers at most one call.
- A layer that attributes a nested call to a binding the composite does not
  list refuses it with F504. A host that can enforce the list (a runtime
  that rejects an invocation outside a declared list) SHOULD.
- `invokes` bounds named invocation only. A composite's own code can still
  write storage or reach the network directly, so the flags it takes from
  `invokes` are a lower bound: declare `flags` or `additional_capabilities`
  for what it does itself.

#### 5.18.5 Scope, Order and Concurrency

- **Scope.** A layer keeps its records per scope, the sequence of calls it
  orders, and names its scope in its conformance statement (§10.4). A
  delegate's calls are another scope, unless the layer orders them with the
  delegator's against one set of records, which it states. Records of one
  scope never authorise a call of another.
- **History.** A call ran before another only if it completed before the
  other started. History counts over the scope's lifetime; a checkpoint's
  power to authorise ends sooner (§5.18.6).
- **`requires`.** A call is refused unless each of its prerequisites
  (§5.18.1) has run earlier in the scope: for `checkpoint`, a checkpoint was
  taken in the scope (§5.18.6); for any other capability, a call of it
  completed successfully. A missing checkpoint is F501, or F503 for a call
  of `rollback`; any other missing prerequisite is V102 (§9.1).
- **`soft_requires`** never refuses a call. A layer MAY report W601.
- **`precedes`** is neither enforced nor reported over calls. At a call the
  layer cannot know whether a call that must come first will follow, and
  when one does, the earlier call has had its effect.
- **`conflicts_with`** is not enforced over calls: it forbids two
  capabilities only in one `parallel_group` (§4.3).
- **Concurrency.** A layer's check of a call and its use of a checkpoint or
  a decision (§5.18.6, §5.18.7) MUST be one atomic step for the scope: two
  calls that overlap never both pass on one checkpoint or one decision. A
  layer achieves this with a lock or a reservation, or relies on its host
  running the scope's calls one at a time, and states which (§10.4).

#### 5.18.6 Checkpoints for Calls

- **Taking one.** A checkpoint is taken in the scope by a call classified
  `checkpoint` that completed successfully, or by the host's own checkpoint
  operation, which the layer records in the scope. A call that failed takes
  none. A call that only leads to one, such as loading a skill's
  instructions, takes none: the call that saves the state does. The layer
  counts the call; it does not verify what the restore point holds.
- **One per call.** A checkpoint authorises one call whose effective
  `requires_checkpoint` is true (§5.2.2). The layer uses the most recently
  taken of the valid checkpoints no other call holds, as the executor does
  for steps.
- **When it is used up.** When every check of this section has passed and
  the call is allowed to start, before its effect. A call that started uses
  it whatever its outcome: a layer may never learn the outcome, a call that
  reports an error may still have changed something, and a failure between
  the effect and the layer's record must not leave the checkpoint valid for
  a second change.
- **Holds.** A call the layer refuses uses nothing up. Where the host can
  still refuse a call after the layer checked it (a permission prompt the
  layer does not run), the layer holds the checkpoint for the call until the
  call is allowed or refused, and releases it on a refusal it learns of. When
  the call is allowed, the layer checks again, in one atomic step with its
  use, that the hold is still the call's and the checkpoint still valid; if
  not, the call is refused with F501. A hold lapses when its checkpoint
  reaches the maximum age, or after a shorter time the layer states. A hold
  the layer cannot resolve, because it never learns what became of the call
  (the hold lapses, the layer restarts, the host does not report a
  refusal), counts as used.
- **Validity.** A checkpoint authorises a call only before the scope's next
  execution boundary, and only within the layer's maximum age: a duration
  the layer states, of at most 30 minutes. The layer names the boundaries
  it observes (§10.4). A permission prompt answered while the call waits is
  not a boundary, but the maximum age keeps running while it is open.
- **None valid.** A call that requires a checkpoint and has no valid one is
  refused with F501. A layer does not take a checkpoint on the call's
  behalf: it cannot know what the call will change, and the model takes one
  with a `checkpoint` call.
- **Rollback.** A call of `rollback` needs a checkpoint taken earlier in the
  scope, valid or not, and uses none up. With none it is refused with F503.

#### 5.18.7 Approval for Calls

A call whose effective `requires_approval` is true runs only on a valid
decision; otherwise it is refused with F502.

- **Shown and hashed.** Approvers are shown, and a decision binds to, the
  array `[{"action": <tool>, "capability": <capability>, "args": <the
  arguments the call will run with>}]`: the shown values of §5.14, with its
  digest (SHA-256 of the RFC 8785 canonical JSON). `capability` is null for
  an unbound tool. The arguments MUST be I-JSON (§5.14); a call whose
  arguments are not is refused with F502.
- **Validity.** As in §5.14: the digest matches; at least `min_approvers`
  (the binding's `approval`, default 1) distinct approvers, as the host
  authenticated them (counted by principal when it attests their
  identities, which the record then carries as
  `approval.approver_identities`, §5.17), agree; it has not expired (the binding's
  `approval.expires`, else the period the layer states); and it has not
  been used. Once any approver rejects, the request is rejected: a
  rejection is never lost to a concurrent approval.
- **One decision per call.** The call that runs under a decision uses it
  up when the call is allowed to start, as for a checkpoint (§5.18.6); an
  identical later call needs a new decision. A call refused for another
  reason uses no decision.
- **Order.** A layer checks approval and the checkpoint in the order it
  chooses, and reports the code of a check the call failed. *(Approval
  first suits decisions recorded while the call waits: the restore point is
  then taken after the wait for a person. The checkpoint first suits a
  prompt answered within the call: a call that would be refused for want of
  a checkpoint does not ask a person first.)*
- **A host's own prompt.** A permission prompt that shows a person the tool
  and the arguments the call will run with, and decides that call alone, is
  a valid `in_session` decision with one approver, bound to the call in
  place of the digest; the layer still records the digest (§5.18.8). Every
  call that requires approval goes to the prompt, even one an allow-list or
  a remembered choice would pass. A prompt that is skipped, cannot be shown,
  is answered by anything but a person (the host itself, an automatic mode,
  a classifier), or shows other arguments than those that run decides
  nothing (F502). A layer relies on a host's prompt only in the host
  configurations it knows to put the prompt to a person, names them in its
  statement (§10.4), and refuses with F502 in any other. Such a prompt
  cannot meet a `min_approvers` above 1, nor a `role` unless the host
  authenticates the person's role to the layer (F502).
- **Changed arguments.** Where the host can answer a prompt with arguments
  other than those the call was checked with, the layer classifies the
  call again with the new arguments, and refuses it if the new
  classification requires approval (F502: the decision was on other
  arguments) or a checkpoint or prerequisite the call does not already hold
  (F501, F503 or V102). Otherwise the call runs with the new arguments, and
  the layer records their digest.
- **No one to ask.** With no one who can decide, the call is refused with
  F502, as under `when_unattended: fail`. Standing mandates, `skip` and
  `defer_to_queue` (§5.14) are not defined for calls.

#### 5.18.8 Refusals, Records and Failure

- **Refusals.** A refusal is a §9.8 diagnostic. Its `location` holds `tool`
  (the name the host offers the tool under), `capability` (absent for an
  unbound tool) and, where the host gives calls an identifier, `call`; it
  holds no `workflow` or `step`. Where the channel to the model or the host
  carries only text, the text opens with the code and the name:
  `F501 CHECKPOINT_REQUIRED: ...`. A refusal for a host's own policy, such
  as a rate limit, is F504.
- **Records.** A layer records each call it allows or refuses: the tool,
  its capability, the digest of its shown value (§5.18.7) when it requires
  approval, the decision and its approvers, the checkpoint it used, any
  nested call with the call that covered it, and, for a refusal, the
  diagnostic. Each record names the layer and its configuration in its
  `recorded_by` member (§6.4): a name, a version, and a digest of the
  bindings and settings it applied (`config_sha256`), with the settings
  themselves listed where they are few (`settings`), so a reader can tell
  which rules a call was held to.
- **Fail closed.** A layer that cannot classify a call applies §5.18.2 or
  §5.18.3. A layer that cannot read its records, complete a check, or write
  the record of a call it is about to allow refuses the call with R407; for
  a control-only call it reports the failure and lets the call run
  (§5.18.3). A host that claims a conforming layer MUST NOT run a call the
  layer covers without the layer's decision: if the layer is missing, fails to load,
  fails or does not answer, the call is refused, by the host or by the tool
  itself (a tool that refuses to run, with R407, unless the layer allowed
  this call). Where the host cannot guarantee this, the conformance
  statement names the gap (§10.4). A mode that only logs, or that lets a
  call run when a check fails, is outside class SL.

#### 5.18.9 Text-Only Results

This rule binds every producer and consumer of a capability output that a
host carries as a string, whether or not a safety layer runs: a tool's
result, a sub-prompt's or a model's reply, and the string a host turns into
the output of an executor's capability call.

Where a host carries a capability output as a string, it travels as the
I-JSON text (RFC 7493) of the output object, with nothing before or after
it. A consumer parses the text and checks that it is an object with every
field the capability's output contract requires; otherwise the output is
refused with R402. A host that answers an executor's capability call from
such a string decodes it by this rule before it answers; a string that
fails is the step's failure (R402). A producer checks the I-JSON limits of
§5.14 before it sends; a value outside them is R402. Where a host carries
validated structure instead (a submit tool's arguments, a structured
result), that structure is the output and this rule does not apply.

#### 5.18.10 Capability Checks

These checks belong to the capabilities, whatever implements them. A check
this Standard requires MUST be decided by code, from the layer's records and
the call's arguments. A model's judgement (a prompt-based hook, a classifier
model) MAY add a refusal; it never satisfies or replaces a required check.

| Capability | Check | Code |
|------------|-------|------|
| `checkpoint` | A checkpoint counts once the call that saves the state completed successfully; a call that only leads to one takes none (§5.18.6) | — |
| `mutate`, `send` | A valid checkpoint for this call alone, and a valid decision (§5.18.6, §5.18.7) | F501, F502 |
| `execute` | A valid decision (§5.18.7) | F502 |
| `rollback` | A checkpoint taken earlier in the scope, valid or not, expired or used (§5.18.6) | F503 |
| `persist` | Its target is the store the host provides for the agent's memory; a call that writes anywhere else is classified `mutate` (§5.18.3) | — |
| `persist` | Its data holds no secret the layer recognises (§6.7) | F504 |
| `audit` | It appends records and changes no other state (§4.4) | — |
| `audit` | The record it appends holds no secret the layer recognises (§6.7) | F504 |
| `send` | Its destination is one every destination policy in force allows (§4.4.2), checked before approval and the checkpoint; a layer that cannot tell a call's destination under a policy refuses it | F504 |
| `transform` | Where its output is recorded or stored, a secret it read is not carried into the record: it is redacted (§6.7) | — |
| every capability | Its output satisfies the output contract (§5.18.9) | R402 |
| every capability | Records and evidence the layer writes carry no secret: it redacts them (§6.7) | — |

A host-specific mechanism, such as a hook declared in a skill's
frontmatter, is one implementation of these checks. A host that loads a
skill's text as instructions without running its hooks applies these checks
by other means, or its layer does not cover the skill's calls and its
statement says so (§10.4). With §5.18.8's rule that a host claiming a
conforming layer runs no covered call without the layer's decision, this
makes each check above required of the host, whatever mechanism declares
it. A condition a skill's hook adds that this table does not list is a
model-judged or host-specific addition: it MAY refuse a call and is never
required.
```

New §10.4:

```markdown
### 10.4 Safety-Layer Conformance

A safety layer conforms to class SL when, for every call it covers, it:

- loads bindings and reports their diagnostics as §5.18.1–§5.18.4 state,
  and passes every binding fixture whose `needs` it supports;
- applies §5.18.5–§5.18.9 and passes every call-sequence fixture whose
  `needs` it supports;
- runs in a mode that fails closed (§5.18.8).

Its **conformance statement** names: the host, and the layer's name and
version; the calls it covers and those it cannot see; its scope, and
whether a delegate's calls share it; the execution boundaries it observes;
its checkpoint maximum age; how it obtains approval (a prompt, recorded
decisions, or both), the host configurations in which it relies on a
prompt, its decision expiry, the most approvers it can obtain for one call,
and whether it can verify an approver's role; how it makes a check and its
use atomic (a lock or reservation, or its host's order); the fixture
features it supports; and its host gaps, the cases in which its host can run
a covered call without the layer's decision.

**Binding fixtures.** Each fixture holds an `ontology` version, `records`,
optionally `needs`, `offered` (each name the host offers a tool under,
mapped to the `tool` of the record it carries, or null), `host_actions`
(each an `action` and a `tool`) and `host_takes_checkpoints` (default
false), and `expect`: the exact sets of error and warning codes with the
tool each names, and the effective flags of each loaded record. A layer
passes a fixture when it reports exactly those diagnostics and computes
exactly those flags. Fixtures that check offered tools and host actions
(§5.18.2, a SHOULD) have `needs: ["offered_tools"]`; a layer that does not
check them skips those fixtures and says so in its statement.

**Call-sequence fixtures.** Each fixture is one scope with a person
present. Its `bindings` are records under its `ontology`; a tool not listed
is unbound. A bound tool succeeds and returns what its output contract
requires; a call of a tool classified `checkpoint` that runs takes a
checkpoint. Its `sequence` is a list of calls and events:

- A call names `call` (the tool), `args` (default `{}`), optionally
  `approve` or `reject` (who decided on it beforehand: on its shown value
  §5.18.7, or at the prompt), `fails` (its tool reports an error after it
  started), `nested` (calls the tool makes while it runs), and `expect`:
  `"run"` or `{"refuse": <code>}`. A call with neither `approve` nor
  `reject` is undecided.
- An event is `{"boundary": true}` (an execution boundary) or
  `{"expire": "checkpoint"}` / `{"expire": "decision"}` (the layer's
  checkpoint maximum age, or a decision's expiry, passes).

`needs` names features a layer must have to run the fixture:
`unbound_calls` (it sees calls of tools with no binding), `nested_calls`
(it attributes nested calls), `recorded_approval` (decisions recorded apart
from the call, from several approvers), and, for binding fixtures,
`offered_tools` (it checks the tools a host offers, §5.18.2). A layer that
lacks one says so in its statement and skips those fixtures; no expectation
depends on the order in which a layer checks approval and the checkpoint.

Not testable by fixture, and stated instead: that a prompt shows what runs
(§5.18.7), that the layer sees every call it claims to cover, and its host
gaps.
```

  Every checkpoint gets an `expires_at`. (Tests that used `expiry_minutes=0`

- **Holds per checkpoint.** `self._reservation` becomes
  `self._reservations: dict[str, _Reservation]` keyed by checkpoint id
  (one holder per checkpoint, one checkpoint per holder). Today's single
  slot is overwritten when a second call reserves a newer checkpoint, so the
  first call's `consume_checkpoint(holder)` finds nothing and its checkpoint
  stays valid: with the fallback below, that would let it authorise a second
  call. `_Reservation` keeps `reserved_at` from `self._now()` and the

  holder's existing hold if it has one (idempotent); otherwise it reserves
  the most recently created checkpoint, active or in history, that is
  valid (unconsumed, not invalidated, unexpired) and not held. This is the
  executor's rule (`machine.rs` `checkpoint()`: newest valid). The active
  one stays the newest. Result `(False, held_id)` when every valid one is
  held, `(False, None)` when none is valid. `can_reserve` is removed (the
  permission-prompt-tool path now reserves too).

  expires or, if `reservation_seconds` is set, after that many seconds
  (default `None`: only expiry ends it, so a person answering a prompt is
  never cut short by a shorter timer than the checkpoint's own age).
  `_sweep_lapsed()` runs under the lock at the start of every public method:
  for each lapsed hold, mark its checkpoint consumed
  (`metadata["consumed_by"] = "lapsed hold of <holder>"`), drop the hold,
  log at WARNING, persist.
- **`consume_if_valid(holder) -> str | None`** (new; use at allow): under
  the lock, after the sweep: if `holder` holds checkpoint `c`, and `c` is
  unconsumed, not invalidated and unexpired at `self._now()`, mark `c`
  consumed, drop the hold, remove the marker if `c` is active, persist, and
  return `c.id`; otherwise drop any hold of `holder` (marking its checkpoint
  consumed if it was not already: a hold that ends without a valid use is
  still used) and return `None`.
- `consume_checkpoint(holder)` (use after the call ran, PostToolUse and

  Used for execution boundaries.

  `"reservations": [{"checkpoint_id", "holder"}]`. On

PreToolUse `check_before_tool` (order: classify, control, rate limit,
prerequisites, checkpoint, approval). `wrap_options` passes the hook the
wrapped options' `permission_mode` (`options_mode`, may be `None`).

1. Classify (unchanged; failure → `UNCLASSIFIED_TOOL`).
2. `mapping.control` → record `allowed` and return `{}`. No rate limit or
   other check applies; a failure to record is logged at ERROR and the call
   still runs (§5.18.3).
3. Rate limit: refusal text now `F504 CONSTRAINT_VIOLATED: rate limit: ...`;
   a limiter failure → `R407 SAFETY_CHECK_FAILED: ...`.
4. Prerequisites: `_prerequisite_refusal` → refuse.
5. `requires_checkpoint`: `validate_and_reserve(holder, scope)` on every
   path, the permission-prompt-tool path included (the first revision's
   unreserved path and `can_reserve` are removed). A call with no
   `tool_use_id` cannot hold a checkpoint: R407 in strict mode. No valid
   unheld checkpoint: F501 in strict mode.
6. `requires_approval` and `asks`, in this order, each refusal releasing the
   hold step 5 took (the layer refused the call, so it learns of it):
   a. `mapping.approval` with `min_approvers > 1` → F502 ("needs N
      approvers; this layer obtains one per call"); with a `role` → F502
      ("needs an approver with role R; a permission prompt cannot show this
      layer the person's role").
   b. `mode = input_data.get("permission_mode") or options_mode or
      "default"` (an omitted mode is Claude Code's default; the options'
      mode covers a host that omits the field). `mode not in
      PROMPTING_PERMISSION_MODES` → F502 ("permission mode '<mode>' does
      not put this call to a person; STANDARD 1.2.0 §5.18.7").
   c. `_shown_digest` (not I-JSON → F502).
   d. Answer `ask` with the F502 reason, record `asked` with the digest and
      the mode, increment `self._allowed[(tool, args_digest)]`.
7. Otherwise (no approval needed): increment `_allowed`, record `allowed`,
   return `{}`.
8. Any other exception: strict → release the hold, refuse `R407`;
   non-strict → log (outside class SL, documented).

Permission callback `check_permission` (`holder` = the context's
`tool_use_id`):

1. Classify the input (`mapping0`); control → allow.
2. `mapping0.requires_checkpoint`: no `holder` → deny R407 ("the call has no
   tool_use_id, so this layer cannot hold a checkpoint for it"); else
   `validate_and_reserve(holder)` (idempotent with PreToolUse's hold) →
   F501 on failure. The checkpoint is checked before a person is asked.
3. Host callback present: call it with the input.
   - Not an allow → `release_reservation(holder)` (a refusal the layer
     learns of), decrement `_allowed`; if `mapping0.requires_approval` and
     `asks`, deny `F502 APPROVAL_REQUIRED: <tool> was not approved: <host
     message>` (keep the host deny's `interrupt`); otherwise return the
     host's result unchanged.
   - An allow: `args1` = the result's `updated_input` when present, else
     the input. If `digest(args1) != digest(input)` (§5.18.7 *Changed
     arguments*): `mapping1 = classify(args1)`; refuse, releasing the hold,
     with F502 if `asks and mapping1.requires_approval`, with the code of
     `_prerequisite_refusal(mapping1)` if it has one, and with F501 if
     `mapping1.requires_checkpoint and not mapping0.requires_checkpoint`;
     re-key `_allowed` to `args1`'s digest; if `mapping0` held a checkpoint
     that `mapping1` does not need, release it. Else `mapping1 = mapping0`.
   - `mapping1.requires_checkpoint`: `cid = tracker.consume_if_valid(holder)`;
     `None` → deny F501 ("the checkpoint this call held expired, or an
     execution boundary passed, while the call waited; take a new
     checkpoint"). This is the atomic re-check and use of §5.18.6 *Holds*.
   - Record the decision: digest of `args1`, `approvers: ["in_session"]`
     when approval was required, `checkpoint_id: cid`; return the host's
     result (with its `updated_input`).
4. No host callback: `mapping0.requires_approval` and `asks` → F502 as now.
   Else, if `mapping0.requires_checkpoint`, `consume_if_valid(holder)` →
   allow or F501.
5. Exception → deny `R407 SAFETY_CHECK_FAILED: ...` (release the hold).

- Layer identity on each trace entry: `{name: '@acs/standard-agents-binding', version: STANDARD_VERSION, config: await digestOf(annotation)}` (computed once, lazily).
- Nested coverage by **nesting tokens** (replaces the first revision's
  per-thread `OPEN` stack, which attributed any call on the thread to the
  running composite: an endpoint's or effect's call, and a parallel tool
  call of the same step, which the specification allows with
  `parallelToolCalls`):
  - Module-level `const TOKENS = new Map<string /* threadId */, NestingToken[]>()`,
    `interface NestingToken { composite: string; seq: number; flow: string; tool: string; digest: string; used: boolean }`.
  - In `execute`, after a successful claim, **every** grounded tool calls
    `options.execute` with `nestingState(state, {name, seq, flow, invokes})`
    instead of `state`: a `Proxy` over the runtime's state whose `get` trap
    returns a wrapped `invokeTool` and, for any other member, the target's
    value (functions bound to the target, so private fields keep working).
  - The wrapped `invokeTool(tool, args)`: if `tool` is not in `invokes` (an
    empty `invokes` included) → append a `refused` trace entry with code
    F504 and `covered_by: seq`, and return the F504 refusal result without
    calling the runtime ("<name> does not list <tool> in invokes"). If
    `flow` is null (the composite ran outside an execution, which only a
    tool that needs neither approval nor a checkpoint can) → call the
    runtime's `invokeTool` with no token: the call is checked on its own.
    Else compute `digest(args)`, push a token `{composite: name, seq, flow,
    tool, digest, used: false}` for `state.threadId`, `await` the runtime's
    `invokeTool(tool, args)`, and in `finally` remove **that token object**
    (by identity, `splice(indexOf(token), 1)`).
  - In `check` (under `serially`, so token consumption is atomic with the
    other checks of the thread): compute `flow` and the args digest; if
    `flow !== null`, look for an unused token of this thread with `token.flow
    === flow`, `token.tool === name` and `token.digest === argsDigest`; if
    found, mark it `used` and the call is **covered**: skip only the
    approval and the checkpoint; the prerequisite check (step 2) still
    runs; trace `started` with `covered_by: token.seq`. One token covers one
    call. A call with no matching token is checked as a call of its own.
  - The token matches the arguments as the composite passed them. A runtime
    that parses arguments (defaults filled in, keys stripped) before the
    nested tool sees them changes the digest, and the call is then checked
    on its own: a composite passes complete, parsed arguments. A runtime
    that runs an invoked tool in a new execution (another `flowId`) gets
    the same fail-closed result. Both are in the statement's host gaps.
  - What remains: a call made at the same moment by other code with exactly
    the same tool and arguments as a pending invocation can take the token.
    It is then the one covered call of that invocation, with exactly the
    arguments the composite chose; the composite's own invocation is
    checked on its own. Stated in the statement.
  - `uses` is set to `Object.keys(invokes)` only when `invokes` is given,
    so the runtime also enforces the list; a tool with no `invokes` keeps
    an unconstrained `uses` (so its `queueTool` calls, which run later and
    are checked on their own, keep working), and its `invokeTool` calls are
    refused F504 by the wrapper.
- Prerequisites (step 2 of `check`): a missing `checkpoint` prerequisite is
  F503 for `rollback` and F501 otherwise (as now); any other missing
  prerequisite is **V102** (was F501). Prerequisites come from
  `prerequisitesOf([capability, ...additional_capabilities])`.
- Internal failure (`catch` in `check`) → `refusal('R407', ...)` diagnostic
  instead of a bare error; a store failure after the tool ran keeps the

- Output: `encodeCapabilityOutput` replaces `outputProblems` +

### 5.5 Plugin hooks (`hooks/`)

The plugin's hooks are aligned with §5.18 where Claude Code allows it and
do **not** claim class SL (SECURITY.md §5.5 states why).

`hooks/pretooluse_require_checkpoint.sh` (same name; matcher unchanged):

1. Read the payload (stdin, or the first argument for manual use, as now).
   **The payload must be Claude Code's JSON object** (`tool_name`,
   `tool_input`, `permission_mode`, `tool_use_id`); `tool_name` and, for
   Bash, `.tool_input.command` are read with jq. A payload that is not a
   JSON object with a string `tool_name`, or no jq: block with
   `R407 SAFETY_CHECK_FAILED: cannot read the tool call (a JSON payload and jq are required)`.
   This replaces matching a regular expression against the payload text and
   the age-only fallback without jq: a behaviour change (part 8), since a
   plain-text payload such as `"Write to file.py"` was classified by its
   words and is now blocked.
2. Classify. The shell's lists are **derived from the SDK mapper** and a
   test keeps them so (part 6.3):
   - `Write|Edit|MultiEdit|NotebookEdit` → mutate.
   - `Bash`: the trimmed command. If it holds any character from
     `;&|<>$` + backtick + `(){}` + newline/CR + backslash, it may be more
     than one simple command or expand something: mutate. Otherwise split
     on blanks into words (exactly one simple command):
     - `WRITES`: if `words[0]` is `git` and any word starts with
       `--output`, or `words[0]` is `file` and a word is `--compile` or a
       short-option cluster containing `C` (`-C`, `-bC`): mutate. These are
       `_writes`' rules for the commands on the list below.
     - `git stash <sub>` (`words[0..1]` = `git stash`), by
       `GIT_STASH_CLASSES` (same table as the mapper's
       `_GIT_STASH_CLASSES`): `create` → checkpoint (allow, exit 0; the
       marker is written after it succeeds, by the PostToolUse hook below);
       `list`, `show` → observe; `pop`, `apply` → rollback; anything else
       (`store`, `push`, `drop`, …) → mutate.
     - `READ_ONLY=(ls cat head tail wc pwd grep stat file du df which whoami uname echo printf "git status" "git log" "git diff" "git show" "git rev-parse" "git ls-files")`:
       `words[0]`, or `words[0] words[1]` for git, on the list → observe
       (allow, exit 0, nothing used). Every entry is in the mapper's
       `_READ_ONLY_COMMANDS` (which gains `git rev-parse` and `git
       ls-files`, part 5.2); the first revision's `rg` (`rg --pre CMD`
       runs CMD for each file) and `tree` (`-R` with `-H` writes files)
       are dropped.
     - anything else → mutate.
3. rollback: allow if `.claude/checkpoint.ok` exists or
   `.claude/checkpoints/used/` holds a file; else block
   `F503 ROLLBACK_FAILED: no checkpoint was taken in this project; there is nothing to roll back to.`
4. mutate: validate the marker as now (exists, regular file, not a
   symlink, JSON object, `checkpoint_id`, numeric `expires_at`, not
   expired); block F501 otherwise.
5. Approval mode, before the marker is taken (so a block here uses
   nothing): unless `ACS_HOOK_APPROVAL=off`, read `mode =
   .permission_mode // "default"`. If `mode` is not `default`,
   `acceptEdits` or `plan`, block (exit 2) with `F502 APPROVAL_REQUIRED:
   permission mode '<mode>' does not put this call to a person; set
   ACS_HOOK_APPROVAL=off to leave approval to Claude Code's permission
   rules.` (the same rule as the adapter's, §5.18.7).
6. Take the marker: `mkdir -p .claude/checkpoints/used` and
   `mv -n "$marker" ".claude/checkpoints/used/<checkpoint_id>.<tool_use_id or epoch-pid>"`;
   if the marker is gone afterwards and the target does not exist (another
   call took it), block F501 "taken by another call". (A rename is atomic
   on one filesystem.)
7. Approval: unless `ACS_HOOK_APPROVAL=off`, print
   `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"ask","permissionDecisionReason":"F502 APPROVAL_REQUIRED: <tool> (capability 'mutate') requires approval; it runs only if this call is approved."}}`
   and exit 0. Else exit 0.
8. ERR trap: `R407 SAFETY_CHECK_FAILED: the checkpoint hook failed at line N, so the call is blocked.` (exit 2).

`hooks/posttooluse_take_checkpoint.sh` (new; PostToolUse, matcher `Bash`):
if the command is the `git stash create` form of step 2 (same character

## 9. RFC-0005 (full replacement text of `spec/RFC-0005-tool-calling-hosts.md`)

```markdown
# RFC-0005: Tool-calling hosts
**Status:** Accepted
**Target:** Standard v1.2.0
**Date:** 2026-11-15

## Summary

Standard 1.1.0 states its safety rules over the steps of a workflow. For a
host where a model chooses one tool call after another and no workflow runs,
it had one sentence, in [§5.2.1](STANDARD-v1.1.0.md#521-safety-flags):
"Validators, executors and safety layers MUST act on effective flags." It
did not define a safety layer, and the word "tool" did not occur in it.

This RFC decides how the Standard applies to such a host. Standard 1.2.0
carries the decisions as §5.18 (Tool-Calling Hosts), §5.2.2 (Checkpoint Use)
and class SL (§10.4) of [STANDARD-v1.2.0](STANDARD-v1.2.0.md). It answers
findings ACS-01, ACS-02, ACS-03, ACS-07, ACS-08, ACS-36, ACS-38, ACS-39,
ACS-41, ACS-55 and ACS-57, and questions ACS-Q01 to ACS-Q04, ACS-Q07 and
ACS-Q08 of the
[Standard Agents mapping](../docs/research/analysis/standard_agents_mapping/findings_agent_capability_standard.yaml).
The maintainers accepted it on 2026-11-15, with every remaining finding to
be implemented in 1.2.0; the open questions of the Draft are decided below.

## Motivation

When the mapping was reviewed, four pieces of code in this repository
enforced the safety flags and disagreed:

| Code | Checkpoint use | Lifetime | With none valid |
|---|---|---|---|
| Reference executor (`core/src/exec/machine.rs`) | One per step, used up before it runs | Until a wait or delay ends | Asks the host |
| TypeScript binding (`examples/standard_agents/src/acs/grounded.ts`) | One per call, used up before it runs | One execution, ten minutes | Refuses |
| Python adapter (`grounded_agency/adapter.py`) | One per call, used up after success | 30 minutes | Refuses in strict mode |
| Plugin hook (`hooks/pretooluse_require_checkpoint.sh`) | A marker file, never used up | The marker's expiry | Blocks |

The ontology requires approval for `execute`, `mutate` and `send`; the hook
asked for none, and a call has no step and no `shows`, so each binding chose
what to hash. A refusal was prose in one layer and a §9.8 object in another.
No record said which capability a tool performs, a tool with no metadata
became `execute`, and skill-level hooks asked a model whether the user had
approved. The levels of [§10](STANDARD-v1.1.0.md#10-conformance) cover
validators only, so a binding had nothing to conform to.

## Goals

- Rules over calls that a safety layer on any tool-calling host can
  implement, with the same effective flags, codes and approval digest as a
  workflow.
- One host-neutral binding record, with the existing carriers as instances.
- Language-neutral fixtures, run by two reference layers.
- No change to what a validator accepts or what the executor does.

## Non-goals

- Delegation semantics beyond scope: a `delegate` call's flags, checkpoints
  across a delegation and agent descriptors (ACS-04, ACS-18, ACS-29) are
  decided elsewhere in 1.2.0.
- Evidence anchors (ACS-06): decision 8 of the Draft is withdrawn from this
  RFC; the evidence rules of 1.2.0 decide it.
- The executor's host protocol (ACS-37), the send destination policy
  (ACS-52) and the secrets rule (ACS-23), which §5.18.10 references.
- Standing mandates, `skip` and `defer_to_queue` for a call, and how a host
  stores records or authenticates approvers.

## Key decisions

### 1) Terms and placement

§2 defines tool-calling host, call, tool binding, safety layer, scope and
execution boundary. The rules are a section of the Standard (§5.18), where
§5.2.1's MUST already points, and conformance is a separate class, SL
(§10.4), not a fifth level: a layer validates no catalog and a validator
checks no call. (Draft open question 8.)

### 2) One host-neutral binding record

`schemas/interop/tool_binding.schema.json`: `tool`, `ontology`, `capability`
(or `control`), `domain`, `flags`, `additional_capabilities`, `classifier`,
`invokes`, `approval`.

- **2.1** An unknown capability is V101; a malformed record S303/S304; an
  unsupported ontology major V109; two records for one tool V110. A record
  that does not load leaves its tool unbound.
- **2.2** Effective flags are the strictest of declaration and ontology,
  flag by flag; a weaker declaration is W602 and has no effect, except
  `mutation: false` on a single `mutation_overridable` capability. A host
  may refuse such a record; the TypeScript binding does.
- **2.3** An unbound tool is the strictest case: high risk, mutation,
  checkpoint and approval. A host that knows the tools it offers reports
  each unbound one as W617. (Draft open question 4: neither `observe` at
  medium risk, which fails open, nor refusal, which makes a layer unusable
  on a host with many built-in tools; a person can still approve.)
- **2.4** Several capabilities: `additional_capabilities`, strictest flags
  and every capability's prerequisites.
- **2.5** Classifiers narrow per call only for arguments they recognise; the
  record is the worst case. A classification can be weaker than the worst
  case, never weaker than its own capability's ontology flags. (Draft open
  question 7: "cannot weaken" bounds a capability, not a tool's worst case.)
- **2.6** Composites: `invokes`, strictest flags transitively; V107 for an
  unresolved name, V105 for a cycle. A nested call is covered by the
  composite's approval and checkpoint where the layer can attribute it, and
  checked on its own where it cannot; its prerequisites are checked either
  way. Attribution needs evidence that the composite's own code made the
  call (the TypeScript binding's one-shot nesting token), not merely the
  same thread or execution. A nested call outside the list is F504. The
  list bounds named invocation only: the flags it gives are a lower
  bound.
- **2.7** The record describes; the enforcing code is authoritative, and
  copies in a carrier are ignored. The Python SDK's tool `metadata` and the
  `acs` annotation are carriers; the annotation schema now rejects copies
  inconsistent with the capability.
- **2.8** Classification by effect, with a table: a change to a resource
  that can be read back, local or remote, is `mutate`; delivering a
  message, notification or event, or a request of unknown effect, is
  `send`; a write to the agent's own memory store is `persist`, anywhere
  else `mutate`; further instructions on a delegated task are `delegate`; a
  tool that only signals the host is control-only. One call a classifier
  reads as several actions takes the strictest flags and every
  prerequisite of all of them. (Draft open question 6.)
- **2.9** Control-only tools are never refused (no gate, no host policy; a
  failure to record one is reported). A host action that follows any call
  of a tool (a stop tool) must not be tied to a tool that is not
  control-only and is unbound, has a prerequisite, or requires a checkpoint
  or approval: F506.

### 3) Over a call sequence, only `requires` refuses

- **3.1** History counts over the scope's lifetime; a checkpoint's power to
  authorise ends at a boundary or its maximum age (decision 4). A delegate's
  calls are another scope unless the layer orders them together and says
  so. (Draft open question 1, first part.)
- **3.2** `requires`: F501 for a missing checkpoint, F503 for `rollback`,
  V102 for any other prerequisite; §9.1 says a V-code keeps its meaning
  when a layer uses it for a call.
- **3.3** `soft_requires` never refuses; W601 may be reported.
- **3.4** `precedes` is neither enforced nor reported: at the earlier call
  nothing is known, and at the later one a refusal protects nothing. (Draft
  open question 1, second part.)
- **3.5** `conflicts_with` is not enforced over calls.
- **3.6** Check and use are atomic per scope: a lock or reservation, or a
  host that runs the scope's calls one at a time, as stated.

### 4) One checkpoint per call, until a boundary

- **4.1** One checkpoint authorises one gated call, and one gated step
  (§5.2.2, the executor's rule): the most recently taken of the valid
  ones, so an earlier valid checkpoint serves once the latest is used. A
  checkpoint is taken by the call that saves the state, not by a call that
  only leads to one (a skill's instructions).
- **4.2** It is used up when the call is allowed to start, before the
  effect, whatever the outcome. A checkpoint held while a host prompt is
  open is re-checked and used in one atomic step when the call is allowed.
  A hold the layer cannot resolve (it lapses, the layer restarts, the host
  never reports a refusal) counts as used. (Draft open question 2: before
  the effect, for every host.)
- **4.3** Validity ends at the next execution boundary the layer names and
  at its maximum age, at most 30 minutes. A prompt answered within the call
  is not a boundary. (Draft open question 2: the Standard caps the age.)
- **4.4** A `rollback` call needs a checkpoint taken earlier, valid or
  not, and uses none; else F503. For workflows, a gate or failure-mode
  rollback restores the latest checkpoint (F503 with none) and a `rollback`
  step restores the checkpoint its input names, as the executor does.
- **4.5** With no valid checkpoint a call is refused with F501; a layer does
  not take one itself. The executor keeps having its host take one for a
  step (§5.2.2). (Draft open question 2.)
- **4.6** Fail closed: R407 when a check cannot complete; a host claiming a
  conforming layer runs no covered call without its decision, or names the
  gap.

### 5) Approval binds to tool, capability and arguments

- **5.1** A gated call runs only on a valid §5.14 decision; else F502.
- **5.2** Shown and hashed: `[{action, capability, args}]`, `capability`
  null for an unbound tool. (Draft open question 3.)
- **5.3** One decision per call, used up when the call starts. (Draft open
  question 3.)
- **5.4** Expiry and `min_approvers` come from the binding's `approval`;
  any rejection rejects.
- **5.5** The order of the approval and checkpoint checks is the layer's;
  neither is used up until both pass. (Draft open question 3.)
- **5.6** A host prompt showing the tool and the arguments, deciding that
  call alone, is a one-approver `in_session` decision; every gated call
  goes to it; the layer records the digest. It cannot meet
  `min_approvers` above 1, nor a `role` the host does not authenticate to
  the layer. A layer relies on a prompt only in host configurations it
  knows to put it to a person, and names them; in any other (a mode that
  approves calls itself or lets a classifier answer) it refuses with F502.
- **5.6a** Arguments the host changes while answering a prompt are
  classified again; the call is refused if it then needs approval, or a
  checkpoint or prerequisite it does not hold.
- **5.7** No one to ask: F502.

### 6) A refusal is a §9.8 diagnostic

`location` holds `tool`, `capability` (absent when unbound) and optionally
`call`; on a text-only channel the text opens with the code and name. A
host policy such as a rate limit is F504; a failure of the layer itself is
R407.

### 7) A text-only result carries I-JSON text

A capability output on a string channel is the I-JSON text of the output
object, nothing around it; the consumer checks required fields (R402); the
producer checks I-JSON limits first (R402); validated structure is
preferred. The rule binds every producer and consumer of a string output,
whether or not a safety layer runs, a host that answers an executor's
capability call from a model's or a sub-prompt's string included.

### 8) (Withdrawn) Evidence anchors

Moved out of this RFC: ACS-06 is decided with the evidence rules of
Standard 1.2.0.

### 9) A conformance class for safety layers

- **9.1** Class SL (§10.4): binding fixtures, call-sequence fixtures and a
  conformance statement naming the host, the calls covered and not seen,
  scope, boundaries, maximum age, approval (with the host configurations
  in which a prompt is relied on, and whether roles can be verified),
  concurrency, fixture features and host gaps.
- **9.2** Fixtures: `tests/conformance/bindings/` and
  `tests/conformance/calls/`, generated by `scripts/gen_call_fixtures.py`
  with a `--check` mode, with schemas beside them. A fixture's `needs`
  (`unbound_calls`, `nested_calls`, `recorded_approval`, and for binding
  fixtures `offered_tools`, since §5.18.2's offered-tool checks are a
  SHOULD) names features a layer may lack and state.
- **9.3** Reference layers: the Python adapter (a hook before each tool)
  and the TypeScript binding (inside each tool) run every fixture whose
  needs they support. The plugin's shell hooks are aligned with the rules
  Claude Code lets them apply and do not claim the class.

### 10) Capability checks are host-neutral

§5.18.10 states the checks of `checkpoint`, `mutate`, `send`, `execute`,
`rollback`, `persist`, `audit` and `transform` as requirements of the
capabilities, citing the destination policy (§4.4.2) and the secrets rule
(§6.7). A check the Standard requires is decided by code; a model's
judgement may add a refusal but never satisfies one. Skill-level hooks are
one implementation; SECURITY.md §5.4 maps every condition of the six
skills' hooks to a row or to "model-judged addition, not required", and the
prompt hooks no longer ask a model about approval, checkpoints or rate
limits. With §5.18.8's required layer, this is the answer to ACS-55's
"required hook": a host that claims the class runs no covered call without
the layer, and a host that does not run a skill's hooks applies their
checks by other means or does not cover those calls. No frontmatter key is
added.

### 11) Records name the layer and its configuration

Every record a layer writes names the layer, its version and a digest of
the bindings and settings it applied, or the settings listed; the plugin's
audit lines carry the sha256 of `hooks/hooks.json` and the effective
environment settings that change its decisions.

## Backward compatibility

- Validators accept what they accept today, and the executor behaves as
  today: §5.2.2 states its behaviour. No repository catalog is affected and
  CI's strict validation is unchanged.
- The terms, sections, class, schemas, fixtures and the codes V110, V111,
  R407, F506 and W617 are additions: MINOR under
  [GOVERNANCE](GOVERNANCE.md#versioning). Existing codes gain meanings for
  bindings and calls with their severities unchanged.
- The annotation schema accepts every annotation it accepted, and rejects
  copies inconsistent with the capability, of which the repository has
  none.
- Implementations change: the Python adapter uses a checkpoint up when a
  call is allowed (re-checked atomically), also for a failed call, counts
  an unresolved hold as used, ends validity when any session it serves
  ends a turn, caps the maximum age at 30 minutes, refuses a `rollback`
  with no checkpoint, counts only state-saving calls as checkpoints,
  refuses gated calls in permission modes that do not reach a person,
  treats a tool with no capability as unbound, and guards its MCP tools;
  the plugin hook reads only JSON payloads, uses its marker once and asks
  for approval; the TypeScript binding reports its lint findings with
  Standard codes and attributes nested calls by nesting tokens.

## Conformance test updates

  actions need the `offered_tools` feature) and call-sequence fixtures
  (20), their schemas, two conformance statements, and runners in Python
  and TypeScript.
- Approval digest vectors `tool_call` and `tool_call_unbound` in
  `tests/conformance/approval/digests.json`.
- Unit tests for the plugin hooks (and a test that their lists are a

- §10.3 names the binding and call fixtures normative for class SL.
- Not testable by fixture, and stated in a conformance statement instead:

## Alternatives considered

- **Leave tool-calling hosts to each binding's documentation.** Rejected:
  §5.2.1 already binds safety layers, and this repository's layers
  diverged.
- **A separate profile and a fifth level L5.** Rejected: §5.2.1's MUST
  points into the Standard, and a level implies the levels below it.
- **Treat a call sequence as a workflow built as it runs.** Rejected:
  `precedes`, W608 and other static checks need a closed step list.
- **Use a checkpoint up after success (the Python adapter's rule).**
  Rejected: a crash between effect and record leaves it valid for a second
  change, and a failed call may have changed something.
- **Let a layer take a checkpoint on a call's behalf, as the executor does
  for a step.** Rejected: a layer cannot know what the call will change;
  the executor's host is given the step.
- **Hash `[args]`, the executor's default.** Simpler, but one decision would
  fit every tool that takes the same arguments.
- **Classify an unbound tool as `observe`, or refuse it.** The first fails
  open; the second makes a layer unusable on hosts with many built-in tools.
- **A new code for every refusal kind (rate limit, undeclared invocation).**
  Rejected: F504 already names a policy constraint; one new runtime code,
  R407, covers the layer's own failure.
- **Check a composite's nested calls on their own.** Rejected where the
  layer can attribute them: the composite would use the checkpoint and its
  nested `mutate` call would be refused, so no composite could change
  anything.
- **Attribute a nested call to whatever composite runs on the thread (and
  execution).** Rejected: an endpoint, an effect or a parallel tool call of
  the same step could call a listed tool at that moment and pass with no
  checkpoint and no approval. The binding issues a one-shot token per
  invocation instead.
- **Waive a nested call's prerequisites too.** Rejected: a composite's
  prerequisites exclude its invokes', so a nested `rollback` could run
  with no checkpoint ever taken.
- **Release a hold that lapses, so the checkpoint can serve another call.**
  Rejected: the layer does not know the held call did not run.
- **One scope per session in the Python adapter.** Rejected for now: it
  would need per-session checkpoints throughout the tracker; the adapter
  states one scope per instance and treats any session's Stop as a
  boundary.
- **A frontmatter key that declares a hook required (ACS-55).** Rejected:
  §5.18.8 and §5.18.10 already require every host claiming the class to
  apply each capability check, whatever declares it; a key would add a
  second, weaker statement of the same rule.
- **Classify `git restore --source=<sha>` as `rollback`** (asked by the
  checkpoint/rollback workstream). Rejected: `<sha>` can name any commit
  (an old one, or one the model made), so a layer cannot tell that it is a
  restore point, and an ungated `rollback` would then overwrite the working
  tree with any commit's content. It stays a gated `mutate`; `git stash
  apply <sha>` is `rollback`.
- **Count `git stash store <sha>` as the checkpoint** (the first
  revision). Rejected: it names a commit the caller chooses, so it can
  mint a restore point that is not the current state, and it fails on a
  clean tree, where a model could then never take a checkpoint. `git stash
  create` captures the current state (or confirms `HEAD` is it) and is
  counted instead.
- **Trust Claude Code's prompt in every permission mode.** Rejected: in
  `bypassPermissions` the documentation does not say the prompt is shown,
  and in `auto` a classifier can answer it, so a gated call could run on
  no person's decision.

## Open questions

1. **Upstream hook.** The Standard Agent Specification has no hook that can
   refuse a call before it runs, so a runtime-level layer cannot cover plain
   `defineTool` tools. Should this project propose one upstream, so the
   class can cover every tool of a Standard Agents runtime?
2. **Machine-readable statements.** Statements are JSON files beside the
   fixtures. Should a later version publish a registry of conformance
   statements, and require one for any implementation that claims SL?
3. **Claude Code host gaps.** A command hook that cannot start, or times
   out, lets Claude Code run the call. If Claude Code offers a fail-closed
   hook mode, should the plugin's hooks then claim class SL?
4. **Permission modes.** The SDK adapter and the plugin rely on an `ask`
   reaching a person in Claude Code's `default`, `acceptEdits` and `plan`
   modes, on the documentation's word. Should a later version ask Claude
   Code to state, per mode, whether a hook's `ask` reaches the permission
   callback, so the list can be tested rather than cited?
5. **What a checkpoint captured.** A layer counts a successful checkpoint
   call without verifying what the restore point holds (a stored commit may
   not be the current state). Should a checkpoint output carry a digest of
   what it captured, so a layer can check it against the scope before it
   counts the call?
6. **Per-session scopes.** Should the Python adapter offer one scope per
   session, so that one session's turn end does not end another's
   checkpoints?
```

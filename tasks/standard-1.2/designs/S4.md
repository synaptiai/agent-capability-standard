## 1. Per finding: decision, rationale, how it fixes the finding

### ACS-06 — `evidence_anchors` has no item schema; the vocabularies disagree

**Decision.**

1. **One type.** The evidence anchor is `event_schema.yaml#/types/Anchor`
   (1.2.0). `world_state_schema.yaml#/types/Anchor` becomes the identical
   type (a test checks the two are equal). Members: `ref` (required,
   non-empty string), `kind` (required), `timestamp` (optional, ISO-8601,
   nullable), `excerpt` (optional, nullable; never a secret), `digest`
   (optional, `sha256:` + 64 lowercase hex: the SHA-256 of the content as the
   producer read it; for a JSON value, of its RFC 8785 canonical JSON in
   UTF-8). Other members are allowed; a producer's own SHOULD start with `x-`.
2. **One kind vocabulary.** `file`, `url`, `tool`, `log`, `sensor`,
   `human_note`, `api` (the event schema's seven) plus **`record`** (a record
   the agent system itself wrote or holds: an action or audit record, a
   checkpoint, a memory item, a workflow value), and vendor kinds
   `x-[a-z0-9][a-z0-9_.-]*` (the grammar `authenticated_by` already uses).
   Expressed as a `pattern` in both canonical schemas.
3. **Refs.** Opaque to the Standard; the producer documents its schemes.
   One scheme is reserved: **`acs:`** followed by a §5.3 reference body
   (`acs:search_out.results[0]`) names a workflow value (ACS-22); its kind
   is `record`.
4. **Capability outputs.** All 36 `evidence_anchors` gain
   `items: {anyOf: [{$ref: schemas/event_schema.yaml#/types/Anchor}, {type: string}, {type: object}]}`.
   The anchor is the form. A bare string, and an object that is not an
   evidence anchor (no `kind`, a kind outside the vocabulary such as the
   SDK's `tool_output`, an empty `ref`, a malformed `digest`), are the
   **legacy forms**: accepted, never counted toward a grounding policy, and
   **deprecated** (removed in 2.0, §11.2). No implementation refuses an
   output for the shape of its items outside a grounding policy, and under
   one a legacy item does not count but is not itself a failure (§5.20).
5. **Empty list.** An empty `evidence_anchors` grounds nothing: the output
   must then be marked inferred (§3.1). This answers RFC-0005 open question 5.
6. **`required_anchor_types`** lists kinds from this vocabulary (any-of: an
   anchor counts when its kind is listed) and maps to a grounding policy's
   `kinds` (§5.20). S6 migrates the shipped profiles' values.
7. **SDK mapping** (RFC-0005 OQ5): `tool_output` → `tool`, `command` →
   `tool`, `mutation` → `record`, `coordination` → `record`, `file` → `file`.
   The legacy names are accepted on input with a `DeprecationWarning`, and a
   query by a legacy name returns what it returned in 1.1: the store answers
   it by the legacy ref prefix (`tool:` for `tool_output`, `command:`,
   `mutation:`, and the coordination prefixes), since `tool` now covers both
   `tool:` and `command:` anchors.
8. **TypeScript binding**: `fileAnchor` returns `{ref, kind: 'file', digest}`
   instead of `metadata.sha256`. The binding's default output check stays
   the 1.1 one (an array; `confidence` only where the contract requires it);
   items, `inference_method` and an optional `confidence` are checked only
   under its `grounding` option.

**Options considered.**
- *Object-only items* (`items: {$ref: Anchor}`). A reference to one anchor
  would type as an object, but every 1.1 workflow that annotates an anchor as
  anything else (`${r.evidence_anchors: array<string>}`, `${r.evidence_anchors[0]: string}`)
  turns valid → B203. That breaks the rule that no 1.1-valid workflow becomes
  invalid. Phasing it in as a warning needs a validator special case keyed on
  the field name. Rejected.
- *Union items* (chosen). `compatible()` (core/src/types.rs) accepts a value
  of a union type where any member fits, so every annotation that was valid
  against `array<unknown>` is still valid; an unannotated reference stays
  B204, as in 1.1 (verified: `${r.evidence_anchors}`, `[0]` and `[0].ref` are
  all B204 today). The `Anchor` and `object` branches type alike
  (`union<object,string>`), so the third branch changes nothing for
  workflows. Typed references come in 2.0 when the legacy branches go.
- *`anyOf [Anchor, string]` only* (revision 1). It made every 1.1 object
  that is not an anchor (`{ref}` without a kind, the SDK's `tool_output`)
  invalid against the contract, and the binding refused them: a narrowing of
  what a 1.1 producer may return with no opt-in. The `object` branch keeps
  them valid; the anchor form is stated by the `$ref` and §6.5.
- *No `items` at all* (contract as in 1.1, anchor only in prose). Keeps
  every item value valid, numbers included, but leaves the anchor type out
  of every contract, generator and typed binding, which is ACS-06 itself.
  The chosen union refuses only items that are neither strings nor objects
  (numbers, booleans, null, arrays), which never named evidence; and only a
  caller that validates outputs against the rendered JSON Schema sees that,
  since no implementation refuses an output for its item shape outside a
  grounding policy. This is recorded as a deprecation, not as a §11.4
  addition.
- *Bare strings forbidden at once.* The SDK's `get_for_capability_output`
  and 42 skills write strings; forbidding them would make every such host
  non-conformant in a MINOR release. Deprecated instead.
- *A new kind per SDK value* (`command`, `mutation`, `coordination`). They
  describe what the agent did, not the medium of the evidence; one `record`
  kind covers the agent system's own records. The SDK keeps its distinction
  in the ref scheme (`mutation:…`, `delegation:…`).
- *Inline the anchor schema in each of the 36 outputs* (about 1,000 lines)
  vs `$ref` to the canonical type (chosen): the reference validator already
  resolves `$ref` in ontology contracts (core/src/validate/mod.rs 141–157);
  one generator learns `$ref`.
- *Kind as an `enum` with `x-` values listed elsewhere* vs a `pattern`
  (chosen, as `authenticated_by`).

**How it fixes the finding.** One item type with a schema for all 36
outputs, both canonical schemas, the SDK and the binding; one vocabulary; a
digest; rules for host kinds and ref schemes; the meaning of
`required_anchor_types` relative to `kind`; and the empty-list question
answered. The strict-catalog precondition of RFC-0005 8.5 is met: the union
keeps every repository catalog valid in strict mode (the only anchor
bindings, in `tests/fixtures/pass_orchestrator_port.workflow_catalog.yaml`,
annotate `array<object>`). Producers that wrote 1.1 forms are not refused:
the forms are deprecated, with 2.0 as the removal.

### ACS-21 — `inference_method` is carried by no schema; F505 is never raised

**Decision.**

1. **§3.1 rewritten.** A capability's output is the claim its step or call
   makes. It is **grounded** when `evidence_anchors` holds an anchor to
   evidence its producer had; **marked inferred** when it carries
   `inference_method` and `confidence`. An ungrounded output MUST be marked
   inferred. An output that reports an action its producer performed
   (`checkpoint`, `rollback`, `mutate`, `send`, `execute`, `audit`,
   `persist`, …) is a claim like any other and is grounded by a `record`
   anchor to that action or its record (`{ref: "checkpoint:cp-1", kind:
   record}`), or by an anchor to what the action read or wrote (the file it
   changed); its producer had that evidence, since it performed the action.
   The reference producers emit one: the Python SDK (`checkpoint:`,
   `mutation:`, `delegation:` and the other coordination refs, all kind
   `record`), the binding's example tools (`checkpoint_config` adds
   `checkpoint:<id>` beside its file anchors), and the `audit` and
   `persist` skills (`audit:<audit_id>`, `memory:<key>`). Outputs the
   executor builds itself are grounded in the run's own records and not
   checked.
2. **`inference_method`** (optional, all 36 outputs) is declared in the
   contracts as a plain string, since 1.1 §3.1 required it of ungrounded
   claims with no vocabulary and producers wrote free values. §4.1.1 lists a
   vocabulary that a producer SHOULD use: `model_knowledge`, `deduction`,
   `induction`, `abduction`, `analogy`, `statistical`, `simulation`,
   `assumption`, or `x-…`. Only under a grounding policy is an output that
   relies on its inference marking refused (F505) for a value outside it. An
   output MAY carry it beside anchors.
3. **`grounding@1`** (new must-understand extension, §5.20) with a workflow
   field `grounding: {require, kinds?, attested?}`. A host may give a
   **list** of **host policies** of the same shape when a run starts
   (executor start option; it covers the steps of nested runs too) or
   configure a list on a safety layer (calls). Every host-side constructor
   refuses an id the ontology does not define (`ValueError` in Python, a
   thrown `Error` in TypeScript, both naming V101), so a typo cannot
   silently turn a check off. Each policy that requires the step's
   capability applies on its own. `grounding::Policy::new(require, kinds,
   attested)` is public so that S6 adds a profile's policy beside the
   host's.
4. **The check** (§5.20), on each host `Output` for a step whose capability
   a policy requires, after the contract's required-field check (R402) and
   before after-gates: unavailable or mislabelled citations fail (F505);
   items that are not anchors do not count; the output passes when at least
   one anchor counts, or when it is marked inferred with a vocabulary method
   and a confidence from 0 to 1; otherwise F505. F505 is not retried (§5.2
   `retry` lists R401/R402/R406 only) and is added to the codes a failure
   mode can fire on.
5. **Executor-built outputs exempt**: `invoke`, a quorum's `constrain`, the
   output of a wait (`receive`, `synchronize`), and a `delegate` that waits
   (§5.13): neither its acceptance (`{accepted, task_id}`, which is not its
   claim) nor the result the executor composes from the event is checked,
   so a policy that requires `delegate` covers only delegations that do not
   wait. The executor skips the check in `output()` for such a step, which
   is where the acceptance arrives. With `grounding@1` declared, a completed
   `invoke` step's `evidence_anchors` are its nested run's anchors (step
   order, each `ref` once, `acs:` anchors left out); without it, `[]` as in
   1.1.
6. **Validation.** `grounding` without `grounding@1` is V106 in a workflow
   that targets 1.2 or later (S6's `semantics::target`); in one that
   targets 1.0 or 1.1, or declares no version, it is an unknown workflow key
   (W604), as in 1.1, so no 1.1-valid workflow becomes invalid.
7. **Profiles.** A profile's `evidence_policy` is a grounding policy:
   `require_grounding` → `require`, `required_anchor_types` → `kinds`. How a
   profile is applied to a run is S6's (ACS-05); the host start option (a
   list) and `Policy::new` are the interface.
8. **SECURITY.md §1.3** aligned with §3.1 (was SHOULD/MUST mixed).

**Options considered.**
- *Profile-only opt-in* (the finding's proposal): core has no notion of a
  profile, and how a profile is selected is S6's open decision. The
  workflow extension gives authors an opt-in that does not wait for it; the
  host policy gives S6 the hook. Both kept.
- *Opt-in by `spec_version: "1.2"`* (check every output of every 1.2
  workflow): which capabilities need checking is a deployment's choice (a
  profile's `require_grounding` names them), not a property of the version
  a catalog targets; checking all 36 would make the version declaration a
  runtime switch, and the executor does not see a header-declared version
  (S2b's finding). Rejected. (Revision 1 also argued that hosts return
  empty anchors for `checkpoint` or `audit`; under §3.1 as revised such an
  output is ungrounded, so that is no longer a reason.)
- *A base 1.2 field* (as S3's `agents`) vs an extension (chosen): grounding
  is opt-in runtime semantics like `wait@1` and `approval@1`; §5.9 exists so
  that a consumer that does not check it refuses the workflow.
- *A closed `inference_method` vocabulary in the contract* (revision 1,
  `pattern`): 1.1 required the field of every ungrounded claim with no
  vocabulary, so a 1.1 producer's `llm-reasoning` would become a contract
  violation without an opt-in. The vocabulary is a SHOULD in §4.1.1 and the
  description, enforced only where a policy opts in.
- *Scope the producer MUST to outputs that make a judgement* (action
  outputs exempt) vs a `record` anchor for actions (chosen): an action
  report is a claim (that the checkpoint exists, that the message was
  sent); the producer has its record, so grounding it costs one anchor and
  lets `require: [checkpoint]` mean something.
- *A new code for a fabricated citation*: F505 `PROVENANCE_MISSING` covers a
  claim whose provenance is missing or invalid; the message says which.
- *Filling `invoke` anchors always*: changes the output of a 1.1 run (two
  runtime fixtures pin `[]`). Gated on `grounding@1`.
- *Check a waiting delegate's composed output when its result arrives*
  (using the event's anchors) vs the exemption (chosen): the composed output
  inherits the acceptance's `evidence_anchors`, the result's anchors are in
  `result.anchors`, and the event path is shared with `receive` and
  `synchronize`, which are exempt as executor-built; checking it would need
  a second, event-shaped rule. The exemption is one condition and matches
  §3.1. Open question 6 asks whether 1.3 should check the result.
- *One host policy* (revision 1) vs a list: S6 applies one policy per
  profile, each on its own; a single slot would merge them.

**How it fixes the finding.** `inference_method` is in every output
contract; F505 has a defined, implemented, tested check in the executor,
the SDK and the binding; `require_grounding` gets a meaning; the rule for
hosts is stated (§5.20 *Hosts outside a workflow*); the executor's own
`invoke` outputs and a waiting delegation's acceptance no longer misfire;
action outputs have a stated way to be grounded.

### ACS-22 — Grounding does not require that the claimant had the evidence

**Decision.**

1. **§3.1 Available evidence.** An anchor grounds a claim only if the
   evidence was available to the claim's producer: obtained while the step
   or call ran, received as input (including anchors inside an input), or
   put in the request a model answered. A host MUST NOT return an anchor it
   knows its producer did not have; a host that assembles a model's context
   per request SHOULD check each anchor a model cites against that request.
2. **Executor-checkable citations.** `acs:<reference>` names a workflow
   value; its kind MUST be `record` (else F505, so a citation of a workflow
   value cannot be relabelled `file` to satisfy `kinds: [file]`). Under a
   grounding policy, the executor parses it (§5.3 body, no annotation) and
   requires it to be **covered** by one of the references the step's
   `input_bindings` make (not its condition or gates: the host never sees
   those values): the same root, and the bound path a segment prefix of the
   cited path, where an index or a slice within a bound slice matches that
   slice. `${search_out.results[0:3]}` covers `acs:search_out.results[1]`
   and `acs:search_out.results[1].url`, not `acs:search_out.results[7]`,
   `acs:search_out.total` (a sibling) or `acs:search_out` (a parent of the
   bound value). Else F505. The executor keeps each step's bound references
   (root and path), parsed once with the program.
3. **Host attestation.** An `Output` response MAY carry **`evidence_seen`**:
   the refs of the evidence the host attests its producer had for this
   answer, and nothing else: what it put in the model's request for it,
   anchors inside the step's inputs, and what the step's tool calls
   returned. A stored trace or history is not a source: a ref there was seen
   by some earlier request, not necessarily by this one. When present,
   every non-`acs:` anchor must be listed, else F505. An absent
   `evidence_seen` attests nothing; an empty list attests that the producer
   saw no evidence, so every non-`acs:` anchor then fails.
4. **Unattested anchors** count, as the host's word, unless the policy sets
   `attested: true`; then only established anchors (`acs:` checked, or
   listed in `evidence_seen`) count, and an output with none counts as
   inferred: it passes only when marked inferred, else F505.
5. **Calls.** Outside a workflow, `acs:<argument>` names an argument of the
   call, which the call received whole, so each argument name is a bound
   reference (root only). A layer that knows what was in the model's
   request for the call gives that as `evidence_seen`; a layer that does
   not (a Claude Code hook sees the tool call, not the request) gives none:
   absent, not an empty list. The TypeScript binding's `seen` option lists
   only the anchors inside the call's arguments (helper `refsIn(args)`) and
   what the tool's own code read during `execute`; the revision-1 helper
   `traceRefs`, which listed the whole stored trace, is removed, since
   attesting from stored history is the failure ACS-22 describes.

**Options considered.**
- *Attestation inside the output* (like `effective`) vs on the protocol
  response (chosen): the attestation is the host's statement to the
  executor about one response, not part of the claim; in the output it would
  be stored, snapshotted and bound by later steps, and could be long. The
  `Event` response already carries host attestations (`principal`,
  `identity`) beside the value.
- *Per-anchor `seen: true` flag*: a host passing a model's JSON through would
  pass a model-written flag; a list of what the host put in the request is
  something only the host produces, and lets the executor do the comparison.
- *Transitive availability* (a step may cite a store its inputs were derived
  from): the step did not receive that value. A step that needs it binds it.
- *Root-only availability* (revision 1): a step that binds
  `${search_out.results[0]}` could cite `acs:search_out.results[7]`, and one
  that binds `${r.data.x}` could cite `acs:r.secret`; both values reach the
  producer only if bound. The prefix rule is what "a value reachable
  through its references" means, and costs one comparison per segment.
- *An index of a bound slice counted from the slice* vs from the array
  (chosen): a citation names a workflow value as a binding would (§6.5), and
  a binding indexes the stored array, so `acs:r.items[3]` is item 3 of
  `r.items` whether the step bound `[2:5]` or `[0:4]`.
- *Fail unattested anchors by default*: every 1.2 host that cannot attest
  would fail every grounded step. Default counts them; `attested` is the
  strict opt-in. This is the finding's "counts as inferred, not failed": by
  default an unattested citation is not failed; under `attested` it no
  longer grounds the claim, which then stands only if marked inferred.

**How it fixes the finding.** A rule ties anchors to what the producer had;
the executor enforces it for workflow values, down to the bound path, and,
where the host attests from what it actually sent, for everything else; the
§5.17 limit (content carried by other means is beyond the executor) is
closed by the host duty and the attestation.

### ACS-23 — No normative rule keeps secrets out of evidence, audit records and stored data

**Decision.** New §6.7 *Secrets in Records*:

1. **Secret**: a value that grants access or proves identity (password, API
   key or token, session cookie, private or signing key, credential inside a
   URL or a header) and anything the host or its operator classifies as
   secret. The host decides how it recognises them; it SHOULD at least
   recognise the credentials it holds itself.
2. **Never written into**: evidence anchors, evidence records and
   notifications; canonical events; world-state records; audit records and a
   safety layer's records of calls; diagnostics and the `message`/`reason` of
   an `Error` a host returns (they reach traces and records); an executor's
   trace; the data a `persist` step stores.
3. **Redaction**: replace each secret (or the part of a string that is one)
   with `[REDACTED]`, or leave out the member or anchor. A documented-loss
   transform (§3.2): the marker shows where; a canonical event lists the
   changed members in an optional `redactions` (JSON pointers) and its `raw`
   is then the original with secrets replaced. A record MAY keep the SHA-256
   digest of a value that contains a secret (as the plugin's audit log keeps
   the digest of a tool input), never the digest of a secret alone; an
   implementation that cannot tell the two apart (a tool's whole response,
   which may be a one-line password file) keeps no digest of a value in
   which it recognises a secret.
4. **`persist`**: data that holds a secret the host recognises is refused,
   not redacted (memory is read back as fact): F504 on a tool-calling host,
   `Error` (R402) as a step.
5. **Workflows carry no secrets**: a catalog MUST NOT contain one; a host
   SHOULD NOT pass one through a run's inputs or outputs (run values reach
   state, snapshots and, through bindings, records); credentials are added
   where they are used. Approval `shown` values are what approvers decide
   on: an approval channel MAY display them redacted, saying so, while the
   digest stays that of the values (S2a's §5.14 rule).
6. **SECURITY.md**: new §1.5 *Secrets Stay Out of Records*, §1.3 aligned,
   STRIDE *Information Disclosure* row, §4.2 and §8.2 checklist lines.
7. **Implementations**: Python `Redactor` (registered exact values + a
   default pattern set) applied by every evidence store on append, by
   `CoordinationAuditLog.record`, and by `WorkflowRunner` to the `Error`
   messages it builds from exceptions; the evidence collector keeps a
   response's `digest` only when the redactor finds no recognised secret in
   it (a digest of a response that is, or holds, a secret could be inverted
   by guessing; one of a secret-free response cannot reveal one).
   TypeScript `redactJson` applied, always, to trace entries (anchors,
   `error`) before `completeTrace` and to notifications, with the default
   patterns; the `secrets` option only adds registered values. Code, not
   model instructions, refuses records that would hold a secret in the two
   skills that write them: the `persist` skill's `Edit` command hook and a
   new `audit` skill `Bash` command hook (for commands that append to
   `.claude/audit/records.jsonl`) run one shared scan (`hooks/secret_scan.sh`,
   copied verbatim into both hooks and kept equal by a test, as
   `validate_yaml_util_sync.py` keeps `safe_yaml.py` and `yaml_util.py`
   equal) and block a match (exit 2, `BLOCK: F504 CONSTRAINT_VIOLATED: …`).
   Each hook reads stdin once and blocks a call it cannot parse. The scan
   matches credential shapes (key and token formats, PEM keys, bearer
   tokens) and assignments whose value looks like a credential (quoted with
   no whitespace and 8+ characters, or unquoted, 12+ characters, mixing
   letters and digits), so prose such as `token: rotate monthly` passes.
   The `audit` skill's procedure cites outputs by reference or digest
   instead of including them. The plugin audit log already writes digests.

**Options considered.**
- *A digest of the secret as the marker* (`[REDACTED:sha256:…]`): a low-entropy
  secret (a password) is recovered by guessing. Plain marker chosen.
- *A `secret: true` flag on workflow inputs* so the executor keeps them out
  of traces and snapshots: a larger feature (every place the executor copies
  a value) for a case the "credentials are added where used" rule avoids.
  Rejected for 1.2; noted as an open question.
- *A validator warning for secret-looking literals*: needs a pattern engine
  in core (no regex dependency today) and is a heuristic; the rule is an
  author MUST the validator cannot decide. Not added.
- *Redact persisted memory instead of refusing*: the agent would read back a
  fact different from what it stored. Refuse.
- *Redact the `audit` skill's record in the hook* instead of blocking: a
  `PreToolUse` hook can only allow or block a command, and rewriting a
  shell command is not something it does reliably. Block, with the reason,
  so the skill rewrites the line by reference or digest.
- *A shared scan read at run time from `${CLAUDE_PLUGIN_ROOT}`*: skill
  frontmatter hooks are inline in this repository (no skill hook calls a
  script), and a skill copied out of the plugin must keep working. One
  source file, copied verbatim and tested, keeps one list without that
  dependency.
- *The revision-1 assignment pattern* (`(password|secret|token|api_key)`,
  `:`/`=`, 4+ characters): blocked ordinary project knowledge
  (`token: rotate monthly`), which is what `persist` writes. Narrowed to
  credential-shaped values.

**How it fixes the finding.** The Standard and SECURITY.md state the rule;
`raw` may be the redacted original with a marker; redaction is a §3.2
transform; tool input in SDK anchors stays opt-in (round 2) and is now
redacted when kept; every reference implementation that writes evidence or
records applies it, by code: the SDK stores, collector, coordination log
and runner, the binding's trace and notifications, and the plugin skills
that write memory or audit records.

### ACS-40 — The evidence store has no host-neutral contract

**Decision.** New §6.6 (normative, conditional on offering a store):

1. **Evidence record**: `record_id`, `anchor`, `recorded_at`, and where they
   apply `run_id`, `frame`, `step`, `capability`, `tool`, `call_id` (the
   correlation members of S2b's `ActionRecord`), optional `metadata`.
2. **An implementation that offers an evidence store**: appends and never
   changes or reorders a kept record, and never gives two records the same
   id, removed ones included; returns a record by id, and the records
   matching `capability`, `anchor.kind` or `run_id`, in append order;
   exports JSON Lines of `EvidenceRecord`; states its **durability**
   (`memory`, `session`, `durable`) and whether it is **bounded**; a store
   that removes records other than by their retention (to stay within a
   size, or when it is cleared) counts them and reports the count
   (`StoreInfo.removed`).
3. A host whose evidence must outlive the session exports each record when
   written to a `durable` store.
4. **Audit sink**: evidence records are not audit records (§6.4); a run's
   audit records go to whatever implements its `audit` steps and to where
   the host keeps executor records (§5.19.4); one store MAY hold both.
5. `schemas/interop/evidence.schema.json` (supporting, listed in §6.1):
   `EvidenceAnchor`, `EvidenceRecord`, `StoreInfo`, `EvidenceRecorded`.
6. **Python**: `EvidenceStoreProtocol`; `EvidenceStore` (memory, bounded,
   priority eviction kept) implements it, keeping a frozen copy of each
   anchor (attribute assignment and `mark_critical()` on a kept anchor
   raise; its metadata is a read-only deep copy), a sequence that `clear()`
   does not reset (cleared records count as removed), and legacy-kind
   queries answered by ref prefix; new `JsonlEvidenceStore` (durable,
   unbounded, append-only file; on open it truncates a last line that has
   no newline, which is an append that never completed, before it appends
   again); `WorkflowRunner(evidence_store=…)` records the anchors of an
   `Output` with `run_id`, `frame`, `step`, `capability` once the core has
   kept that output (the step's next trace entry for it is
   `step_completed`, not `step_failed`, `retry` or `delegated`), skipping
   and logging items that are not valid anchors; the evidence collector
   records `tool` and `call_id`; `GroundedAgentConfig.evidence_store` lets a
   caller supply the backend; `record_capture_failure()` (S2b's request)
   counted in `info()`.
7. **TypeScript**: `exportEvidence(state)` builds `EvidenceRecord`s from the
   thread's trace; `EVIDENCE_STORE_INFO = {durability: 'session', bounded: false}`.

**Options considered.** *Informative interop interface only* (the audit's
reading): would leave "how durable is the evidence" unstated, which is what
ACS-53 trips over. A small normative section, conditional on offering a
store, is the minimum that lets a binding in another language know what to
implement; the operations' spelling stays the binding's. *A required store
for every implementation*: the Standard does not require one for validators
or for executors (which do no I/O). *Making the coordination log pluggable*:
S2b converts `CoordinationAuditLog` to export `ActionRecord`s; an audit
store is §6.4's subject, not this one. *Recording each `Output` as soon as
the host answers* (revision 1): a malformed anchor raised `ValueError`
inside the runner, and anchors of an output refused with F505 or R402 were
kept as evidence. *A new core call that says whether an output was kept*:
the trace already says it (`step_completed` follows the stored output), so
the runner reads the entries added since its submit. *Making
`EvidenceAnchor` frozen*: callers build anchors and call `mark_critical()`
before adding them (a test does); only what the store keeps must not
change, so the store freezes its copy. *Truncate or terminate a torn last
line*: truncating leaves a valid JSON Lines file for readers that do not
go through the store; the bytes it drops were never a record.

**How it fixes the finding.** A storage-neutral interface with a stated
durability; the audit sink stated; the binding's thread-store trace exported
in the common shape; the Python store accepts a persistent backend.

### ACS-51 — The `confidence` principle contradicts the schemas; `confidence` is undefined

**Decision.**

1. **Principle reworded** (`meta.principles`): "Every capability output
   carries evidence anchors, or is marked inferred with an inference method
   and a confidence" and "A capability whose output contract requires a
   confidence returns one in every output".
2. **§4.1.1 Common Output Fields** defines `evidence_anchors`, `confidence`,
   `inference_method`, `uncertainty`. `confidence`: the producer's
   probability, 0–1, that the output's principal claim is correct (a
   contract MAY say more precisely, as `inquire`'s does); self-reported; a
   host that calibrates SHOULD document how; not a trust score; no threshold
   in the Standard — gates, conditions and profiles set them.
3. **Ontology**: `confidence` described on the 23 that require it and
   declared (optional) on the 13 that lack it (receive, execute, mutate,
   send, checkpoint, rollback, constrain, audit, persist, recall, delegate,
   synchronize, invoke), so an inferred output of any capability can carry
   one and a workflow can bind it.
4. **`Uncertainty` reconciled**: the event schema's type gains world
   state's optional `interval {low, high}` and `distribution`; the two are
   then equal (tested). Optional `uncertainty: {$ref: Uncertainty}` on every
   output but `measure`; when both are given, `uncertainty.confidence`
   equals `confidence`.
5. **`measure.uncertainty`** keeps its required-by-contract members `lower`
   and `upper` and gains `type`, `confidence`, `interval`, `distribution`,
   `notes` (all optional); `interval.low`/`high` then equal `lower`/`upper`.
6. **§8.1** "Confidence weight": "The confidence the source reports (§4.1.1)".
7. A repository test pins the 23/13 split and the principle text.
8. **Skills.** Each of the 33 capability skills that documents a
   `confidence` (all but `execute`, `mutate` and `invoke`) says, in its output
   contract table and its contract block comment, what the number is a
   probability of, citing §4.1.1: for the ten of the 13 that gloss it today,
   `receive` "that the parsed data is what was received", `send` "that the
   message was delivered as reported", `checkpoint` "that the checkpoint
   restores the state it reports", `rollback` "that the state now matches
   the checkpoint", `constrain` "that the verdict is right under the
   policy", `audit` "that the record was appended as reported", `persist`
   "that the data was stored as reported", `recall` "that the returned
   memories are correct for the query", `delegate` "that the delegation was
   accepted as reported", `synchronize` "that the agreed state is what the
   participants hold"; the other 23 rows are reworded the same way from
   their current subject (`predict`: "that the prediction holds; distinct
   from `probability`, the predicted event's probability"). A parse-error
   count, delivery confirmation or conflict count stays as guidance on how
   the producer estimates the probability. `docs/proposals/OASF_SAFETY_EXTENSIONS.md`
   §2.2 quotes the reworded principle. A test fails on a gloss that
   contradicts the definition.

**Options considered.** *Retype `measure.uncertainty` as `Uncertainty`*:
changes a required output's shape (MAJOR). *Declare `uncertainty` only on
the 23*: two rules where one serves. *A calibration field*: no consumer;
documentation suffices for now (open question). *Drop `confidence` from
the skills of action capabilities*: each of them can state a probability
of its report, and a workflow that binds `${s.confidence}` keeps working;
reworded instead. *Align only the ten*: the other rows' glosses
("methodology", "analysis completeness") contradict §4.1.1 too, and one
test over all rows is simpler than a list of exceptions.

**How it fixes the finding.** The principle matches the contracts;
`confidence` has a definition, and every skill that returns one uses it;
one `Uncertainty`; every output can carry one; thresholds are placed.

### ACS-53 — Retention fields assume a store that outlives the session

**Decision.**

1. **§6.3**: `retention_policy` and an `audit` step's `retention` apply to
   the store the records are written to. A `memory` or `session` store
   (§6.6) cannot keep a record past the process or session whatever its
   retention says; a host that must keep records longer exports each record
   when written to a durable store.
2. **`audit.retention`** is a duration (§5.10.1: `2555d`, `P30D`); absent,
   the store's own policy applies. A literal outside the grammar is **W614**
   (its description extended). The four repository uses are `2555d`, valid.
   A reference is not checked statically and is passed on unchanged.
3. **`audit` output `store`**: `name`, `durability`
   (`memory|session|durable`), `retention` (the duration the store applies).
   A host SHOULD report it; a host whose store does not outlive the session
   MUST NOT report `durable`. A workflow that needs a durable record stops on
   it with an after-gate: `${a.store.durability} != 'durable'`.
4. `world_state_schema.yaml` `retention_policy` and `max_age` descriptions
   name the store and the §5.10.1 grammar (P30D is a valid §5.10.1 duration,
   so nothing changes for existing values).

**Options considered.** *ISO-8601 only for `audit.retention`* ("the form
`max_age` uses"): the four healthcare steps use `2555d` and would warn.
§5.10.1 accepts both. *An error for a bad literal*: breaks 1.1 workflows.
*A `retention_met` boolean*: the host cannot know the session's length;
durability is what it knows. *A keyword for indefinite retention*: omit
`retention` and use a durable store whose policy keeps records; open
question.

**How it fixes the finding.** Retention is tied to a store; session-scoped
storage is named and reported; the workflow can react; `retention` has a
grammar and a check.

### ACS-58 — No defined notification for newly recorded evidence

**Decision.** §6.6 *Notification* (MAY): when a host stores evidence
records, a canonical event or an audit record (§6.4), it MAY notify its
clients with `EvidenceRecorded`: `type: "acs.evidence_recorded"`;
`record_ids` (evidence records), `event_id` (a canonical event) or
`action_ids` (audit records, by S2b's `ActionRecord.action_id`); `anchors`
(each `ref`, `kind`, optional `digest`; no `excerpt`; an audit record's own
`anchors`, possibly none); `capability`, `run_id`, `frame`, `step`,
`tool`, `call_id`, `recorded_at`. It is not a record; delivery may be at
most once; a client that needs the evidence or the record reads the store;
it carries no secret. One notification per append batch (one step's or one
call's anchors, or the audit records one write stores).

Python: `subscribe(listener)` on every store; listeners run after the
append, outside the store's lock; an exception in one is logged and does not
reach the appender or the other listeners. TypeScript: after a grounded
tool's trace entry is completed with anchors, `state.emit('acs.evidence_recorded', payload)`
when `emit` exists, in a `try` (at most once, as SA's `emit` is). The
executor emits nothing (no I/O); the Python runner's store notifies.

**Options considered.** *Interop schema only, no Standard text* (the
audit's reading): the maintainer asked for every finding to be implemented,
and a one-paragraph MAY with a schema lets conformance statements cite it.
*A trace kind carrying anchors*: the trace is pull-only and informative
(S2b). *One notification per anchor*: noisier, no gain. *Audit records
named by `record_ids`* vs a separate `action_ids` (chosen): `record_ids`
are evidence-store ids; one member per kind of id keeps a client from
looking an id up in the wrong store. *A second payload type for audit
records*: the finding asks for one notification for both; one `type`, with
the id member saying what was stored.

**How it fixes the finding.** One payload, one event name, for evidence,
canonical events and audit records, at-most-once semantics stated, the SA
form documented and implemented (the Python store and the binding emit it
for evidence; S2b's audit writers MAY emit it with `action_ids`).

~~~~markdown
### 3.1 Grounded Claims

Every claim MUST be evidence-backed or explicitly marked as inferred. The
output of a capability is the claim its step or call makes:

- It is **grounded** when its `evidence_anchors` (§4.1.1) holds an evidence
~~~~

~~~~markdown
#### 4.1.1 Common Output Fields

Every capability's output contract declares these fields, with the same
meaning in each:

| Field | Type | In the contract | Meaning |
|-------|------|-----------------|---------|
| `evidence_anchors` | array of evidence anchors (§6.5) | Required | What the output is based on (§3.1) |
| `confidence` | number from 0 to 1 | Required where the capability's contract requires it, optional elsewhere | The producer's probability that the output's claim is correct |
| `inference_method` | string | Optional | How an output not grounded in evidence was reached (§3.1) |
| `uncertainty` | `Uncertainty` (`event_schema.yaml#/types/Uncertainty`) | Optional | The uncertainty of the output's principal value |

**`confidence`** is a probability, from 0 to 1, that the output's principal
claim is correct: for `classify`, that its labels are right; for `predict`,

statistical or learned model), `simulation`, `assumption` (taken as given
without evidence), or a vendor value: `x-` followed by a lower-case letter
or digit, then lower-case letters, digits, `_`, `.` or `-`. With
`confidence`, it marks the output inferred (§3.1). The contracts declare it
as a string; under a grounding policy (§5.20), an output that relies on
being marked inferred MUST use a value of this vocabulary.

principal value; when an output has both, `uncertainty.confidence` equals

and `upper` of 1.1, the bounds of the value, and MAY carry the members of an
`Uncertainty` beside them; `interval.low` and `interval.high` then equal
`lower` and `upper`.

The ontology's `meta.principles` say the same: every output carries
evidence anchors or is marked inferred, and a capability whose output
contract requires a confidence returns one in every output.
~~~~

### 2.9 §5.20 Grounding *(new, after S2b's §5.19)*

~~~~markdown
### 5.20 Grounding

```yaml
spec_version: "1.2"
workflow_extensions:
  requires: [grounding@1]
grounding:
  require: [classify, predict, generate]
  kinds: [file, record, x-lab_result]
  attested: true
```

With `grounding@1` declared, a workflow MAY state a **grounding policy** in
`grounding`:

| Field | Description |
|-------|-------------|
| `require` | Required: the capabilities whose outputs are checked, a non-empty list of distinct ontology ids |
| `kinds` | A non-empty list of distinct anchor kinds (§6.5): only anchors of these kinds count |
| `attested` | Boolean, default false. When true, an anchor counts only when its availability is established: an `acs:` anchor (checked as below) or one whose `ref` the host lists in `evidence_seen` |

In a workflow that targets 1.2 or later (§11.5), `grounding` without the
declaration is V106; in one that targets an earlier version or declares
none, it is an unknown field (W604), as in 1.1. With the declaration, a
`grounding` that is not a mapping, a `require` or `kinds` that is not a
non-empty list of distinct strings, a kind outside §6.5's vocabulary and an
`attested` that is not a boolean are S303; a missing `require` is S304; an
id in `require` that the ontology does not define is V101; unknown fields
are W604. A workflow's policy applies to the workflow's own steps, not to
the steps of a workflow it invokes.

A host MAY also apply grounding policies, of the same three fields, to a
run, by giving a list of them when it starts the run (§5.19.2), and a
safety layer to the calls it covers (below). A policy a host applies to a
run applies to the steps of the run's nested runs (§5.12) as well as its
own. A host refuses a policy whose `require` names a capability the
ontology does not define, as a validator does (V101), rather than apply it
to nothing. A domain profile's `evidence_policy` states one:
`require_grounding` is its `require` and `required_anchor_types` its
`kinds`. Each policy that requires a step's capability applies on its own:
the output must pass every one.

**The check.** When a host answers a step's `InvokeCapability` with an
`Output` (§5.19.1), and a policy requires the step's capability, the
executor checks the output after the fields its contract requires (a
missing one is R402) and before its after-gates. A `delegate` step that
waits (§5.13) is not checked: its `Output` is the delegation's acceptance,
not its claim, and its result is an output the executor composes; a policy
that requires `delegate` covers the delegations that do not wait. The
`Output` MAY carry `evidence_seen`: a list of the `ref`s of the evidence
the host attests the output's producer had for this answer (§3.1): what it
put in the request a model answered, the anchors inside the step's inputs,
and what the step's tool calls returned. It lists nothing the producer did
not receive for this answer, such as an item of a stored history that the
request did not carry. An absent `evidence_seen` attests nothing; an empty
one attests that the producer had no evidence.

A reference (§5.3) B **covers** a reference C when they have the same root
and each segment of B's path matches the segment of C at the same
position: the same field name or the same index, or, where B's segment is
a slice, an index within it or a slice within it (indices count, for both,
from the start of the array the path names before the slice). C may go on
past B's path. For instance, `search_out.results[0:3]` covers
`search_out.results[1]` and `search_out.results[1].url`, but not
`search_out.results[7]`, `search_out.total` or `search_out`.

The executor reads `evidence_anchors`:

1. A value that is not a list fails the step: F505.
2. An item that is an object whose `ref` is a string starting with `acs:`
   cites a workflow value (§6.5). Its `kind` MUST be `record`, and the rest
   of its `ref` MUST be a reference body (§5.3, without `${`, `}` and a type
   annotation) that one of the references in the step's `input_bindings`
   covers; otherwise the step fails: F505. Its availability is established.
3. Any other item that is an **evidence anchor** (an object whose `ref` is
   a non-empty string and whose `kind` is in §6.5's vocabulary, with a
   `digest`, when present, of §6.5's form): when the `Output` carries
   `evidence_seen` and does not list its `ref`, the step fails: F505; when
   it lists it, its availability is established.
4. Any other item (a bare string, or an object that is not an evidence
   anchor, the deprecated forms of §6.5) does not count, and is not itself
   a failure.
5. An anchor of items 2 and 3 **counts** when its kind is in the policy's
   `kinds` (when the policy has them) and, under `attested`, its
   availability is established.

The output passes when at least one anchor counts. Otherwise it MUST be
marked inferred, with an `inference_method` of §4.1.1's vocabulary and a
`confidence` from 0 to 1, or the step fails: F505. F505 is not retried
(§5.2); a failure mode can fire on it (§5.12).

Outputs the executor builds itself are not checked (§3.1). With
`grounding@1` declared by the workflow a completed `invoke` step belongs
to, the step's `evidence_anchors` are the anchors of the outputs its nested
run stored, in the order of its steps, each `ref` once, and without `acs:`
anchors, which name the nested run's values; without the declaration they
are empty, as in 1.1.

**Hosts outside a workflow.** A safety layer (§5.18), or any host that runs
capabilities as calls without a workflow, applies the grounding policies
its configuration names to the output of each call whose capability one
requires, as above. An `acs:` anchor names an argument of the call
(`acs:<argument>`, or a path within it): each argument the call received
counts as a reference the call binds. A layer that knows what was in the
request the output answers gives that as `evidence_seen`; a layer that does
not know the request gives none (absent, not an empty list). It refuses an
output that fails with F505 (§5.18.8); the call has run, and the refusal is
what its caller is told.
~~~~

### 2.14 §6.5 Evidence Anchors *(new, after S2b's §6.4)*

~~~~markdown
### 6.5 Evidence Anchors

An **evidence anchor** names one piece of evidence. It is the item of a
capability output's `evidence_anchors` (§4.1.1), of a canonical event's
`anchors` (§6.2) and of the `anchors` of world-state records (§6.3): one
type, `event_schema.yaml#/types/Anchor`, which `world_state_schema.yaml`
repeats.

| Member | Required | Description |
|--------|----------|-------------|
| `ref` | Yes | Where the evidence is: a non-empty string |
| `kind` | Yes | What kind of evidence it is (below) |
| `timestamp` | No | ISO-8601 time at which the producer read or observed it |
| `excerpt` | No | A short quotation of it, as the producer read it; never a secret (§6.7) |
| `digest` | No | `sha256:` and the 64 lower-case hexadecimal digits of the SHA-256 of its content as the producer read it: the bytes `ref` names or, for a JSON value, its canonical JSON (RFC 8785) in UTF-8 |

Other members MAY appear; a producer's own SHOULD start with `x-`.

**Kinds.** `file`; `url`; `tool` (the result of a tool call); `log`;
`sensor`; `human_note` (something a person wrote); `api` (a response of a
service's API); `record` (a record the agent system itself wrote or holds:
an action or audit record, a checkpoint, a memory item, a workflow value);
or a vendor kind: `x-` followed by a lower-case letter or digit, then
lower-case letters, digits, `_`, `.` or `-`. A domain profile's
`required_anchor_types` and a grounding policy's `kinds` (§5.20) list kinds
of this vocabulary.

**Refs.** A `ref` is opaque to this Standard: a URI, or `<scheme>:<rest>`
with a scheme its producer documents (for instance `file:src/app.py#L10-L20`
or `tool:Read:toolu_01`). The scheme `acs:` is reserved: `acs:` followed by
a reference body as §5.3 writes it without `${` and `}` (for instance
`acs:search_out.results[0]`) names a workflow value, the one a binding with
that body would resolve to in the run, and its kind MUST be `record`.
Outside a workflow, `acs:<argument>` names an argument of the call (§5.20).

**Anchors of actions.** An output that reports an action its producer
performed is grounded by an anchor to the action's record, of kind
`record`, with a ref its producer documents (for instance
`checkpoint:<checkpoint_id>`, `audit:<audit_id>`, `mutation:<target>`), or
by an anchor to what the action read or wrote (§3.1).

**The legacy forms.** Before 1.2 an item of `evidence_anchors` was not
specified: producers wrote bare strings, and objects of their own shape
(without a `kind`, or with a kind outside this vocabulary, such as
`tool_output`). Both are still accepted there: a string reads as an anchor
with that `ref` and no kind, and an object that is not an evidence anchor as
its producer's own citation. Neither counts toward a grounding policy
(§5.20), and neither is refused for its shape: no implementation refuses an
output because of the shape of its `evidence_anchors` items unless a
grounding policy applies, and under one such an item only does not count.
Both are deprecated, and the next major version removes them (§11.2). A
producer SHOULD write evidence anchors. No validator can see an output, so
this deprecation is announced here rather than by W603. The items of an
event's or a record's `anchors` are evidence anchors.
~~~~

### 2.15 §6.6 Evidence Records and Stores *(new)*

~~~~markdown
### 6.6 Evidence Records and Stores

An **evidence record** is an evidence anchor kept with the context it was
recorded in: `record_id` (unique within its store), `anchor` and
`recorded_at` (ISO-8601), and, where they apply, the run's `run_id`,
`frame` and `step` (§5.19), the `capability`, and a call's `tool` and
`call_id` (§5.18). `schemas/interop/evidence.schema.json` defines it
(`EvidenceRecord`).

An **evidence store** keeps evidence records for later reading. This
Standard requires none. An implementation that offers one:

1. appends records, never changes or reorders a record it has kept, and
   never gives a record the `record_id` of another, including one it has
   removed;
2. returns a record by its `record_id`, and the records whose `capability`,
   `anchor.kind` or `run_id` match a given value, in the order they were
   appended;
3. exports its records as JSON Lines, one `EvidenceRecord` per line, in the
   order they were appended;
4. states its **durability**: `memory` (its records are lost when its
   process ends), `session` (deleted with the session, conversation or
   thread they belong to) or `durable` (kept until its retention removes
   them, §6.3); and whether it is **bounded**, that is, removes records
   before their retention ends to stay within a size. A store that removes
   records other than by their retention (because it is bounded, or when it
   is cleared) counts them and reports the count with what it exports
   (`StoreInfo.removed`).

A host whose evidence must outlive the session SHOULD NOT rely on a
`memory` or `session` store: it exports each record, when it is written, to
a `durable` one.

Evidence records are not audit records (§6.4). A run's audit records go to
whatever implements its `audit` steps and to where the host keeps the
executor's records (§5.19.4); a host MAY keep evidence records and audit
records in one store.

**Notification.** When a host stores evidence records, a canonical event
(§6.2) or audit records (§6.4), it MAY notify its clients with an
`EvidenceRecorded` payload (`schemas/interop/evidence.schema.json`): `type`
`acs.evidence_recorded`; what was stored: the evidence records'
`record_ids`, the canonical event's `event_id`, or the audit records'
`action_ids`; the `anchors` of what was stored, each as its `ref`, `kind`
and `digest` (an audit record's own `anchors`, possibly none); and, where
they apply, `capability`, `run_id`, `frame`, `step`, `tool`, `call_id`, and
`recorded_at`. A notification is not a record: it MAY be delivered at most
once, and a client that needs the evidence or the record reads the store.
It carries no `excerpt` and no secret (§6.7).
~~~~

### 2.16 §6.7 Secrets in Records *(new)*

~~~~markdown
### 6.7 Secrets in Records

A **secret** is a value that grants access or proves identity (a password,
an API key or token, a session cookie, a private or signing key, a
credential inside a URL or a header), and any value the host or its
operator classifies as secret. How a host recognises secrets is its own
choice; it SHOULD at least recognise the credentials it holds itself.

**Where secrets never go.** An implementation MUST NOT write a secret into:

- an evidence anchor, an evidence record or a notification (§6.5, §6.6);
- a canonical event (§6.2) or a world-state record (§6.3);
- an audit record (§6.4) or a safety layer's record of a call (§5.18.8);
- a diagnostic (§9.8), or the `message` or `reason` of an `Error` a host
  returns (§5.19.1), which reach a run's diagnostics, trace and records;
- an executor's trace;
- the data a `persist` step or call stores.

**Redaction.** An implementation that would write a value holding a secret
into one of these redacts it: it replaces each secret, or the part of a
string that is one, with the string `[REDACTED]`, or leaves out the member
or the anchor that holds it. Redaction is a transform with documented loss
(§3.2): the marker shows where the loss is, and a canonical event MAY list
the members it changed in `redactions` (§6.2), its `raw` then being the
original with its secrets replaced. A record MAY hold, in place of a value
that contains a secret, the SHA-256 digest of the whole value (a tool's
whole input, say), so that a reader who has the value can confirm it; it
MUST NOT hold the digest of a secret alone, which guessing can invert. An
implementation that cannot tell whether such a value is more than the
secret it holds (a file's whole content, a tool's whole response) keeps no
digest of it.

Data a `persist` step or call would store that holds a secret the host
recognises is refused, not redacted, since memory is read back as fact:
a tool-calling host refuses the call with F504 (§5.18.8); a host answering
a step returns an `Error` with reason `secret_in_data` (§5.19.7), and the
step fails with R402.

**Workflows carry no secrets.** A catalog MUST NOT contain a secret. A host
SHOULD NOT pass one through a run's inputs or a step's output, since a
run's values are kept in its state and snapshots and reach records through
bindings: it adds a credential where it is used, to the request a
capability makes. The values an approval request shows (§5.14) are what the
approvers decide on; an approval channel MAY display them with secrets
replaced, saying so, and the digest stays that of the values.
~~~~

### 5.1 Rust core

**`core/src/grounding.rs` (new; `pub mod grounding;` in `lib.rs`).** Pure

```rust
use crate::refs::{Ref, Seg};

pub const KINDS: &[&str] = &["file", "url", "tool", "log", "sensor", "human_note", "api", "record"];
pub const METHODS: &[&str] = &["model_knowledge", "deduction", "induction", "abduction",
                               "analogy", "statistical", "simulation", "assumption"];
/// `x-` then [a-z0-9] then [a-z0-9_.-]* (moved here from validate/identity.rs).
pub fn vendor(v: &str) -> bool;
pub fn is_kind(k: &str) -> bool;          // KINDS or vendor (the name S6's profile.rs uses)
pub fn is_method(m: &str) -> bool;        // METHODS or vendor
pub fn digest_ok(d: &str) -> bool;        // "sha256:" + 64 of [0-9a-f]
/// An evidence anchor of §6.5: object, non-empty string `ref`, `kind` with
/// is_kind, `digest` absent or digest_ok.
pub fn is_anchor(v: &Value) -> bool;

#[derive(Debug, Clone, PartialEq, Default, Serialize, Deserialize)]
pub struct Policy {
    pub require: Vec<String>,
    #[serde(default)] pub kinds: Option<Vec<String>>,
    #[serde(default)] pub attested: bool,
}
impl Policy {
    /// Shape check (non-empty distinct `require`; `kinds` non-empty,
    /// distinct, each `is_kind`). Ontology ids are checked by the caller
    /// that holds the ontology (`check_ids`). Public for S6.
    pub fn new(require: Vec<String>, kinds: Option<Vec<String>>, attested: bool) -> Result<Policy, String>;
    /// `Err` names the first id the ontology lacks, with V101's closest-match hint.
    pub fn check_ids(&self, ontology: &Ontology) -> Result<(), String>;
    pub fn requires(&self, capability: &str) -> bool;
    /// From a validated `grounding` mapping (the validator checked it).
    pub fn from_value(v: &Value) -> Option<Policy>;
}

/// §5.20 "covers": same root; each segment of `bound.path` matches the
/// cited segment at its position (equal field or index; a bound slice
/// [a:b] matches an index i with a <= i < b, or a slice [c:d] with
/// a <= c and d <= b, absent bounds being 0 and unbounded); the citation
/// may be longer.
pub fn covers(bound: &Ref, cited: &Ref) -> bool;

/// The bound references of a value (input_bindings), every `${...}` in it
/// that parses, annotation dropped; sorted and deduplicated by text.
pub fn bound_refs(v: &Value) -> Vec<Ref>;
/// Parse caller-given bodies (Python, vectors); Err names the bad one.
pub fn parse_bound(bodies: &[String]) -> Result<Vec<Ref>, String>;

#[derive(Debug, Clone, Copy, PartialEq, Eq, Serialize)]
#[serde(rename_all = "snake_case")]
pub enum Status { Grounded, Inferred }

#[derive(Debug, Clone, PartialEq)]
pub struct Checked { pub status: Status, pub counted: usize, pub legacy: usize, pub unattested: usize }

/// §5.20 for one output. `Err(message)` is F505.
pub fn check(output: &Value, policy: &Policy, bound: &[Ref],
             seen: Option<&[String]>) -> Result<Checked, String>;
```

`check` follows §5.20 items 1–5 in order and stops at the first F505. Item
2 applies to any object item whose `ref` is a string starting `acs:`: kind
must be `"record"`; `crate::refs::parse_ref(&r[4..])` must succeed with
`annotation == None`; some `b` in `bound` must `covers(b, &cited)`. Item 3
uses `is_anchor`; item 4 counts the rest into `legacy`. The inference test
(only when nothing counts) requires `inference_method` with `is_method` and
`confidence` a JSON number in [0, 1] (not a bool). Messages name the item:
`evidence_anchors[2] cites 'acs:search_out.results[7]', which the step's
input_bindings do not cover (they bind search_out.results[0:3]) (§3.1)`,
`evidence_anchors[0] cites a workflow value with kind 'file'; an acs: anchor
is of kind record (§6.5)`, and for an ungrounded output one sentence saying
why nothing counts (`no anchors` / `N items that are not evidence anchors,
which do not count` / `N anchors of kinds the policy does not list` / `N
anchors whose availability is not established`) followed by `and it is not
marked inferred (inference_method of §4.1.1's vocabulary and a confidence
from 0 to 1, §3.1)`; a present but invalid `inference_method` or
`confidence` is named. Unit tests read `tests/conformance/grounding/check.json`
(`include_str!("../../tests/conformance/grounding/check.json")` in
`core/tests/grounding.rs`), passing `parse_bound(bound_refs)`.

## 9. RFC text: `spec/RFC-0008-evidence-grounding-and-secrets.md`

~~~~markdown
# RFC-0008: Evidence, grounding and secrets
**Status:** Accepted
**Target:** Standard v1.2.0
**Date:** 2026-11-15

## Summary

Standard 1.1.0 says every claim must be evidence-backed or marked as
inferred (§3.1), and gives that sentence nothing to stand on: the 36
capability outputs require `evidence_anchors` with no item schema, the
repository holds three anchor vocabularies, `inference_method` is in no
schema, F505 is reserved and never raised, nothing ties a citation to what
its producer saw, no rule keeps secrets out of evidence and records, the
evidence store has no contract, retention ignores where records live,
`confidence` is undefined and contradicted by the ontology's own
principle, and no notification exists for recorded evidence.

This RFC records the decisions Standard 1.2.0 makes on findings ACS-06,
ACS-21, ACS-22, ACS-23, ACS-40, ACS-51, ACS-53 and ACS-58 of the
[Standard Agents mapping](../docs/research/analysis/standard_agents_mapping/findings_agent_capability_standard.yaml).
It takes over decision 8 of [RFC-0005](RFC-0005-tool-calling-hosts.md)
(one anchor item, one kind vocabulary), withdrawn there, and answers its
open question 5. It is Accepted by the maintainer's instruction that every
remaining finding is implemented in 1.2.0; the text is in
[STANDARD-v1.2.0](STANDARD-v1.2.0.md) §3.1, §4.1.1, §5.20, §6.5, §6.6 and
§6.7.

## Motivation

- A consumer cannot check an anchor whose shape each producer chooses. The
  event schema allows seven kinds, the world state schema six, the Python
  SDK writes five others, a profile's `required_anchor_types` matches none,
  and the skills write bare strings. No schema has a digest, so a consumer
  cannot tell whether the cited content changed.
- §3.1 is called non-negotiable, but an output with `evidence_anchors: []`
  runs through the reference executor unremarked, and `inference_method`,
  the field §3.1 requires of an ungrounded claim, exists nowhere. A naive
  check would misfire: the executor builds `invoke` outputs with empty
  anchors itself.
- On a host that assembles a model's context for each request, a model can
  cite a stored item it never received. §5.17 says the executor cannot see
  content carried by other means; nothing asks the host to.
- §6.2 requires an event's `raw` to be "original unmodified data", so a host
  that redacts a credential contradicts the Standard and one that does not
  writes it into evidence. The rules existed only as model instructions in
  skills.
- A binding in another language has no evidence store interface to
  implement, and no way to say whether its evidence outlives the session; a
  retention period written to session-scoped storage cannot be kept, and
  nothing reports it.
- `meta.principles` says every capability returns confidence; 13 outputs do
  not declare it, and nowhere says what it measures.
- A host that pushes records to clients, as Standard Agents does, has the
  transport and no payload.

## Goals

- One evidence anchor type for capability outputs, events and records, in
  the canonical schemas, the ontology, the Python SDK and the TypeScript
  binding.
- A definition of grounded and inferred outputs, and a check (F505) that a
  workflow or a host opts into, implemented by the reference executor, the
  SDK and the binding, with language-neutral vectors.
- A rule tying a citation to the evidence its producer had, checkable for
  workflow values and attestable by the host for the rest.
- A normative rule keeping secrets out of evidence, records, diagnostics,
  traces and persisted memory, with a redaction marker.
- A small, storage-neutral contract for evidence stores with a stated
  durability, and an optional notification.
- Definitions of `confidence`, `inference_method` and `uncertainty`, and an
  ontology principle that matches the contracts.
- No 1.1-valid workflow becomes invalid; no 1.1 run behaves differently
  unless it opts in.

## Non-goals

- How a domain profile is selected and applied to a run (ACS-05, RFC-0010).
  This RFC states what a profile's `evidence_policy` means as a grounding
  policy; the host start option is the interface.
- Which anchor supports which field of an output: grounding is per output.
- Calibration of confidence, and thresholds: gates, conditions and profiles
  set those.
- A secret detector: the host decides what is secret. The reference
  implementations ship an informative default pattern set.
- Audit records (§6.4, RFC-0006 Part B) and the host protocol (§5.19), which
  this RFC only extends with `evidence_seen`, a start option (a list of
  grounding policies), and the optional notification of a stored audit
  record (`action_ids`).
- Privacy of personal data: the redaction mechanism applies, the policy is
  the deployment's.

## Key decisions

### 1) One evidence anchor (ACS-06)

`event_schema.yaml#/types/Anchor` 1.2.0, repeated by
`world_state_schema.yaml`: `ref` and `kind` required; `timestamp`,
`excerpt`, `digest` (`sha256:` + 64 hex, of the content as read; RFC 8785
canonical JSON for a JSON value) optional. Kinds: the event schema's seven,
`record` (the agent system's own records and workflow values), and vendor
kinds `x-…`. `ref` is opaque except the reserved `acs:` scheme.

### 2) Output items are anchors; other forms are deprecated, not refused (ACS-06, RFC-0005 OQ5)

All 36 outputs' `evidence_anchors` items are `anyOf [Anchor, string,
object]`. The anchor is the form. A bare string, and an object that is not
an evidence anchor (no kind, a kind such as `tool_output`), are the
deprecated legacy forms of 1.1 producers: accepted, never counted toward a
grounding policy, and removed in 2.0. No implementation refuses an output
because of the shape of its items unless a grounding policy applies, and
under one a legacy item only does not count. For workflows the union keeps
every annotation valid in 1.1 valid (verified on every repository catalog);
an unannotated element reference stays B204 until 2.0. An empty list
grounds nothing.

### 3) Grounded, inferred, and the evidence a producer had (ACS-21, ACS-22)

§3.1: an output is grounded when it holds an anchor to evidence its
producer had (obtained while it ran, received as input, or in the request a
model answered); otherwise it MUST carry `inference_method` and
`confidence`. An output that reports an action its producer performed is a
claim too, grounded by a `record` anchor to the action's record
(`checkpoint:<id>`, `audit:<id>`) or by what the action read or wrote; the
reference producers emit one. A host MUST NOT return an anchor it knows its
producer did not have. Outputs the executor builds itself, including a
waiting delegation's acceptance and result, are not checked.

`inference_method` is a plain string in the contracts, because 1.1 asked
for it with no vocabulary; §4.1.1 gives a vocabulary (with `x-` values) a
producer SHOULD use, and a grounding policy requires it of an output that
relies on being marked inferred.

### 4) `grounding@1` and F505 (ACS-21)

A must-understand extension with a workflow policy (`require`, `kinds`,
`attested`), host run policies of the same shape (a list given at start,
covering the steps of nested runs), and the same policies on a safety layer
for calls. Every host-side policy is checked against the ontology: an
unknown capability id is refused, never silently ignored. The executor
checks each host `Output` of a required capability: an `acs:` citation that
is not of kind `record` or that no reference the step binds covers (same
root, the bound path a segment prefix of the cited one, an index within a
bound slice counting), and an anchor missing from the host's
`evidence_seen`, fail with F505; otherwise the output passes when an anchor
counts or when it is marked inferred with a vocabulary method and a
confidence. F505 is not retried and can fire a failure mode. With
`grounding@1`, an `invoke` step carries its nested run's anchors. In a
workflow that targets 1.2, `grounding` without the extension is V106; in a
1.0 or 1.1 workflow it stays an unknown key (W604).

### 5) Attestation on the response (ACS-22)

`evidence_seen` is an optional member of the `Output` response, not of the
output: it is the host's statement about one answer, like `principal` and
`identity` on `Event`. It lists what the producer received for that answer
and nothing from stored history. Absent, it attests nothing; empty, it
attests that nothing was seen. A host that does not know the request (a
hook that sees only the tool call) omits it. `attested: true` counts only
established anchors, so an unattested output counts as inferred.

### 6) Common output fields (ACS-51)

§4.1.1 defines `confidence` (a self-reported probability that the output's
claim is correct; no threshold in the Standard), `inference_method` and
`uncertainty`. Every output declares all three; the event schema's
`Uncertainty` gains `interval` and `distribution`; `measure.uncertainty`
keeps `lower`/`upper` and gains the `Uncertainty` members. The ontology
principle is reworded, and every capability skill's `confidence` gloss
states what it is a probability of.

### 7) Evidence records and stores, and a notification (ACS-40, ACS-58)

§6.6: an evidence record is an anchor with its correlation (`run_id`,
`frame`, `step`, `capability`, `tool`, `call_id`). An implementation that
offers a store appends only, never reuses an id, reads by id and by
capability, kind and run, exports JSON Lines, states its durability
(`memory`, `session`, `durable`) and whether it is bounded, and counts the
records it removes other than by retention. Evidence records are not audit
records. A host MAY send `acs.evidence_recorded` when it stores evidence
records, a canonical event or audit records (named by `record_ids`,
`event_id` or `action_ids`); it is not a record and may be delivered at
most once. `schemas/interop/evidence.schema.json` defines the four shapes.

### 8) Retention follows the store (ACS-53)

Retention applies to the store records are written to; a session-scoped
store cannot keep a record longer. `audit.retention` is a §5.10.1 duration
(W614 for a literal outside it), and `audit` reports its `store`, so a
workflow can stop when the record will not outlive the session.

### 9) Secrets stay out of records (ACS-23)

§6.7 defines a secret and lists where it never goes: evidence, records and
notifications, events, world-state and audit records, diagnostics and host
error messages, traces, persisted data. Redaction replaces a secret with
`[REDACTED]`, a documented-loss transform (§3.2); an event's `raw` may be
the redacted original and MAY list `redactions`. A record MAY hold the
digest of a whole value that contains a secret, never the digest of a
secret alone; an implementation that cannot tell the two apart (a tool's
whole response) keeps no digest of a value in which it recognises a secret.
Persisting a secret is refused, not redacted. Workflows
carry no secrets: a host adds credentials where they are used. In the
reference implementations the rule is enforced by code: the SDK's stores,
collector, coordination log and runner, the binding's trace and
notifications (always), and the plugin's `persist` and `audit` skills,
whose command hooks share one scan and block credential-shaped content with
F504.

## Backward compatibility

- Opt-in: `grounding@1`, a host's grounding policies, `evidence_seen`, the
  filled `invoke` anchors. A 1.1 validator refuses the extension (V106).
  V106 for `grounding` without the extension applies only to workflows that

## Alternatives considered

- **Object-only anchor items, or `anyOf [Anchor, string]`.** Typed element
  references, but 1.1 workflows that annotate anchors as strings would
  become invalid (object-only), and 1.1 producers' objects without a kind
  would violate the contract with no opt-in (both). Rejected for 1.x.
- **No item schema at all.** Leaves the anchor type out of every contract
  and generator, which is the finding.
- **Forbid bare strings now.** The SDK and 42 skills write them. Deprecated
  instead.
- **A closed `inference_method` vocabulary in the contract.** Would make a
  1.1 producer's free value a contract violation without opting in. A
  SHOULD, enforced under a policy.
- **Opt in by `spec_version: "1.2"`.** Which capabilities to check is a
  deployment's choice, not a property of a catalog's target version; the
  executor does not see a header-declared version. Rejected for an
  extension.
- **Profile-only opt-in.** The Standard does not yet say how a profile is
  applied; a workflow extension and a host option do not wait for it.
- **Root-only availability of `acs:` citations.** A step that binds one
  element could cite another; the bound path is the unit.
- **Check a waiting delegate's result when it arrives.** Needs a second,
  event-shaped rule for an output the executor composes; exempt, as other
  wait outputs are (open question 6).
- **Attestation in the output.** It would be stored, snapshotted and bound;
  the protocol response is where hosts already attest. Attestation from a
  stored trace is rejected: it is the failure the rule is meant to stop.
- **Fail unattested citations by default.** Every host that cannot attest
  would fail; `attested` makes it the workflow's choice.
- **A digest of a secret as the redaction marker.** Low-entropy secrets
  would be recoverable by guessing.
- **A validator warning for secret-looking literals.** A heuristic needing a
  pattern engine in the core; the catalog rule stays the author's.
- **Model instructions only in the plugin skills.** The finding; code
  checks in both skills that write records instead.
- **An informative-only store interface.** Leaves durability, which
  retention depends on, unstated.
- **A separate notification type for audit records.** One payload with an
  id member per kind of store is simpler for clients.
- **Retype `measure.uncertainty` as `Uncertainty`.** Changes a required
  output shape (MAJOR).

## Open questions

1. **Secret inputs.** Should 1.3 let a workflow mark an input `secret`, so
   the executor keeps it out of its trace, records and snapshots, instead of
   relying on hosts to add credentials where they are used?
2. **Indefinite retention.** Should `audit.retention` accept a keyword for
   "keep until removed by hand", or is a durable store without retention
   enough?
3. **Calibration.** Should a host be able to state, in a machine-readable
   field, how its confidences are calibrated, so a profile's
   `minimum_confidence` can require calibrated ones?
4. **Per-field grounding.** Should an anchor be able to say which output
   field it supports, for outputs that combine grounded and inferred parts?
5. **Typed anchors in 2.0.** When the legacy forms are removed, should
   `evidence_anchors` become `minItems: 1` for capabilities whose outputs
   are always about external evidence, or stay grounding-policy driven?
6. **Waiting delegations.** Should a later version check the result of a
   waiting `delegate` against the delegate's own anchors (the event's
   `anchors`), now that a policy requiring `delegate` covers only
   delegations that do not wait?
7. **Plugin scan reach.** The `audit` skill's hook scans the command that
   appends the record; a record copied from an intermediate file is outside
   it, and the skill's procedure forbids that path. Should the plugin's
   global `PreToolUse` hook refuse any write to `.claude/audit/records.jsonl`
   that does not carry the record as a literal?
~~~~
